# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This document is a continuation of `01-UI-SPEC.md`, not a replacement.** Phase 1's approved
contract — the spacing scale, the four-size two-weight type scale, the colour roles, the
interaction and accessibility baseline, and the pure-core boundary as a UI rule — remains
binding in full. This document states only what is **added** and what is **amended**.
Where this document is silent, Phase 1's contract governs.

**Scope:** the four surfaces Phase 2 renders or reshapes — the landing screen, the config
screen, the two-pane shared draft screen, and the six confirmation dialogs — plus the two
token-system extensions (three display densities, eighteen type colours) that the pool card
needs.

**Binding upstream:** `02-CONTEXT.md` (D-01…D-39, all locked), `01-UI-SPEC.md` (approved),
`01-CONTEXT.md` (D-06, D-07, D-08, D-10, D-13 load-bearing), `CLAUDE.md` §Conventions and
§Architecture, `.planning/REQUIREMENTS.md` (DRFT-01, 02, 03, 05–16, BAN-01, BAN-02, BAN-08,
RULE-07), `.planning/ROADMAP.md` §Phase 2.

## Amendments to Phase 1's Contract

Three Phase 1 contracts are deliberately broken by this phase. Each is listed with the exact
text it replaces. **`tokens.css` must be edited in the same change that breaks it** — a stale
contract comment is worse than no comment, because the next reader trusts it
(02-CONTEXT §Specific Ideas).

### Amendment 1 — the density contract (supersedes `src/ui/tokens.css:10-11`)

**Removed text:**

> Phase 2 density contract: the densities change exactly four tokens —
> `--sprite-lg`, `--cell-min`, `--cell-h`, `--text-label`. Nothing else.

**Replacement contract (D-25):**

1. Density is carried by one attribute, `data-density="minimal|standard|full"`, on the **pool
   pane root**. That attribute redeclares exactly **three** tokens: `--sprite-lg`,
   `--cell-min`, `--cell-h`. See §Density Contract for the values.
2. `--text-label` is **removed from the density-varying set.** The type scale is invariant
   across densities. This is stricter than Phase 1, not looser: it makes it structurally
   impossible for a density to shrink text below 14px, which is what DRFT-14 needs, and it
   removes the hazard that a density swap introduces a fifth font size into a scale the
   contract fixes at four.
3. Density additionally changes the **content** of `MonCard` — the whole reason the four-token
   rule had to go. Pure scaling cannot deliver a usable "full" density, because six 14px
   numbers in a 112px cell are unreadable at any scale. See §Density Contract for the
   content table.
4. Because the redeclaration is scoped to the pool pane subtree, the board pane never inherits
   it. **This is how D-24 ("density affects the pool only") is enforced structurally rather
   than by discipline.** A density that reached the board would have to be written into a
   second selector to do so.

### Amendment 2 — the reserved-colour rule (supersedes `src/ui/tokens.css:80`)

**Removed text:**

> The focus ring is the accent, always. Reserved use 3 of 3.

**Replacement contract (D-26, D-27):** colour in this project is reserved for four things, not
three. The three semantic reservations from Phase 1 are unchanged — accent (3 uses), danger
(now 3 uses, see §Color), focus ring — and a fourth is added:

4. **The type palette.** Eighteen hues, one per Pokémon type, a closed enumerated set derived
   from roster data. A type hue may appear on a pool-card type pill and on a type filter
   control (D-29) and **nowhere else**. It never marks state, never marks emphasis, never
   marks a control, and never appears on a board chip.

The palette is a real expansion of the token system and is documented as such in the full
token table below, with every pairing's measured ratio.

### Amendment 3 — one-click undo narrowed (narrows Phase 1 D-10)

Phase 1 D-10 is "unlimited undo, one click, no confirmation". D-37 narrows it: **undo confirms
only when the pick being undone belongs to a round earlier than the round the draft is
currently on.** The mechanism is unchanged (`log.pop()` plus a re-fold), the cheap case stays
one click, and the expensive case — where several players' picks are at stake — gains a stop.

Because undo removes exactly one pick, this fires exactly at a round boundary: the last pick
was the closing pick of Round *r*, the draft is on Round *r+1*. Walking back two rounds costs
one or two confirms, never one per pick. The confirm dialog is specified in §Confirmation
Dialogs; it is **not** danger-toned, because Phase 1's rule that "undo must read as routine
and reversible" still holds.

`Ctrl+Z` / `Cmd+Z` routes through the same gate. A keyboard undo that crosses a round boundary
opens the same dialog; it does not bypass it.

## A tension in the locked set, resolved here

D-18 and D-19 lock "either pane expandable to full width", three discrete states. ROADMAP
Phase 2 criterion 5 requires the shared screen to show the full board "at every moment", and
02-CONTEXT §Specific Ideas states "any proposal that puts the board behind a tab or a toggle
fails it". `pool-full` puts the board behind a toggle.

**Resolution — the control shape is kept, its availability is scoped:**

| Screen | States available |
|--------|-----------------|
| Config screen (ban grid section) | `split` is meaningless here — the ban grid is full-width by default; the density control and filter bar are shared, the expand control is not rendered |
| Draft screen, draft in progress | `split` and `board-full` only. The pool pane's expand button is **not rendered.** |
| Completed-draft screen | `split`, `pool-full`, `board-full` — the draft is over, criterion 5 no longer binds, and 8 stacked export panels are exactly what wants full width |

The persisted state model still carries all three values (D-20), so the control's shape is set
for later phases and nothing is redesigned. If the persisted value is `pool-full` when a draft
screen mounts, it is **coerced to `split`** and the coercion is silent.

This is recorded as a spec resolution rather than absorbed silently, because it declines part
of a locked decision's reach. The planner should read it as such.

## Design System

Unchanged from Phase 1. Restated because the constraint is absolute.

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-built Preact components under `src/ui/` |
| Icon library | none. The one glyph this phase needs is the text character `×` (U+00D7) on a ban chip, `aria-hidden`. No icon file, no icon font, no SVG. |
| Font | system stack, no webfont (Phase 1 §Typography) |

**Hard constraint — do not violate.** `CLAUDE.md` pins the project to exactly two runtime
dependencies (`preact@10.29.8`, `@preact/signals@2.10.1`), both exact-pinned. No CSS
framework, no CSS-in-JS runtime, no component registry, no icon package, no combobox library,
no colour library. This phase adds a typeahead, six segmented controls, a two-pane splitter
and a roving-tabindex grid — every one of them hand-built. A third runtime dependency is a
constraint violation, not a trade-off.

**Styling mechanism:** unchanged. `src/ui/tokens.css` declares values on `:root` and styles
nothing. One stylesheet per component, beside it, consuming tokens only. No raw hex anywhere.
No raw px for anything the token table covers. The two sanctioned raw lengths in this phase are
both single-layout geometry, exactly as Phase 1 treated the 160px board label column: the board
label column (now `176px`) and the pane split ratio (`60fr 40fr`).

### Size tokens

Phase 1's eight size tokens are unchanged in name and in default value. One is added.

| Token | Value | Notes |
|-------|-------|-------|
| `--sprite-lg` | 96px (density-scoped, see below) | Pool card sprite. Measured native size of all 311 committed PNGs. |
| `--sprite-sm` | 48px | Board chip sprite. Exact 2:1 integer downscale. |
| `--cell-min` | 128px (density-scoped) | Pool grid `minmax()` floor. **Default changes from 112px to 128px** because standard density now carries a pill row and a stat line. |
| `--cell-h` | 188px (density-scoped) | Pool cell height. **Default changes from 144px to 188px**, and its CSS role changes from `height` to `min-height` — see §Density Contract. |
| `--target-min` | 44px | Minimum interactive target, both axes. Also the width of a collapsed pane's restore strip. |
| `--radius` | 8px | Unchanged. One radius, no variants. Type pills use it too. |
| `--border-w` | 2px | Unchanged. Also the selected-state border on a type filter pill. |
| `--hairline-w` | 1px | Unchanged. |
| **`--pill-h`** | **24px** | **NEW.** Type-pill height on a pool card. 14px × 1.4 = 19.6px of text plus 2px above and below. Filter pills do **not** use this — they are controls and take `--target-min`. |

**Only sanctioned sprite sizes are 96px and 48px.** Both derive from the 2026-08-04
measurement (96×96, 311 files, zero outliers) and 48px is its exact 2:1 integer downscale.
No density, no pane state, and no screen may render a sprite at any other size: every other
value is a non-integer downscale of pixel art. This is why minimal density drops to 48px
rather than to an intermediate 72px.

## Density Contract

Three densities (DRFT-06). Selected by `data-density` on the pool pane root, default
`standard` (D-31). The value persists in browser storage, never in the tournament document
(D-20).

### Tokens per level

| Token | `minimal` | `standard` (default) | `full` |
|-------|-----------|---------------------|--------|
| `--sprite-lg` | `48px` | `96px` | `96px` |
| `--cell-min` | `96px` | `128px` | `208px` |
| `--cell-h` | `88px` | `188px` | `236px` |

Every value is a multiple of 4. Nothing else is redeclared — not a colour, not a font, not a
spacing token.

### Content per level (D-25)

Cumulative. Each level renders everything the level above it renders, plus its own additions.

| Level | Sprite | Name | Type pills | Stat total | Six stats |
|-------|--------|------|-----------|-----------|-----------|
| `minimal` | 48px | yes | — | — | — |
| `standard` | 96px | yes | 3-letter code (D-28) | `Total {n}` | — |
| `full` | 96px | yes | full type name (D-28) | `Total {n}` | HP/Atk/Def/SpA/SpD/Spe, two rows of three (D-30) |

`full` keeps the stat total because D-25's notation is cumulative ("Full = **+** all six base
stats"). The total is the figure a drafter compares at a glance; the six are what they check
once the total has caught their eye.

### Cell height arithmetic — how each `--cell-h` was derived

Stated so the executor can verify a rendered cell rather than trust a number.

```
minimal   8 pad + 48 sprite + 4 + 20 name                                    + 8 pad =  88
standard  8 pad + 96 sprite + 4 + 20 name + 4 + 24 pills + 4 + 20 total      + 8 pad = 188
full      8 pad + 96 sprite + 4 + 20 name + 4 + 24 pills + 4 + 20 total
                                                        + 4 + 44 stat grid  + 8 pad = 236
```

`20` is `--text-label` at 14px × 1.4 line-height, rounded up from 19.6. `44` is two 20px stat
rows with a `--space-1` gap. `24` is `--pill-h`.

**`MonCard.css` must change `height: var(--cell-h)` to `min-height: var(--cell-h)`.** A fixed
height clips a pill row that wraps, and at full density a two-type species with two long names
can wrap. The grid's own row sizing already equalises every cell in a row, so nothing shifts.

### Columns per level at the split pool pane

The pool pane is 1109px at a 1920px viewport (derivation in §Two-Pane Geometry). With
`gap: var(--space-2)`:

| Level | `--cell-min` | Columns | 48-Pokémon pool (8 players, Exact) | 235-cell ban grid |
|-------|-------------|---------|-----------------------------------|-------------------|
| `minimal` | 96px | 10 | 5 rows, 480px — no scroll | 24 rows |
| `standard` | 128px | 8 | 6 rows, 1168px — short scroll | 30 rows |
| `full` | 208px | 5 | 10 rows, 2440px — scrolls | 47 rows |

`auto-fill` (not `auto-fit`) is retained from Phase 1: a heavily filtered pool leaves its
survivors at normal size instead of stretching two of them across the row.

**Minimal density's known trade-off, accepted:** at 96px the name has 80px of content width,
roughly 10 characters at 14px semibold before the ellipsis engages. `Tauros-Paldea-Combat`
(20 characters, the roster's longest) truncates hard. The full name stays in the existing
`title` attribute, the sprite is the primary identifier at this density, and search (DRFT-08)
is how a specific species is found here. Minimal exists to cut scroll height 2.5× — 24 rows
against standard's 30 rows at almost twice the row height — and that is the win it is chosen
for.

**Why the ink is two tokens and not `var(--color-bg)` / `var(--color-text)`.** Phase 1 set the
precedent: `--color-accent-ink` and `--color-danger-ink` are both `#0f1216` and both exist
separately from `--color-bg`. Ink is a role, not a coincidence of value. Aliasing would make a
future change to the page background silently change pill text.

**Why five fills sit below 3:1 against the surface, and why that is not a violation.** Dark,
Dragon, Fighting, Ghost and Poison measure 2.48–2.97:1 fill-against-surface. WCAG 1.4.11
requires 3:1 for *visual information required to identify a component or its state*. On a pool
card the pill is a **text label**, and its text clears 4.5:1 (SC 1.4.3, which is the criterion
that applies). On a filter control the pill is a button identified by its text label, and its
pressed state is carried by a `--border-w` border in `--color-text` (14.06:1 on surface), not
by the fill. In neither case is the fill boundary required information. Darkening or lightening
those five hues was rejected by D-27 — Ice, Fairy, Electric and Ground stop looking like
themselves — and the recognition is the entire reason colour was chosen.

**The three-letter codes are a lookup map, not a string slice.** All eighteen happen to be the
first three characters uppercased, and all eighteen are distinct (`GRA`/`GRO`, `DRA`/`DAR`,
`FIR`/`FIG` are the near misses). It is still written as an explicit 18-entry map in one
module, with a test asserting 18 entries and 18 distinct codes, so a nineteenth type cannot
silently collide. `CLAUDE.md`'s rule against deriving structure from a name string points the
same way even though a type name is a closed set and a species name is not.

### Accent reserved for

Exactly three things, unchanged from Phase 1. What changes is which elements fill each slot.

1. **The on-the-clock indicator** — the turn banner's `--space-1` left rule and the active
   player's name inside it, plus the `--border-w` border and `--color-accent-soft` tint on the
   single `board__cell--next`. Unchanged mechanism, now one cell out of up to 48.
2. **The primary action of the current screen** — accent fill, `--color-accent-ink` text, one
   per screen. This phase's primary actions: `New tournament` (landing), `Start draft`
   (config), `Copy team paste` (completed, repeats per player — same action, not a second
   one), `Download tournament JSON` (checkpoint panel), and the confirming button of each
   non-destructive confirm dialog. **The draft screen still has no accent-filled button at
   all.** Picking is the action and the pool cells are the target.
3. **The keyboard focus ring** — `outline: 3px solid var(--focus-ring); outline-offset: 2px`
   on `:focus-visible`, applied once globally in `app.css`.

A selected type filter pill is **not** accent. It carries `--border-w solid var(--color-text)`
plus `aria-pressed="true"`. A selected segmented-control option is **not** accent either — see
§Segmented Control.

### Destructive reserved for

Three things in Phase 2, up from two. The addition is a genuine data-loss action, not an
emphasis.

1. **The storage-unavailable blocking screen** (PERS-02 / Phase 1 D-13) — now fired from the
   landing screen (D-01). Heading colour and the `--space-1` left rule.
2. **The import-overwrite confirm button** (PERS-05) — already shipped, unchanged.
3. **The abandon-draft confirm button** (D-36) — danger fill, `--color-danger-ink` text.
   Abandoning discards every pick with no way back, which is the same category as replacing a
   draft by import.

**The four config-time confirms and the undo confirm are not danger-toned.** Re-rolling the
pool, re-randomizing the order, removing a player and clearing the banlist all happen before a
draft exists — nothing is lost that was ever played. Undo must read as routine and reversible
because D-08's no-confirm pick depends on it. All five use `tone="default"`, accent fill on the
confirming button, secondary on the safe one.

**A blocked `Start draft` is not danger-coloured.** Nothing is lost; it is a not-yet state. The
reason sentence renders in `--color-text`.

## Two-Pane Geometry

The single number that shaped D-19, D-21 and D-28 is the board pane's per-round cell width.
This section derives it, and every responsive consequence, from measurable values.

### The shell changes (amends Phase 1 §Layout shell)

Phase 1 has one shell: `.app-shell`, `max-width: 1600px`, centred, `--space-4` padding. Phase 2
needs two.

| Class | Used by | Geometry |
|-------|---------|----------|
| `.app-shell` | landing, config, storage-blocked | `max-width: 1200px`, centred, `--space-4` padding. **Cap tightened from 1600px** — a config form and a landing screen do not want a 1600px measure. |
| `.draft-shell` | draft screen, completed-draft screen | **Full-bleed** (no `max-width`), `--space-4` padding, `height: 100dvh`, `display: flex; flex-direction: column`. |

`.draft-shell` drops the 1600px cap deliberately. Phase 1 capped it "so a wide monitor does not
stretch the pool grid into an unreadable band" — with a 60/40 split the pool no longer stretches
to the viewport, and the board needs every pixel it can get. At the 1600px cap the board pane
would be 611px wide and the per-round cell 64px; full-bleed at 1920px it is 739px and 86px.

**Independent pane scrolling, without hardcoding the sticky head's height:**

```
.draft-shell           display: flex; flex-direction: column; height: 100dvh
  .sticky-head         flex: none                (TopBar + TurnBanner, Phase 1 mechanism)
  .draft-panes         flex: 1; min-height: 0; display: grid; gap: var(--space-4)
    .pane              height: 100%; overflow-y: auto; min-width: 0
```

`min-height: 0` on the flex child is load-bearing — without it a flex item refuses to shrink
below its content and both panes grow the page instead of scrolling. `min-width: 0` on each pane
is what lets the board's name ellipsis and the pool's grid reflow engage inside a grid track.
`100dvh` rather than `100vh` so mobile browser chrome cannot clip the bottom pane. No
`top: 76px` offset anywhere — the height is never named, so it cannot go stale when the top bar
gains a button.

### Pane states

```css
.draft-panes                          { grid-template-columns: 60fr 40fr; }
.draft-panes[data-pane="pool"]        { grid-template-columns: 1fr var(--target-min); }
.draft-panes[data-pane="board"]       { grid-template-columns: var(--target-min) 1fr; }
```

`60fr 40fr` is a raw ratio, sanctioned as this one layout's geometry (same standing as the board
label column). The collapsed pane becomes a `--target-min`-wide strip holding one button with
`writing-mode: vertical-rl`, so the restore control meets the 44px minimum in both axes without
a horizontal label.

`data-pane` persists in browser storage with `data-density`, never in the tournament document
(D-20). No draggable splitter: pointer-drag needs a keyboard equivalent, is awkward on touch,
and a free ratio has to be persisted anyway (D-19).

```
÷ 6 rounds                                                86  px per round cell
```

**86px is the number three decisions rest on.**

- A sprite-only `MonChip` needs `--sprite-sm` (48) + `--space-1` padding × 2 (8) = **56px**.
  86 > 56 with 30px of slack → **D-21's sprite-only board in split view fits.**
- A chip with a name at that width would leave 22px for the name. It does not fit → **D-21's
  names-only-when-expanded is forced by arithmetic, not preference.**
- Two full-name type pills would need ~144px in a 128px pool cell → **D-28's three-letter codes
  at standard density are forced the same way.**

### Derived widths at 1920 × 1080, `board-full`

```
1872 − 176 label − 48 gaps = 1648 ÷ 6 = 275 px per round cell
```

A named chip needs 8 (padding) + 48 (sprite) + 4 (gap) + name. 215px of name at
`--text-label` is roughly 27 characters; the roster's longest name is 20
(`Tauros-Paldea-Combat`). **No board name ellipsises in `board-full`** — which is precisely the
job D-21 gives the expand control, and it is now a checkable assertion.

### Board height at 8 players

```
.board__cell min-height  = --sprite-sm + --space-3 = 64
8 rows × 64 + 7 gaps × 8                                 =  568
+ round header row (20 + 8 gap) + pane header (44 + 16)   ≈  656
```

Available height at 1080p: `1080 − 24 shell padding − ~181 sticky head − 24 bottom ≈ 851px`.
**656 < 851 — the full 8-player board fits in the split board pane with no internal vertical
scroll at 1080p.** This is the measurement that justifies D-18's panes over the rejected
stacked sticky board, which 02-CONTEXT records as consuming ~590px of a 1080p screen at 8
players.

The board label column widens from Phase 1's 160px to **176px**, buying roughly two more
characters of player name at `--text-heading`, at a cost of 2px per round cell (88 → 86). The
`overflow-x: auto` wrapper and the `position: sticky; left: 0` label column from Phase 1's
BoardGrid.css are retained unchanged and now carry the narrow-viewport case as well.

### Responsive behaviour

| Width | Layout |
|-------|--------|
| ≥ 1280px | Two panes side by side. States as above. |
| 768–1279px | **Panes stack vertically, board first.** `.draft-panes { grid-template-columns: 1fr; grid-template-rows: minmax(0, 40vh) minmax(0, 1fr); }`. Both rows keep `overflow-y: auto`. Board first because criterion 5 outranks pool convenience. |
| < 768px | Same stack. The board's own `overflow-x: auto` plus the sticky label column carries it. Not a target platform — this is a shared screen — but it must not break. |

Stacking below 1280px is not a reversal of D-18. D-18 rejected the stacked sticky board *as the
primary desktop design*; below 1280px side-by-side is not available at all, so stacking is the
fallback, not the choice.

The three pane states survive stacking with the same meanings: `split` shows both rows,
`board-full` collapses the pool row to a `--target-min`-tall restore strip, `pool-full`
(config/completed only) collapses the board row the same way. Same persisted value, same
control, no second code path.

**200% browser zoom on a 1920px screen yields a 960px CSS viewport, which stacks.** Phase 1's
rule — layout survives 200% zoom without page-level horizontal scroll — is therefore satisfied
by the same media query, not by a separate accommodation.

### 2. Config screen (D-02)

**One scrolling form.** Not a wizard, not progressive reveal. Player count invalidates pool
size, bans and feasibility simultaneously, and backtracking is the normal case.

`.app-shell` (1200px cap). Each group is a `<fieldset>` with a `<legend>` at `--text-heading`,
`--color-surface` fill, `--space-3` padding, `--radius`, `--space-5` between groups. Text and
numeric inputs cap at `60ch` (the project's existing measure); the ban grid uses the full
1200px.

**Group order, and why:**

| # | `<legend>` | Contents | Why here |
|---|-----------|----------|----------|
| 1 | `Players` | One row per player: name `<input>` + `Remove {name}`. `Add a player`. Then `Randomize order` and the resulting numbered `<ol>`. | Player count invalidates everything below it |
| 2 | `Tournament` | `Format label` text input (prefilled `Champions {regulation}`). `Tournament depth` segmented control. | Independent of the arithmetic |
| 3 | `Mega rules` | `Megas required per team` numeric input, 0–6, default 0. Then one row per dual-Mega species with an X / Y / Either segmented control, default `Either`. | Constrains the draw, feeds feasibility |
| 4 | `Bans` | `Ban mode` segmented control. `TypeaheadField` + `BanChipList` + `Clear the banlist`. Then the ban-mode `PoolGrid` in a capped scroll region. | Constrains the draw |
| 5 | `Pool` | `Pool size` segmented control (Exact / ×1.5 / ×2, default Exact). `Pool size override` numeric input. The draw readout. `Re-roll pool`. | **Last, so its readout reflects every group above it** |
| — | pinned | `FeasibilityBar` | Always visible |

- **Dual-Mega rows are derived from `megaFormes.length > 1`, never a hardcoded list** (D-03).
  The roster currently yields exactly two — Charizard and Raichu — so the group renders two
  rows, and a regulation that adds a third just appears.
- **Tournament depth: all three options enabled and selectable**, stored in config, with a
  `--text-label` `--color-text-muted` note under the group:
  `Depth is recorded now. Round robin and brackets arrive with the tournament screens.` This
  satisfies criterion 1 literally ("enters … a tournament depth") without claiming a screen
  that does not exist. Deliberately *unlike* ban mode, where two options are disabled: a
  disabled depth would make criterion 1 unmeetable.
- **Ban mode: `Host banlist` enabled; `Blind` and `Snake` rendered, `disabled`,
  `aria-disabled="true"`, each with the visible suffix `— Not yet available`** (D-12). The
  control's shape is set now so Phase 4 enables two options rather than redesigning it.
- **Pool size override is a free numeric input with no clamping** (D-06). Anything
  unsatisfiable fails the feasibility gate with the arithmetic stated. One authority on what is
  satisfiable, not two.
- **The draw readout** at `--text-body`:
  `Pool: {n} Pokémon — {m} Mega-capable`. It is a pure derivation of (config, seed), so it is
  stable unless the config or the seed changes. `Re-roll pool` changes the seed, and the seed is
  captured at the impure edge, never inside a reducer.
- **The ban grid is a capped scroll region:** `max-height: 60vh; overflow-y: auto`,
  `--hairline-w solid var(--color-hairline)` border, `--radius`. 235 cells at standard density
  is 30 rows, and a form should not be 5900px tall.
- **The ban grid reuses `PoolGrid` whole** — its header, its filter bar and its density control
  (D-10: "search and the type filters work in ban mode for free"). The density value is the
  same persisted preference the draft screen uses. One preference, two places, one component.

### 3. Ban mode on `PoolGrid` (D-10, D-11, BAN-02)

- Every one of the 235 draftable entries renders. Clicking a cell toggles a ban.
- Each cell is the same `<button type="button">` with `aria-pressed={banned}`.
- **Banned treatment:** `opacity: 0.45` **and** `text-decoration: line-through` on the name.
  Two signals, neither of them hue. `opacity` alone would be indistinguishable from the
  disabled convention.
- D-13's "not dimmed, not struck" applies to the **draft pool**, where a banned species is
  absent from the DOM entirely. The config ban grid is the opposite surface: it must show what
  you are excluding.
- Count line becomes `{n} of 235 banned`.
- **Species bans only** (D-11). One flat list of banned species ids. The host cannot ban a Mega
  forme while keeping the species draftable. Consequence, accepted knowingly: Phase 3 must add
  a Mega-ban list to a config shape that has already shipped.

### 4. Typeahead + chip list (D-10)

**`TypeaheadField`** — the host who already knows the name.

- `<input role="combobox" aria-expanded aria-controls aria-autocomplete="list">` with a
  visually-hidden `<label>`: `Ban a Pokémon by name`. `min-height: var(--target-min)`.
- Results are a `<ul role="listbox">` of `role="option"` items, `aria-activedescendant` on the

- Matching uses the **same normalized substring predicate as DRFT-08** (D-32) — one predicate,
  one module, one test suite. Not a second matcher that can drift.

**`BanChipList`** — the chips.

- Each chip is itself the remove control: `<button type="button">` containing the name at
  `--text-label` plus an `aria-hidden` `×`, with
  `aria-label="Remove {name} from the banlist"`. The accessible name **contains** the visible
  text, satisfying SC 2.5.3 Label in Name.
- `min-height: var(--target-min)`, `--color-surface-raised` fill,
  `--hairline-w solid var(--color-border-strong)`, `--radius`, `--space-2` gap between chips,

- `Clear the banlist` sits after the list and confirms (D-36). Not rendered when the list is

### 5. Feasibility bar (RULE-07, D-14…D-16)

`position: sticky; bottom: 0`, `--color-bg` backdrop, `--hairline-w` top border in
`--color-hairline`, `--space-3` padding. `Start draft` on the left, the reason to its right.

- **`Start draft` uses `aria-disabled="true"` and stays focusable.** It does **not** take the
  native `disabled` attribute. A natively disabled button is not focusable, so a keyboard user
  could never reach the explanation — and the explanation is the whole point of RULE-07. The
  click handler returns early. `aria-describedby` points at the reason element. Visually:
  `opacity: 0.45; cursor: not-allowed`, same as Phase 1's undo.
  This is a deliberate divergence from Phase 1's undo pattern, which uses native `disabled`
  correctly: undo's disabled state needs no explanation, and Start's does.
- The reason element is `role="status"`, so a change is announced without a manual `announce`
  call and without competing with the global live region.
- **Recomputes live on every change** (D-16). Pure functions over a few hundred ids. No
  debounce, no `Check` button.
- **One reason at a time**, in a fixed precedence order, because the conditions interact and
  fixing the first usually changes the rest — which is D-15's whole point. When more than one
  blocker holds, a second `--text-label` `--color-text-muted` line reads
  `{n} other problems also block the start.`

**Precedence order (declared, not emergent):**

1. Fewer than two players
2. A player name is empty
3. Two players share a name
4. Pool larger than the post-ban legal count
5. Pool smaller than `players × rounds`
6. More Megas required than exist post-ban
7. *(warning, non-blocking)* Pool exactly `players × rounds`

Blocking severity disables Start. Warning severity does not (D-14). The non-colour distinction
between the two is exactly that, plus the `Warning — ` text prefix. One severity is
insufficient specifically because Exact is now the default pool preset and it passes every
blocking check.

### 6. Draft screen — pool pane

Header, two rows:

- **Row 1:** `Pool` at `--text-heading`; `{n} available` at `--text-label` in
  `--color-text-muted`; `Display density` segmented control; the expand button
  (**not rendered while a draft is in progress** — see §A tension in the locked set).
- **Row 2:** the `FilterBar`.

Grid and cells are Phase 1's contract with the density additions. Retained from Phase 1
verbatim: `auto-fill` not `auto-fit`; explicit `width`/`height` on every `<img>` from
`spriteMeta`, never a literal; no `loading="lazy"` because D-16 precaches every sprite;
`spriteMissing` chooses the committed placeholder and never fires a request the build knows
404s; a picked species is **removed from the DOM immediately**, not greyed.

**Performance:** the live draft pool is 48–96 entries (8 players × 6 rounds at Exact, doubled
at ×2), not 235. The 235-cell case is the config ban grid, which is a capped scroll region. Ship
without virtualization. The one sanctioned escape hatch remains exactly
`content-visibility: auto; contain-intrinsic-size: var(--cell-min) var(--cell-h);` on
`.mon-card`. Nothing else.

### 7. Draft screen — board pane

Header: `Draft board` at `--text-heading` plus the expand button. Grid is Phase 1's, with the
176px label column and a derived round count.

- **Split view: chips are sprite-only** (D-21). `MonChip` receives `showName={false}`.
- **`board-full`: names render** at `--text-label`. This is what gives the expand control a job
  beyond preference — it is the answer to "what is that one".
- **Known risk, accepted (D-21):** Charizard and Charizard-Mega-X share a base sprite in this
  pipeline, and the Rotom appliances read alike at 48px. A split-view board can be genuinely
  ambiguous. Expanding resolves it; that is the design, not a workaround.
- **Board chips stay monochrome** (D-29). No type colour on the board. Forty-eight saturated
  pills would compete with the accent-coloured next-slot highlight, which is the one signal
  that must never be missed.
- **Board cells are not interactive**, in this phase or any planned one. Undo is a top-bar
  button. Forty-eight tiny retract buttons on a shared screen is a misclick surface, and the
  one thing a no-confirm pick cannot afford is a second easy way to lose one.
- **No separate "your team" panel** (Phase 1 D-06). A board row *is* a `TeamStrip`; DRFT-10 and
  DRFT-11 are one surface.

### 8. Filter bar (DRFT-08, DRFT-09, D-32…D-35)

Left to right, `flex-wrap: wrap`, `--space-2` gap.

1. **Search** — `<input type="search">`, visually-hidden `<label>`
   `Search the pool by name`, `placeholder="Name"`, `min-height: var(--target-min)`.
   Live normalized substring match (D-32): lowercase and strip non-alphanumerics from both
   query and name — Showdown's `toID` normalization — then substring. `mr rime`, `Mr. Rime` and
   `mrrime` all hit; `rotom` returns every appliance; `aqua` finds `Tauros-Paldea-Aqua`.
   **No name splitting anywhere.** Prefix matching is rejected precisely because `wash` and
   `aqua` are how people refer to those species.
2. **Type toolbar** — `<div role="toolbar" aria-label="Filter by type">` holding 18
   `TypePill` toggle buttons, `aria-pressed`, roving tabindex, arrow keys, Home/End.
   One tab stop. Each pill `min-height: var(--target-min); min-width: var(--target-min)`.
   Label form follows the pool density: full names at `full`, three-letter codes otherwise —
   so the filter and the thing it filters keep speaking the same language (D-29). At `full` the
   toolbar wraps to two rows; at 1109px the three-letter row fits on one.
3. **`Match all selected types`** — a checkbox with a visible label. OR is the default; this is
   the AND toggle (D-33). `aria-disabled="true"` and `opacity: 0.45` when fewer than two types
   are selected, but **always rendered** — a control that appears and disappears is worse on a
   shared screen than one that is predictably inert.
   D-33 calls this "match both". The visible label says `Match all selected types` because
   "both" is wrong at three selections. Wording refinement, not a decision change.
4. **`Mega capability`** segmented control — All / Mega-capable / Non-Mega, default All (D-34).
   Non-Mega is a genuine query for a host who set a Mega requirement and wants to see what is
   left for the ordinary rounds. Phase 3 adds the round's own restriction as a separate
   composed constraint without reshaping this control.
5. **`Clear filters`** — secondary. Not rendered when nothing is active.

**Everything here clears the moment a pick commits** (D-35). Search text, every type pill, the
match-all toggle, the Mega control. On one shared screen the alternative is the real hazard:
player 5 picks from player 4's leftover "Fire only" filter and never notices the other 30
options. Filter state is ephemeral UI state and never enters the tournament document.

**Focus after a pick.** The picked cell's DOM node is removed. Focus must be moved to the cell
that now occupies that grid position, or to the last cell when the pool shrank at the end.
Without this, a keyboard pick drops focus to `<body>` and the next arrow key does nothing. This
is a contract, not a nicety.

### 9. Type pill anatomy

| | `standard` (and `minimal` filter) | `full` |
|-|----------------------------------|--------|
| Text | 3-letter uppercase code, `--text-label` | Full type name, `--text-label` |
| Height | `--pill-h` (24px) on a card; `--target-min` (44px) as a filter | same |
| Padding-x | `--space-1` | `--space-1` |
| Radius | `--radius` | `--radius` |
| Fill | `var(--type-{name})` | same |
| Ink | `var(--type-ink-dark)` or `var(--type-ink-light)` per the token table | same |
| Accessible name | `aria-label="{Full type name}"` on the card pill when the code is shown; the visible name when it is not | visible text suffices |

Two 3-letter pills at standard density: 35px each plus a `--space-1` gap = 74px, inside 112px of
cell content width. Two full-name pills at full density: ~70px each = 144px, inside 192px. Both
fit. `Electric` + `Flying` at 14px is roughly 130px of text before padding, which is why they
cannot both fit a 112px cell and why D-28 exists.

The card pill row is `display: flex; gap: var(--space-1); flex-wrap: wrap; justify-content: center`.
Wrapping is why `--cell-h` became a `min-height`.

### 10. Stat block anatomy (D-30)

- **Standard:** one line, `Total {n}`. `Total` in `--color-text-muted`, the number in
  `--color-text`, both `--text-label`. The total is the figure a drafter compares at a glance,
  and Champions' stat-point budget makes it meaningful rather than arbitrary.
- **Full:** the total line, then a `display: grid; grid-template-columns: repeat(3, 1fr);
  gap: var(--space-1)` block of six cells, two rows of three, in Showdown's canonical order:
  `HP` `Atk` `Def` / `SpA` `SpD` `Spe`. Each cell is `{label} {value}`, label in
  `--color-text-muted`, value in `--color-text`.
- Measured bounds from `public/data/roster.mb.json` on 2026-08-06: stat totals run 288–600 and
  no single stat exceeds 200, so every figure is at most three digits. `SpA 150` at 14px
  semibold is ~54px inside a 61px grid column at `--cell-min: 208px`. It fits without wrapping.
- The stat grid is a `<dl>` with `<dt>`/`<dd>` pairs, not a table and not bare spans, so the
  label/value relationship survives without a screen reader having to infer it from
  proximity.

### 11. Confirmation dialogs (DRFT-13, D-36…D-39)

**Six confirms. All six reuse `Dialog.tsx` through one `ConfirmDialog`** (D-38). Focus trapping,
Escape handling and return-focus are already solved there; a second pattern is where
accessibility bugs come from. `ImportConfirmDialog` is refactored onto `ConfirmDialog` so the
count is one pattern and six sets of copy, not six components.

Every one: consequence sentence stating what is lost **in numbers**, then two buttons that each
name a verb and its object (D-39). Destructive/confirming button first, safe button second — so
the safe one is the last thing focus reaches and the last thing read. **Escape maps to the safe
button** in all six. Nothing is labelled `OK`, `Submit`, `Yes` or `Cancel` alone.

**Picking never confirms.** Phase 1 D-08 stands, and D-36 preserves it explicitly.

| Action | Tone | Confirm button | Safe button |
|--------|------|---------------|-------------|
| Abandon draft / start a new tournament | `danger` | `Abandon draft` | `Keep drafting` |
| Import JSON over a live draft | `danger` | `Replace draft` | `Keep current draft` |
| Re-roll pool | `default` | `Draw a new pool` | `Keep this pool` |
| Re-randomize starting order | `default` | `Roll a new order` | `Keep this order` |
| Remove a player | `default` | `Remove {name}` | `Keep {name}` |
| Clear the banlist | `default` | `Clear the banlist` | `Keep the bans` |
| Undo across a round boundary | `default` | `Undo the pick` | `Keep the pick` |

The `default`-tone dialogs put accent fill on the confirming button (accent reserved use 2 — the
primary action of the current screen, and a modal is the current screen). The `danger`-tone
dialogs put danger fill there instead and leave the safe button secondary.

**The `Filters cleared.` suffix is conditional on purpose.** Clearing is silent visually — the
pool repopulating is the feedback — but a screen-reader user needs to know the set changed.
Appending it only when at least one filter was active keeps the common announcement short.

**`LiveRegion`'s byte-identical limitation, and why this phase does not hit it.** Assistive
technology announces a *change* to the region, so repeating an identical string is silent the
second time; `LiveRegion.tsx` records this and records that Preact batches a clear-then-set into
one render so the naive fix does not work. Consecutive turn announcements always differ, because
either the round or the player name changes. The one way two could be identical is two players
sharing a name — **which is a blocking feasibility error** (precedence 3). The duplicate-name
blocker therefore protects the live region as a side effect. If that blocker is ever relaxed,
`LiveRegion` needs a two-frame clear first.

**Copy rules for this phase** (unchanged from Phase 1, restated because they are load-bearing):

- Second person, present tense, no exclamation marks, no emoji.
- Errors state the problem *and* the next action. Never a bare "Something went wrong".
- Never blame the user. The feasibility sentences blame the arithmetic, which is accurate.
- Numbers, not adjectives. `48 Pokémon`, not `enough Pokémon`.

## DRFT-14 as a Checkable Assertion

D-23 requires DRFT-14 be verified two ways: a stated numeric target that makes it reviewable and
regressable, **and** a physical check, which is what the requirement actually means. Neither
alone is sufficient. ROADMAP Notes call DRFT-14 "an acceptance criterion for the whole shared
screen, not a polish item".

**Assertions (any one failing fails the phase):**

| # | Assertion | Measured where |
|---|-----------|---------------|

## Interaction & Accessibility Baseline

Phase 1's table applies in full and is not restated. These are the additions this phase forces.

| Rule | Requirement |
|------|-------------|
| **`MonChip` alt text** | **Not optional, and the single most breakable contract in this phase.** `MonChip` sets `alt=""` *because* the adjacent name text is the accessible name — its own doc comment says so. Removing that text in split view leaves the cell with **no accessible name at all**. Therefore: `alt={entry.name}` whenever `showName` is false, `alt=""` whenever it is true. The two are one decision and must be written in one expression, never as two independent props a caller can desynchronise. A test asserts both branches. |
| **Pool grid keyboard navigation** | One tab stop. Roving tabindex: exactly one cell carries `tabindex="0"`, the rest `tabindex="-1"`. Arrow keys move focus, Home/End jump to first/last, Enter and Space pick (native button behaviour). Column count for Up/Down is read from the rendered grid, not assumed — `auto-fill` means the app does not know it statically. No `role="grid"`, no `role="row"`, no `role="gridcell"`: the DOM has no rows because the grid is implicit, and inventing row elements would break `auto-fill`. The cells stay real `<button>`s. |
| **Focus after a pick** | Moved to the cell that now occupies the removed cell's grid position, or to the last cell when the pool shrank at the end. Never left on a detached node, never dropped to `<body>`. |
| **Type toolbar** | `role="toolbar" aria-label="Filter by type"`, roving tabindex over 18 `aria-pressed` buttons, arrow keys, Home/End. One tab stop. Shares `useRovingTabindex` with the pool grid. |
| **Segmented control** | `<fieldset>` + `<legend>` + visually-hidden `<input type="radio">` + styled `<label>`. One tab stop, arrow keys and grouping native. Focus ring via `input:focus-visible + label`. Never a set of buttons with `aria-checked` hand-rolled. Six instances: density, Mega capability, pool size, ban mode, tournament depth, and one per dual-Mega row. |
| **Typeahead** | `role="combobox"` + `aria-expanded` + `aria-controls` + `aria-autocomplete="list"` + `aria-activedescendant`, over a `role="listbox"` of `role="option"`. Escape closes the list without clearing the input. |
| **Focus order across two panes** | DOM order equals visual order: sticky head → pool pane → board pane. No CSS reordering, so WCAG 1.3.2 and 2.4.3 hold trivially. The sequence is short because the pool grid and the type toolbar are one tab stop each: TopBar controls → pool header controls → filter bar → pool grid → board pane expand. |
| **`Start draft` when blocked** | `aria-disabled="true"`, **focusable**, `aria-describedby` → the reason. Not native `disabled`. Rationale in §Feasibility bar. |
| **Live regions** | Exactly **one global** `<div role="status" aria-live="polite">` at app root, visually hidden, for transient announcements with no on-screen home. A surface may additionally carry its own `role="status"` for a message that lives on that surface and stays on screen — the existing `TopBar` import error already does this, and the feasibility reason does it now. Nothing uses `aria-live="assertive"`. This restates Phase 1's "exactly one" rule to match what Phase 1 actually shipped. |
| **`announce` in tests** | `announce` is a module-level signal that outlives any render. A test touching the live region resets it in `beforeEach`. Existing convention, restated because this phase adds nine announcements. |
| **Bans disclosure** | Native `<details>`/`<summary>`, `min-height: var(--target-min)` on the summary. Not a hand-rolled disclosure — the native element carries keyboard operation and expanded state for free. |
| **Target size** | Every interactive element ≥ `--target-min` (44px) in both axes: pool card (96 × 88 minimum), filter type pill (44 × 44 minimum — this is why filter pills do not use `--pill-h`), ban chip, segmented-control label, expand button (44 × 44), restore strip (44 wide × pane tall), `<summary>`, every text and numeric input. Board chips are not interactive and are exempt. |
| **Motion budget** | Unchanged. Colour and border transitions only, ≤ 120ms. **A pane state change is not animated** — no width transition, no slide. Animating a grid-template change is expensive, and the `prefers-reduced-motion` block already in `app.css` would have to special-case it. |
| **Zoom** | Unchanged, and now satisfied by the same media query that handles tablets: 200% on 1920px is a 960px CSS viewport, which stacks the panes. |
| **Images** | Unchanged. Explicit `width`/`height` from `spriteMeta`, never a literal. `alt` per the `MonChip` rule above and Phase 1's `MonCard` rule (empty, because the name is beside it — and `MonCard` always renders its name, at every density, so its `alt=""` stays correct). |

### View preferences in storage (D-20)

- One key, `champions-drafter:view`, matching the existing `champions-drafter:tournament`
  convention in `src/adapters/persistence.ts`.
- Value: `{ "density": "standard", "pane": "split" }`.
- Owned by `src/adapters/`, never by `src/core/` and never by a component.
- **Absent, unparseable, or carrying an unknown value → fall back to the defaults
  (`standard`, `split`) silently.** A view preference must never block a render and must never
  produce a warning. It is not a fact about the tournament.
- **Never written into the tournament document.** It must not travel through JSON export or a
  future sync layer. ARCHITECTURE sync rule 3 (nothing derived is stored) points the same way.

### Pure-core boundary — still a UI rule

No component owns a game rule. Whose turn it is, the current round, the remaining pool, the
search predicate, every filter predicate, the pool draw, and the feasibility gate with all seven
of its reasons are **selectors and pure functions in `src/core/`**. `npm run check:pure` fails the
build on any DOM, clock, randomness, network, storage or `preact` import under `src/core/`.
`npm run check:nohtml` forbids `innerHTML` and `dangerouslySetInnerHTML` anywhere under `src/`.

Two things in this phase are UI-layer by necessity and are named so nobody has to guess: the
300ms debounce on the filter-result announcement (a timer, so it lives in the component), and
reading the rendered grid's column count for arrow-key navigation (a DOM measurement, so it
lives in the hook). Neither is a rule.

If a surface in this spec seems to need the UI to decide a rule, the selector is missing. Add the
selector.

## Deferred to Phase 3 by this contract

Recorded here so the Phase 3 planner does not discover it.

- **Mega-forme bans.** D-11 chose species-only bans. ROADMAP ordering constraint 4 and Phase 3
  success criterion 1 both assume this phase's banlist supplies the compiler's Mega-ban list.
  It does not. Phase 3 needs a `SCHEMA_VERSION` bump and a second banlist surface on top of the
  compiler work already planned there.
- **`megasRequiredPerTeam` is compiler input, not the compiler.** D-08's deliberate deviation
  from ROADMAP ordering constraint 6. Phase 2 uses the field for exactly two things: constraining
  the draw to contain at least `players × N` Mega-capable entries, and feeding the feasibility
  gate. It builds no Mega-only rounds and compiles no schedule. Phase 3's RULE-09 gate reads the
  recorded Mega-capable count (D-09) rather than recomputing, and must handle the case where the
  two disagree after a roster rotation.
- **Typed slot rendering.** `TeamStrip` slots stay untyped in Phase 2. Typed-slot team panels
  arrive with the compiler, when a slot genuinely carries information the board row does not.
- **The round's own pool restriction.** DRFT-09's "composing with the round's own restriction"
  is trivially satisfied here because no round restrictions exist. The Mega segmented control is
  shaped so Phase 3 adds that as a separate composed constraint without reshaping it.
