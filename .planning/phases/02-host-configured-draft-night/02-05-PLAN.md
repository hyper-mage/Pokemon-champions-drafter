## Phase Goal

Verbatim from `.planning/ROADMAP.md` §Phase 2. **Note: this Goal line is not written in
`As a … I want to … so that …` form**, and was not rewritten here — see 02-01-PLAN.md.

> A host sets up a real tournament for their group — names, format, pool size, banlist —
> and 4–8 friends draft through it on one shared screen with everything they need visible
> at once.

**Slice delivered by this plan:** the host chooses how big the pool is and how many Megas each
team must field, sees the resulting draw described in numbers, re-rolls it if the group dislikes
it, and starts a draft whose pool actually satisfies the Mega requirement. End to end: two
numeric fields and two segmented controls → `checkFeasibility` → `drawPool` → `pool/built`.

<objective>
Add the `Mega rules` and `Pool` config groups, and make the drawn pool obey both.

Purpose: this closes the highest-severity defect the research found. A free numeric pool-size
input yields `NaN` on empty, and `NaN > 235` and `NaN < 48` are BOTH false — so without an
explicit blocker the gate reports all-clear and Start enables on a broken configuration. It also
lands D-08's deliberate deviation from ROADMAP ordering constraint 6, which the planner is
required to record rather than absorb silently.

Output: `NumericField`, the two remaining arithmetic config groups, the draw readout, `Re-roll
pool`, and a pool draw constrained to `players × megasRequiredPerTeam` Mega-capable entries.
</objective>

<deviation_record>
**D-08 is a deliberate deviation from ROADMAP §"Ordering Constraints" 6**, which places
Mega-specific feasibility (RULE-09) wholly in Phase 3. This plan implements the deviation and
records it here rather than absorbing it silently, as 02-CONTEXT D-08 requires.

What crosses the line: a `megasRequiredPerTeam` config field, used for exactly two things —
constraining the draw to contain at least `players × N` Mega-capable entries, and feeding the
feasibility gate's `notEnoughMegas` blocker.

Why: a pool drawn in Phase 2 blind to the Mega requirement can be dead on arrival in Phase 3,
and the alternative — re-emitting `pool/built` during Phase 3 config — makes the host configure
a pool and then watch it change.

What does NOT cross the line: no Mega-only rounds, no compiled schedule, no round-level Mega
feasibility. Phase 3 still owns all of that and reads this field as compiler input, plus the
`megaCapableCount` this plan records into `pool/built` (D-09).

**Also recorded, per 02-CONTEXT D-11:** this phase's banlist is species-only, so it does NOT
supply the Mega-ban list that ROADMAP ordering constraint 4 and Phase 3 success criterion 1
both assume. Phase 3 must add Mega-forme bans to a config shape that has already shipped — a
schema bump plus a second banlist surface. Do not smuggle it into Phase 2.
</deviation_record>
