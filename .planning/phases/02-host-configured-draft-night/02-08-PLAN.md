## Phase Goal

Verbatim from `.planning/ROADMAP.md` §Phase 2. **Note: this Goal line is not written in
`As a … I want to … so that …` form**, and was not rewritten here — see 02-01-PLAN.md.

> A host sets up a real tournament for their group — names, format, pool size, banlist —
> and 4–8 friends draft through it on one shared screen with everything they need visible
> at once.

**Slice delivered by this plan:** the person on the clock finds the Pokémon they are thinking of.
They type `wash` and Rotom-Wash is the only cell left; they press `Water` and `Flying` and see
what is still available in those types; they switch the Mega control to `Non-Mega` and see what
is left for the ordinary rounds. End to end: `FilterBar` → `PoolFilters` → `compileFilters` →
`matchesFilters` → the cells `PoolGrid` renders → the count line → the live region.

This is ROADMAP Phase 2 Success Criterion 4, and it is the last unbuilt half of it. 02-03
delivered the reading half — sprite, typing, base stats, three densities. Nothing before this
plan builds a way to find anything.

<deviation_record>
Five places where this plan resolves, declines or extends something a source document or an
orchestrator instruction says. Each is recorded here rather than absorbed silently.

**1. Filter state lives in `PoolGrid`, not in `src/app.tsx`.** The obvious alternative is to lift
it beside `availableEntries` where `handlePick` already is. It is rejected for a concrete reason:
02-07 mounts a second `PoolGrid` inside the config screen's `Bans` group, and 02-UI-SPEC §2 says
that grid "reuses `PoolGrid` whole — its header, its filter bar and its density control". Lifting
the state would require `ConfigScreen` to hold a duplicate copy of it and a duplicate call to the
predicates — a second call site 02-UI-SPEC §4 forbids by name ("one predicate, one module, one
test suite. Not a second matcher that can drift"). `PoolGrid` already owns density in a
`useState` initializer (02-03), so self-owned ephemeral view state is an established shape in
this exact file rather than a new one. The only fact that has to leave the component is a single
boolean, and it leaves through the existing `onPick` call — see item 3.

**2. `src/core/search.ts` gains four ADDITIVE exports.** The orchestrator's decision 1 says
"consume them, you do not reimplement or extend them. If a predicate you need does not exist, say
so rather than duplicating logic in the UI." Saying so: **the composed predicate does not exist.**
This plan adds `PoolFilters`, `CompiledPoolFilters`, `NO_FILTERS`, `compileFilters`,
`matchesFilters` and `hasActiveFilters`, all of which call the four existing predicates and
contain no matching logic of their own. Not one existing export changes signature or behaviour,
and an acceptance criterion pins that. The alternative — chaining the three predicates inside
`PoolGrid`'s `useMemo` — was rejected because 02-UI-SPEC §Pure-core boundary states that "the
search predicate, every filter predicate … are selectors and pure functions in `src/core/`", and
because it would put the Phase 3 round-restriction seam in a `.tsx` file where `npm run
check:pure` cannot defend it. Composition is a rule; rules live in core.

**3. `PoolGridProps.onPick` gains a second parameter.** `onPick(entry, { filtersCleared })`. A
function of arity 1 is assignable to a function of arity 2 in TypeScript, so 02-07's `toggleBan`
and every existing call site compile unchanged and are not edited. The parameter exists because
of a real ordering hazard, not for symmetry: on a pick commit, `TurnBanner`'s announcement effect
and `PoolGrid`'s filter clear land in the same commit, `PoolGrid` is the later sibling in DOM
order, and a second `announce` would overwrite whose turn it is — the one fact a shared screen
must never lose. 02-UI-SPEC's design answers this by composing one string in `TurnBanner`
(`Round {r} of {rounds} — {playerName} picks. Filters cleared.`), which requires `TurnBanner` to
know. One boolean is the smallest thing that can travel.

**4. The type toolbar's buttons are not `TypePill` elements.** 02-UI-SPEC §8 item 2 says the
toolbar holds "18 `TypePill` toggle buttons". `TypePill` is a `<span>` whose stylesheet sets
`height: var(--pill-h)` (24px), and the same document's §Target size row says filter type pills
must be 44 × 44 and "this is why filter pills do not use `--pill-h`". The two cannot both hold
for one element. So the toolbar renders its own `.type-filter` `<button>`, styled in
`FilterBar.css` at `--target-min` in both axes, and the shared thing is the DATA rather than the
box: hue, ink, three-letter code and full name all come from `typeDisplay()` in
`src/ui/type-codes.ts`, which is the closed 18-entry map 02-03 built and which is the only place
a drift between the card pill and the filter pill could actually happen. `src/ui/type-codes.ts`
and `TypePill.tsx` are read and not modified.

**5. The `role="toolbar"` column count is injected, not measured inside the hook.** 02-UI-SPEC
§Pure-core boundary names "reading the rendered grid's column count for arrow-key navigation (a
DOM measurement, so it lives in the hook)". `useRovingTabindex` instead takes an optional
`columns: () => number` and defaults it to `() => 1`. The navigation RULE — which index an arrow
key moves to, how it wraps, where Home and End go — still lives in the hook and is the part that
can be wrong; only the measurement is injected. The reason is testability: happy-dom performs no
layout and does not resolve `repeat(auto-fill, …)`, so a hook that read the DOM itself would ship
its two-dimensional behaviour with no headless test at all. With injection a test passes
`() => 4` and asserts the full 2-D rule against twelve buttons. 02-PATTERNS requires the hook be
written for both consumers "from the start"; this is how it is written for both while remaining
provable for both.
</deviation_record>

```ts
// src/core/search.ts — ADDITIVE. The four existing exports are untouched.

/** Host-operated filter state. Ephemeral view state: never persisted, never in the document. */
export interface PoolFilters {
  /** Raw text as typed. Normalized exactly once, by `compileFilters`. */
  query: string;
  /** Selected type names, exactly as they appear in `RosterEntry.types`. */
  types: readonly string[];
  /** True = every selected type must be present (D-33's AND). False = any (the default, OR). */
  matchAll: boolean;
  mega: MegaFilterMode;
}

/** `PoolFilters` with the query normalized. Build once per change, not once per entry. */
export interface CompiledPoolFilters {
  readonly key: string;
  readonly types: readonly string[];
  readonly matchAll: boolean;
  readonly mega: MegaFilterMode;
}

/** The neutral value. Never mutated — filter state is replaced wholesale, never edited. */
export const NO_FILTERS: PoolFilters;

export function compileFilters(filters: PoolFilters): CompiledPoolFilters;

/**
 * The one composed predicate. ANDs `matchesName`, `matchesTypes` and `matchesMega`.
 *
 * This is the Phase 3 seam. A round's own pool restriction joins by adding one field to
 * `PoolFilters` / `CompiledPoolFilters` and one clause here. No UI file changes, because a
 * round restriction is not host-operated — it is a rule the compiled schedule imposes, so it
 * gets no control in `FilterBar`. `MegaFilterMode` does NOT gain a fourth member; 02-01
 * recorded that decision in `matchesMega`'s doc block and this module honours it.
 */
export function matchesFilters(entry: RosterEntry, compiled: CompiledPoolFilters): boolean;

/** True when any control is away from its neutral value. Drives `Clear filters` and D-35. */
export function hasActiveFilters(filters: PoolFilters): boolean;
```

```ts
// src/ui/use-roving-tabindex.ts — kebab-case filename, matching `src/ui/use-ownership.ts`.
import type { RefObject } from 'preact';

export interface RovingTabindexOptions {
  /** How many focusable items are rendered right now. Shrinking clamps the active index. */
  count: number;
  /**
   * Columns in the rendered layout. Injected rather than measured — see the plan's
   * `<deviation_record>` item 5. Omit for a single-axis toolbar; the default `() => 1`
   * makes Down behave as Right and Up as Left, which is correct for one row.
   */
  columns?: () => number;
}

export interface RovingTabindex {
  /** Attach to the element that CONTAINS the items. Used to focus by position. */
  containerRef: RefObject<HTMLElement>;
  activeIndex: number;
  /** `0` for the active item, `-1` for every other — the whole of the one-tab-stop rule. */
  tabIndexAt: (index: number) => 0 | -1;
  /** Attach to the container. Handles ArrowLeft/Right/Up/Down, Home, End. Nothing else. */
  onKeyDown: (event: KeyboardEvent) => void;
  /** Attach to every item. Keeps the active index in step with focus arriving by mouse. */
  onItemFocus: (index: number) => void;
  /** Move the active item and focus it. For restoring focus when the set changes. */
  focusItem: (index: number) => void;
}

export function useRovingTabindex(options: RovingTabindexOptions): RovingTabindex;
```

## Trust Boundaries

This is a static, serverless, single-origin browser application with no accounts, no network
calls after first load, and no server-side model to invent one for. The surface this plan adds is
narrow and is stated honestly rather than padded.

| Boundary | Description |
|----------|-------------|
| host-typed query → `FilterBar` → the empty-state sentence and the live region | Free text authored on this machine, rendered back into a `<p>` and into `announce`. The only new untrusted-shaped input in this plan, and it is untrusted in shape only. |

| filter state → nowhere | Deliberately terminal. It reaches no action, no reducer, no `localStorage` key and no exported JSON. Its absence from every persistence path is the security-relevant property. |
