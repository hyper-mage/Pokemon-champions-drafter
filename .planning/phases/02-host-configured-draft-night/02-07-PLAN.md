## Phase Goal

Verbatim from `.planning/ROADMAP.md` §Phase 2. **Note: this Goal line is not written in
`As a … I want to … so that …` form**, and was not rewritten here — see 02-01-PLAN.md.

> A host sets up a real tournament for their group — names, format, pool size, banlist —
> and 4–8 friends draft through it on one shared screen with everything they need visible
> at once.

**Slice delivered by this plan:** the host excludes Pokémon from the draft. They type a name
or click a cell in the full roster grid, the excluded species collect as removable chips, the
feasibility gate recomputes against the smaller legal count, and the draft that starts contains
none of them anywhere. End to end: `ConfigScreen` ban state → `checkFeasibility` → `drawPool`
candidates → `createTournament` → `pool/built.ids` → the pool the table actually sees.

This is ROADMAP Phase 2 Success Criterion 2, and nothing before this plan builds a ban surface.

<objective>
Build the two ban input surfaces D-10 specifies over one flat species banlist, the ban-mode
selector BAN-01 requires, and the two places a banned species has to be accounted for — absent
from the pool, and named in the top-bar disclosure.

Purpose: `drawPool` already excludes whatever is not in its candidate list and `checkFeasibility`
already counts bans by set membership, but nothing in the phase ever hands either of them a
non-empty banlist. Success Criterion 2 is unmeetable until something does. This plan is that
something, and it adds no second gate, no second count and no second write path to do it.

Output: `src/core/bans.ts`, `TypeaheadField`, `BanChipList`, a ban mode on `PoolGrid` and
`MonCard`, the `Bans` config group at its declared position, the seventh confirm set, and the
`Bans ({n})` draft-screen disclosure.
</objective>

<deviation_record>
Four places where this plan resolves or declines something a source document says. Each is
recorded here rather than absorbed silently.

**1. `{n} bans` gets a singular/plural helper.** 02-UI-SPEC gives the announcement
`{name} banned. {n} bans.` and the confirm body `This clears all {n} bans at once.` as literal
templates. Rendered at `n === 1` both read `1 bans`. Both counts are reachable at 1 — the first
ban announces, and `Clear the banlist` renders as soon as the list is non-empty. S-5 requires a
singular/plural helper for every interpolated count and `importConfirmBody` is the precedent,
with its reason recorded there: a visible grammar error reads as a tool that was not finished.
02-06 made the same call on `REMOVE_PLAYER_CONFIRM`'s "0 players" clause. So one helper produces
`1 ban` / `{n} bans` and both strings consume it; every other character is verbatim.

**2. Ban mode's disabled options take native `disabled` AND `aria-disabled`, not
`FeasibilityBar`'s divergence.** S-9 records that a disabled control whose reason matters stays
focusable so it can state that reason, and `Start draft` is built that way. Ban mode is not that
case and must not copy it. `Start draft`'s reason is computed, changes on every keystroke, and
lives in a separate `role="status"` element that only a focusable control can point at with
`aria-describedby`. Blind and snake carry a reason that is static and sits **inside the option's
own accessible name** — the visible suffix `— Not yet available` that 02-UI-SPEC §2 specifies and
02-03's `SegmentedControl` was explicitly built to accept from the caller. A natively disabled
radio is still in the accessibility tree and still announces that name. Nothing is lost, and
`SegmentedControl` needs no change. Record this in a comment beside the options array so a
reviewer does not "fix" it in either direction.

**3. `PoolGrid` in ban mode renders no `<h2>`.** The copywriting contract gives `Pool heading |
Pool` under **Draft screen** only, and gives the ban grid exactly one string, its count line. A
`<section>` needs an accessible name to earn its role, and inside the `Bans` `<fieldset>` the
`<legend>` already supplies one. So in ban mode the root is a `<div class="pool pool--ban">` with
no heading and no `aria-labelledby`; in draft mode the `<section aria-labelledby="pool-heading">`
02-03 shipped is untouched. This invents no copy and removes no landmark that had a name.

**4. `confirm-copy.ts`'s "deliberately absent" note is deleted in the same change that makes it
false.** 02-06's module doc block records that a seventh set — `Clear the banlist` — is specified
by 02-UI-SPEC §11 and absent because no plan builds the surface it sits on, and that this is a
gap in the phase's coverage rather than an omission from the module. This plan builds that
surface, so the note must go with the same edit that adds the copy. A stale contract comment is
worse than none because the next reader trusts it. 02-06's acceptance criterion
`grep -c "Clear the banlist" src/ui/confirm-copy.ts` returns at least 1 either way — it is
satisfied by the real copy afterwards rather than by the note.
</deviation_record>

import type { RosterEntry } from './roster/types';

/**
 * The roster entries a banlist actually excludes, sorted by `name` for display.

 * The length of the returned array is |B ∩ rosterIds| — the same figure
