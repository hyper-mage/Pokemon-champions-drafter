## Phase Goal

Verbatim from `.planning/ROADMAP.md` §Phase 2. **Note: this Goal line is not written in
`As a … I want to … so that …` form**, and was not rewritten here — see 02-01-PLAN.md.

> A host sets up a real tournament for their group — names, format, pool size, banlist —
> and 4–8 friends draft through it on one shared screen with everything they need visible
> at once.

**Slice delivered by this plan:** eight friends sit in front of one screen and every fact the
draft needs is on it at once — whose turn it is, the whole players × rounds board, and every
team as it fills — and nothing destructive happens without being asked first. End to end:
`loadViewPrefs` → `SplitPanes` → `PoolGrid` beside `BoardGrid` → `TeamStrip` → `MonChip`, with
`handleUndo` → `undoCrossesRoundBoundary` → `ConfirmDialog` → `store.undo`.

This is ROADMAP Phase 2 Success Criterion 5, and it is the last plan of the phase.

<objective>
Build the shared draft screen: the two-pane shell that keeps the board visible at every moment,
the board itself at N players, and the one confirm pattern that stands in front of every
destructive action.

Purpose: criterion 5 is the only success criterion that is about the room rather than about the
arithmetic. Everything before this plan produced correct numbers; this plan is what makes eight
people around one screen able to read them. It also closes the phase's single easiest defect to
ship — a confirm wired to a button while `Ctrl+Z` walks straight past it.

Output: `SplitPanes` and `.draft-shell`, a board that renders N players and derived rounds with
names that appear on expansion, `ConfirmDialog` plus `confirm-copy.ts`, the pure
`undoCrossesRoundBoundary` predicate, and the non-blocking feasibility notice that is the one
place an adopted document's arithmetic becomes visible to the host.
</objective>

<deviation_record>
Four places where this plan declines or resolves something a source document says. Each is
recorded here rather than absorbed silently.

**1. `02-UI-SPEC` §Responsive behaviour says the stacked panes put the board first; this plan
puts the pool first.** The same document's §Interaction & Accessibility Baseline says "DOM order
equals visual order: sticky head → pool pane → board pane. No CSS reordering, so WCAG 1.3.2 and
2.4.3 hold trivially." Below 1280px those two rules contradict each other. The board-first rule
exists to serve criterion 5 ("the board visible at every moment"), and criterion 5 is satisfied
by either order once both rows live inside a `100dvh` grid whose rows scroll independently — the
board is on screen either way. The focus-order rule is a WCAG conformance rule and cannot be
satisfied another way. So the ordering preference is declined and the conformance rule is kept.
Below 1280px is explicitly "not a target platform" in the same section.

**2. `02-UI-SPEC` §11 gives the import confirm a new body string; §Component inventory says
`ImportConfirmDialog`'s copy is unchanged.** §11 wins: it states "D-39 is an instance-level
contract, not a pattern to be improvised against at build time. Every body string is given
literally below." The body becomes §11's. Tone (`danger`) and button order and labels
(`Replace draft` / `Keep current draft`) are unchanged, so the inventory row survives except on
the one field the two rows disagree about. The existing Phase 1 assertion on `importConfirmBody`
is updated in the same task.

**3. `02-UI-SPEC` §11's undo body has a second clause that the shipped mechanism cannot make
true.** The row reads `… Picks made after it are undone too — {n} in total.` `undoLast`
(`undo.ts:92-100`) removes exactly one pick — the most recent — so in the only state where this
dialog can appear there are no picks after it and `{n}` is 1. The clause is kept in the composer
but gated on `removedCount > 1`, so it is dormant today and correct the day a walk-back undo
exists. D-37 is explicit that "the mechanism is unchanged"; inventing a walk-back undo to make a
sentence true would be the larger deviation.

**4. `02-UI-SPEC` §11 gives no dialog headings, and `Dialog` requires one** (`Dialog.tsx:43`).
Phase 1's `IMPORT_CONFIRM_HEADING` — `Replace the current draft?` — is the only precedent: a
question naming the action. The new headings follow it and are listed literally in Task 3.
</deviation_record>
