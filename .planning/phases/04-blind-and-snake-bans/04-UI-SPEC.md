# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This document is a continuation of `03-UI-SPEC.md`, which continues `02-UI-SPEC.md`, which
continues `01-UI-SPEC.md`.** The spacing scale, the four-size two-weight type scale, the colour
roles and their four reservations, the density contract, the two-pane geometry, the confirm
pattern, the inert-with-a-reason mechanism, and the interaction and accessibility baseline all
remain binding in full. This document states only what is **added** and what is **amended**. Where
it is silent, Phase 3's contract governs; where that is silent, Phase 2's does; where that is
silent, Phase 1's does.

**Scope — the seven surfaces this phase renders or reshapes:**

1. Config screen additions — `bansPerPlayer`, the duplicate-policy control, two enabled ban modes.
2. The ban stage shell — shared-screen, draft-styled, sequenced **before** the draft.
3. The blind **locked** state — the resting destination, and where D-18's discards land.
4. The blind **entry** surface — full-screen, behind the shield.
5. The **reveal** screen — attributed bans, named collisions, a feasibility line, `Start draft`.
6. The **snake** ban surface — previous bans visible, already-banned species inert with a reason.
7. The **blocked** feasibility state at the reveal (D-22).

**Binding upstream:** `04-CONTEXT.md` (D-01…D-23, all locked), `03-UI-SPEC.md` (approved),
`02-UI-SPEC.md` (approved), `01-UI-SPEC.md` (approved), `CLAUDE.md` §Conventions / §Architecture,
`.planning/REQUIREMENTS.md` (BAN-03…07, RULE-08), `.planning/ROADMAP.md` §Phase 4.

**There is no `04-RESEARCH.md`.** Every measured figure in this document was read from this
repository on 2026-08-20 and the source is named at the point of use.

## The reframe this contract is built on

`04-CONTEXT` §Phase Boundary is load-bearing and every decision below inherits it:

> **The host is the scribe.** Players hand their bans over out of band — Discord, usually — and the
> host types them in on the shared machine.

Therefore BAN-05's "full-screen pass-the-device interstitial" is satisfied as a **shield against
the room reading the screen**, not as a per-player identity handshake. There is no "I'm Sam" step
anywhere in this contract, and designing one would be designing for the exception (D-04).

### How the shield and D-05 fit together — read this before implementing

D-05 says *"nothing but progress is on screen until the reveal — not for the current player, not
for the finished ones."* There is one screen, so the person typing must be able to see what they
are typing. The resolution is that **D-05 governs the screen's resting state**, and the ban stage
has two states rather than one:

| State | What is on screen | How it is left |
|-------|------------------|----------------|
| **Locked** — the resting destination | `{n} of {m} entered`, whose turn is next, and one button. **No species name anywhere.** | Only by a deliberate tap on `Enter {playerName}'s bans` |
| **Entry** — transient, deliberate | The roster, the typeahead, and the current selection. Necessarily readable by anyone looking. | Lock in · `Hide these bans` · tab-hide · bfcache restore |

The screen never *sits* in Entry. Every exit from Entry — deliberate, accidental, or hostile —
lands on Locked, and Locked is designed as a real destination with its own copy, not as an error.
That is what makes D-05's "a host who steps away cannot leave a leak on screen" true with zero
discipline required from the room.

## Amendments to Phase 2's and Phase 3's Contracts

Two shipped contracts are deliberately narrowed by this phase. Each names the exact text it
replaces. **Every stylesheet or source comment stating the superseded rule must be corrected in the
same change that breaks it** — a stale contract comment is worse than no comment, because the next
reader trusts it (`02-UI-SPEC` §Amendments, `03-UI-SPEC` §Amendments).

### Amendment 1 — the top-bar bans disclosure never contains an unrevealed ban (narrows `02-UI-SPEC` §Accessibility, row `Bans disclosure`; narrows `TopBar.tsx:209-217`)

**The disclosure is a leak channel and it is the least obvious one in the phase.** It renders every
banned name behind a native `<summary>` that anyone in the room can open with one click.

**Replacement contract:** the disclosure's count and list are `bannedEntries(entries, publicBans)`
where `publicBans` is:

| Mode / stage | `publicBans` |
|--------------|-------------|
| `hostBanlist`, any time | `config.bans` — unchanged from today |
| `snake`, during and after the ban stage | `config.bans` ∪ every ban already placed — snake bans are public the instant they land (BAN-03) |
| `blind`, **before** `bans/revealed` | `config.bans` **only** |
| `blind`, after `bans/revealed` | `config.bans` ∪ every revealed ban |

The label stays `Bans ({n})` in every case; only the content varies. The count rising at the reveal
is honest — the bans genuinely increase there.

`bannedEntries` remains **the one correct source of any displayed ban count** (`src/core/bans.ts`,
`CLAUDE.md` §Conventions). `bans.length` is never that number, and neither is
`revealed.flatMap(...).length` — a collision means two submissions and one banned species, which is
exactly the case the array length gets wrong.

The disclosure stays read-only and stays unrendered at zero, both unchanged.

### Amendment 2 — pane-state availability during the ban stage (extends `03-UI-SPEC` Amendment 3)

The scoping table gains two rows. The mechanism is unchanged — an unavailable expand is **rendered
inert with a visible reason**, never omitted, and the persisted value is silently coerced.

| Screen state | States available | Coercion |
|--------------|-----------------|----------|
| **Snake ban stage** | `split`, `board-full` | a stored `pool-full` → `split`, silently — same as picking |
| **Blind ban stage** (locked and reveal) | **none — there are no panes** | **the stored preference is neither read nor written.** It must survive the ban stage untouched so the draft opens in the state the host chose. |

Blind's locked and reveal screens use `.app-shell`, not `.draft-shell`. They are read-and-act
screens like the landing screen, not two-pane working screens. Snake keeps `.draft-shell` because
it *is* the two-pane working screen — pool on the left, ban board on the right, exactly the draft
the room is about to run (D-02).

## A conflict in the upstream instructions, recorded rather than silently resolved

D-19 requires the disabled duplicate-policy member be labelled `Re-ban — not yet available`
(lowercase `n`) **and** "matching the established label form at
`src/ui/screens/ConfigScreen.tsx:277-278`". The shipped string at that location is:

```ts
{ value: 'blind', label: 'Blind — Not yet available', disabled: true },
```

Capital `N`. The two requirements cannot both be met literally.

**This contract specifies `Re-ban — Not yet available`, matching the shipped casing.** D-19's own
stated intent is to "reuse the label form exactly rather than inventing a second way to say it",
and two casings of one label form *is* a second way to say it. The lowercase rendering in the
decision text reads as prose quoting, not as a case-sensitive string.

This is a one-token change if the owner prefers otherwise. It is recorded here so the planner does
not discover the conflict at build time and guess.

## Design System

Unchanged. Restated because the constraint is absolute and this phase adds five components.

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-built Preact components under `src/ui/` |
| Icon library | none. **This phase needs zero glyphs.** Progress is the words `Entered` / `Not yet`; the shield is a heading and a button; an empty ban slot is a dashed box. No lock icon, no eye icon, no SVG, no icon font. |
| Font | system stack, no webfont (Phase 1 §Typography) |

**Hard constraint — do not violate.** Runtime `dependencies` is exactly `preact@10.29.8` and
`@preact/signals@2.10.1`, both exact-pinned (verified in `package.json` this session). No CSS
framework, no CSS-in-JS runtime, no component registry, no icon package, no modal library — the
shield is a screen state, not a third-party overlay. A third runtime dependency is a constraint
violation, not a trade-off.

**Styling mechanism:** unchanged. `src/ui/tokens.css` declares values on `:root` and styles
nothing. One stylesheet per component, beside it, consuming tokens only. No raw hex. No raw px for
anything the token table covers. The two sanctioned raw lengths remain `--board-label-w: 176px` in
`BoardGrid.css` and the `60fr 40fr` pane split; **this phase adds none.**

`npm run check:nohtml` forbids `innerHTML` and `dangerouslySetInnerHTML` anywhere under `src/`.

## Typography

**Unchanged in every respect.** Four sizes, two weights (400, 600), no 500, no 700, no italics. No
fifth size is introduced by any surface in this phase.

| Token | Value | New usage in this phase |
|-------|-------|------------------------|
| `--text-body` | 400 18px / 1.5 | Locked-panel progress line; progress-row `Entered` / `Not yet`; **reveal-row species names**; collision lines; the post-reveal feasibility line; the snake phase line; the snake "already banned" rule line; entry-surface progress line |
| `--text-label` | 600 14px / 1.4 | Ban-board column headers (`Pass {n}`); config helper text; ban count line inside the entry grid |
| `--text-heading` | 600 24px / 1.25 | **Reveal-row and progress-row player names**; locked-panel sub-heading; config sub-section headings |
| `--text-display` | 600 36px / 1.15 | **The locked panel's headline**; the entry surface's `<h1>`; the reveal's `<h1>`; the snake turn banner (unchanged mechanism) |

**Three legibility floors, and why each sits where it does.**

- The **locked panel's headline** takes `--text-display`. It is the entire information content of a
  screen a whole room is waiting on, and the largest token in the scale is the correct one — the
  same argument `03-UI-SPEC` made for the card digit.
- **Player names**, on both the progress board and the reveal, take `--text-heading` (24px),
  matching the board row label and the hand-strip pips. Player identity is read at a distance in
  every surface this project has shipped; giving it one size across all of them is what makes the
  ban stage read as the same tool as the draft.
- **Species names on the reveal** take `--text-body` (18px), which is the floor `02-UI-SPEC`
  assertion 2 set for board chip names. The reveal is the `board-full` case — names exist and are
  read aloud — so it sits at that floor and not below it.

| Secondary (30%) | `#1A1F26` | unchanged, plus the locked panel, the progress rows and the reveal rows |

| Accent (10%) | `#FFCB05` | **unchanged reserved list — see below** |
| Destructive | `#FF7A70` | **unchanged reserved list — the ban-stage abandon is the *same* reserved use as the draft abandon, not a fourth** |

### Accent reserved for — still exactly three

1. **The on-the-clock indicator** — in snake this is the ban board's next cell, using
   `board__cell--next`'s existing `--border-w` accent border and `--color-accent-soft` tint, plus
   the accent left rule on the turn banner. Same mechanism, new grid.
2. **The primary action of the current screen** — one per screen:
   - Blind locked: `Enter {playerName}'s bans`, or `Reveal bans` at `{m} of {m}`.
   - Blind entry: `Lock in {playerName}'s bans`.
   - Reveal: `Start draft`.
   - The confirming button of each `default`-toned confirm dialog (a modal is the current screen).
3. **The keyboard focus ring** — unchanged, global, `:focus-visible`.

**The snake ban surface has no accent-filled button at all**, for exactly the reason the draft
screen has none: banning *is* the action and the pool cells *are* the target. One click bans and
the turn passes (§6). A `Confirm ban` button would be a second way to do the one thing the screen
does.

### Destructive reserved for — still exactly three

1. The storage-unavailable blocking screen (unchanged).
2. The import-overwrite confirm (unchanged).
3. **The abandon confirm** — which now has two copy sets, one for a live draft (`Abandon draft`,
   shipped) and one for the ban stage (`Abandon tournament`, §7). Two strings, one reservation, one
   mechanism. Abandoning from the ban stage discards a tournament with locked bans and no picks;
   that is the same category of loss, not a new one.

**A blocked `Start draft` at the reveal is not danger-coloured** (D-22). Nothing is lost — it is a
not-yet state, and its sentence renders in `--color-text`. This restates `02-UI-SPEC` rather than
amending it, because a *permanently* blocked Start is the one place a reader might expect danger
and must not find it.

### Colour is never the only signal — new rows

| State | Colour signal | Non-colour signal |
|-------|--------------|-------------------|
| **A ban already placed publicly** (host ban always; another player's ban in snake) | none | `aria-disabled="true"` + `opacity: 0.45` + `text-decoration: line-through` on the name + the reason in the accessible name + one visible rule line beneath the grid |
| **A ban chosen now, not yet locked** | none | `aria-pressed="true"` + `--color-surface-raised` fill + `--border-w solid var(--color-text)` — the shipped segmented-control/type-filter selected treatment, a lightness and shape change, no hue. **Deliberately not dimmed-and-struck:** dim+strike means *gone*, border+raise means *yours, pending*. |
| **A player who has entered (blind progress)** | none | the word `Entered` at `--text-body`, and a solid filled marker |
| **A player who has not entered (blind progress)** | none | the words `Not yet` at `--text-body`, and a `--hairline-w dashed` marker in `--color-border-strong` — the shipped empty-board-slot treatment |
| **An empty ban-board slot (snake)** | none | `--hairline-w dashed var(--color-border-strong)`, unchanged from the draft board |
| **A collision, at the reveal** | none | a full sentence naming every player involved and the species (D-19) |
| **Blocked `Start draft` at the reveal** | `opacity: 0.45` | `aria-disabled="true"` + `aria-describedby` → the arithmetic in a `role="status"` region |

## Layout Budget — measured, not assumed

Every figure below is derived from `02-UI-SPEC` §Two-Pane Geometry and `BoardGrid.css:54`, both
read this session.

### The snake ban board fits the split board pane

The ban board is `BoardGrid`'s geometry with one column per **pass** instead of per round:

```
grid-template-columns: var(--board-label-w) repeat({bansPerPlayer}, minmax(0, 1fr));
gap: var(--space-2);
```

A sprite-only `MonChip` needs `--sprite-sm` (48) + `--space-1` padding × 2 (8) = **56px**, the same
figure D-21 rests on.

```
board pane, split, 1920px                       739
  − label column                       −176  →  563
  − (n − 1) gaps × --space-2 (8)
÷ n passes
```

Solving `56n + 8(n − 1) + 176 ≤ 739` gives `64n ≤ 571`, so **n ≤ 8**.

| `bansPerPlayer` | Cell width, split | Verdict |
|-----------------|------------------|---------|
| 1 | 563px | huge |
| 2 | 273px | comfortable — **the realistic case at 4–8 players** |
| 3 | 176px | comfortable |
| 6 | 86px | **exactly the draft board's round cell**, which ships |
| 8 | 63px | fits, 7px of slack |
| 9 | 55px | **below the 56px chip minimum** |

**Above 8, `board-full` is the remedy and it is already built.** At `board-full` the same solve is
`64n ≤ 1480`, so **n ≤ 23**. This is the same job D-21 gave the expand control — the ban board
inherits it with no new code and no new state.

**No feasibility reason is added for this.** Layout is not satisfiability, and the gate is the one
authority on what is satisfiable (Phase 3 D-30, `03-UI-SPEC` §4). A `bansPerPlayer` of 9 produces a
tight but working screen with a working expand, which is a preference problem, not a blocked
tournament. `CLAUDE.md` §Constraints says warn rather than hard-cap; here there is nothing to warn
about that the expand control does not already answer.

### The blind progress board fits with room to spare

Eight rows of `--text-heading` (24 × 1.25 = 30px) plus `--space-2` gaps:

```
8 × 30 + 7 × 8 = 296px
```

Against a 1080p viewport minus the top bar and `--space-4` padding, this is not close to binding
even with the headline (41px), the progress line (27px), `--space-6` above and below (96px) and a
`--target-min` button (44px): **504px of content in roughly 950px of shell.**

### The reveal fits at the realistic worst case

One row per player, each row `--text-heading` name (30px) over a wrapping strip of named chips.
A named chip is `--sprite-sm` (48) + `--space-1` gap (4) + the name at `--text-body`; the roster's
longest name is 20 characters (`Tauros-Paldea-Combat`, measured Phase 2), roughly 180px at 18px/400.
So a named chip is ~232px wide and a row of them at 1200px (`.app-shell` cap) holds **five per
line**.

```
8 players × (30 name + 8 gap + 60 chip row) = 784px, plus collisions and the feasibility line
```

The reveal scrolls at 8 players with high ban counts and that is correct — the room reads it top to
bottom, and D-23 gives them the time to. It is not a fixed-height surface and must not be made one.

### 1. Config screen — the `Bans` group grows

Group order is unchanged (six groups, `Bans` at 4, `Pool` last). Sub-sections inside `Bans` are
`--text-heading` headings with `--space-5` between them, matching `Mega rules`.

**`Ban mode` segmented control — two options enabled.**

| Value | Label | State |
|-------|-------|-------|
| `hostBanlist` | `Host banlist` | enabled, default |
| `blind` | `Blind` | **enabled** — the `— Not yet available` suffix is removed |
| `snake` | `Snake` | **enabled** — same |

Removing the suffix is the whole of D-12's promised payoff: Phase 4 enables two options rather than
redesigning the control.

**`Bans per player` — a `NumericField`, rendered only at `blind` or `snake`.**

| Property | Value |
|----------|-------|
| Label | `Bans per player` |
| Default (new tournament, blind/snake) | `1` |
| Stored value at `hostBanlist` | `0` |
| `min` / `max` | `1` / `MAX_BANS_PER_PLAYER` — a new constant beside `MAX_SWAP_BUDGET = 24` in `import-guard.ts`, at the same value, so the build cannot create a document `isValidTournament` refuses to re-open (STATE decision, Phase 3) |
| Helper | `Each player bans this many Pokémon before the pool is drawn. Every ban applies to everyone.` |

The helper's second sentence is not decoration: a player new to the format reads "my bans" as
personal, and the whole ritual depends on them not doing so.

**Why it is not rendered at `hostBanlist`.** There are no player bans in that mode, so the field is
*wholly void* — the shipped precedent for a wholly void affordance is not to render it
(`Clear the banlist` at zero bans, `Clear filters` with none active, `03-UI-SPEC`'s reorder controls
when every round is the same kind). This also keeps `hostBanlist` byte-identical to what Phase 2
verified, which is exactly D-01's zero-regression posture.

**Why the default is `1` and not `0`.** Every other numeric field in this project defaults to 0
because a feature the host has not asked for should stay invisible. This field only *exists* once
the host has picked a mode whose entire purpose is player bans, so 0 is never the intent, and a
default of 0 would greet every blind/snake host with an immediate blocker. `1` is a constant, not a
derivation from player count or roster size, so it introduces no second authority on what is
sensible — which is the precise thing D-10 rejected.

**Migration default is `0`, and it is a different number on purpose.** A schema-3 document was
necessarily `hostBanlist` (blind and snake were disabled), so `bansPerPlayer: 0` is lossless there.
Do not unify the two constants; they answer different questions.

**Duplicate policy — a `SegmentedControl`, rendered at `blind` or `snake`.**

| Property | Value |
|----------|-------|
| Legend | `Duplicate bans` |
| Option 1 | `Both apply, one is spent` — enabled, default |
| Option 2 | `Re-ban — Not yet available` — `disabled: true` (see §A conflict in the upstream instructions) |
| Helper | `Blind mode only. If two players ban the same Pokémon it is banned once, the second ban is spent, and the reveal says who collided.` |

**At `snake` the whole control renders inert** — `aria-disabled="true"`, `opacity: 0.45`, click
refused — with the visible reason beside it:

```
Snake shows previous bans, so two players cannot ban the same Pokémon.
```

Inert rather than unrendered, because a host flipping between blind and snake to compare them will
look for it, and this is exactly the case the inert-with-a-reason mechanism exists for (the Mega
filter during a Mega round, the pane expand during card play). **The inert ARIA is shed the moment
the mode changes to `blind`** — WR-04, and this phase adds a fifth consumer of it.

The `— ` separator is an `aria-hidden` span, not generated content, with the reason constant
excluding it, so the string table, the source constant and the test assertion stay one value
(plan 02-12, WR-03).

### 2. Feasibility additions (RULE-08, D-21)

**This spec does not restate the precedence order.** It lives in `feasibility.ts`'s `PRECEDENCE`
and a third copy is a third thing that can drift (`03-UI-SPEC` §5). The additions and their
**neighbours** are named instead.

| Code | Severity | Sits beside | Copy |
|------|----------|-------------|------|
| `bansPerPlayerNotAnInteger` | blocking | `swapBudgetNotAnInteger` | `Bans per player needs a whole number. Enter 1 or more, or switch to host banlist.` |
| `bansPerPlayerNotPositive` | blocking | immediately after the above | `Blind and snake need at least 1 ban per player. Enter a number, or switch to host banlist.` |
| `notEnoughMegas` — **re-measured again** | blocking | unchanged position | see below |

**The RULE-09 blocker gains D-21's pessimistic player-ban term.** Phase 3's string is unchanged
whenever player bans contribute zero; the blind/snake string adds one clause and one remedy:

| Mode | Copy |
|------|------|
| `hostBanlist` | `Not enough Pokémon can Mega. {p} players × {m} Mega rounds needs {x}; {y} can still Mega after {b} species bans and {f} Mega-forme bans. Lower the Mega requirement, or unban a Mega forme.` *(verbatim from `03-UI-SPEC` §5 — unchanged)* |
| `blind` / `snake` | `Not enough Pokémon can Mega. {p} players × {m} Mega rounds needs {x}; {y} can still Mega after {b} species bans, {f} Mega-forme bans and {q} player bans. Lower the Mega requirement, lower bans per player, or unban a Mega forme.` |

`{q}` is `players × bansPerPlayer` — D-21's fully pessimistic assumption that **every** player ban
lands on a Mega-capable species. Both strings must be composed by **one function** so the shared
prefix cannot drift; a test pins the `hostBanlist` arm byte-identical to Phase 3's shipped string.

Severity is unchanged in kind: blocking disables `Start draft` via `aria-disabled` on a focusable
button with `aria-describedby` pointing at the reason.

### 4. The blind locked state (BAN-05, D-05, D-08, D-18)

`.app-shell` (1200px cap), one centred `--color-surface` panel, `--radius`, `--space-3` padding,
`--space-6` above and below the headline.

Top to bottom:

| Element | Size | Copy |

### 5. The blind entry surface (BAN-04, BAN-05, D-04, D-16)

**Full-screen. No top bar, no turn banner, no panes.** This is what satisfies BAN-05's "full-screen
interstitial, not an input mask" literally: the ban entry is the entire working area, not a masked
field inside a visible screen.

Top to bottom:

| Element | Size | Copy / behaviour |
|---------|------|-----------------|
| `<h1>` `tabindex="-1"` | `--text-display` | `{playerName}'s bans` |
| progress | `--text-body` | `{k} of {m} chosen` |
| `TypeaheadField` | — | visually-hidden label `Ban a Pokémon by name`, placeholder `Name`. **The host-as-scribe's primary path** — reading names off Discord, typing beats hunting a 235-cell grid. |
| `BanChipList` | `--text-label` chips | The pending selection. Chip accessible name `Remove {name} from {playerName}'s bans`. Not rendered when empty. |
| `PoolGrid` ban mode | density-scoped | 235 entries in a capped scroll region — `max-height: 60vh; overflow-y: auto`, `--hairline-w solid var(--color-hairline)`, `--radius`. Identical treatment to the config ban grid. `idPrefix` distinguishes it. |
| count line | `--text-label` | `{k} of 235 banned` — composed by the shipped `banCountLine`, one sentence shape |
| footer | sticky bottom | see below |

The footer uses the `FeasibilityBar` mechanism — `position: sticky; bottom: 0`, `--color-bg`
backdrop, `--hairline-w` top border, `--space-3` padding:

| Control | Style | State |
|---------|-------|-------|
| `Lock in {playerName}'s bans` | accent fill, `--color-accent-ink` | `aria-disabled="true"` until exactly `{m}` are chosen, `aria-describedby` → the reason |
| `Hide these bans` | secondary | always live |
| reason | `--text-body`, `role="status"` | `Choose {r} more.` — `banCountPhrase`-style singular/plural helper required (S-5 convention) |

**Species only** (D-16). One flat list of species ids, the ban-mode `PoolGrid` exactly as it ships.
Mega-forme bans stay a host tool on the config screen — that is what Phase 3's 76-cell surface was
built for, and it keeps the ritual explainable at the table in one sentence.

**Locking does not confirm.** Phase 1 D-08's no-confirm posture holds: locking a ban is the same
category of act as making a pick, and D-03's mandatory full undo is what makes it safe.

**There is no review-before-lock step.** Three reasons, strongest first:

1. **The selection is already fully visible on this screen.** `BanChipList` renders every chosen
   species by name, above the grid. A review step would be a second rendering of the same fact, and
   a second rendering of one fact is a second thing that can disagree — the reasoning `03-UI-SPEC`
   used to refuse typed-slot team panels.
2. **D-03 makes undo the correction path**, and it is mandatory precisely because the host will
   type the wrong Pokémon. A review step would be a second correction path competing with the one
   the phase already commits to.
3. **The host enters six players in a row.** Every extra tap is paid six times per stage while the
   room waits.

**`Hide these bans` is the panic control, and it exists because it is free.** D-18 already forces
the entry surface to discard and lock on `visibilitychange` and on a persisted `pageshow`. `Hide
these bans` is a button wired to that same transition — **no new state, no new machinery, one new
label**. Refusing it would mean the tool handles the accidental exposure (an alt-tab) but not the
deliberate one (someone walks in), which is the case a host can actually see coming.

**It does not confirm.** A confirm on a panic control is a second second of exposure, and D-18
establishes that a half-finished entry is discarded with no ceremony. The locked state's discard
notice is where the host is told what happened.

### 6. The snake ban surface (BAN-03, D-12, D-20)

`.draft-shell`, sticky head, two panes. **This is the draft screen's interaction model with ban
columns instead of round columns**, which is D-02's requirement made literal.

**Sticky head:**

| Line | Copy |
|------|------|
| `TurnBanner` (`--text-display`) | `Pass {p} of {passes} — {playerName} bans` |
| phase line (`--text-body`) | `Still to ban this pass: {name} · {name}` — not rendered when empty |

`{passes}` is `bansPerPlayer`; in a true serpentine each player bans exactly once per pass, so a
pass **is** a column. **`Pass` and not `Round`** — `Round` is taken by the draft's own rounds and
by the board's `R{n}` header, and two meanings for one word on a shared screen is how a room ends
up arguing about which round it is.

**D-12's serpentine is not explained on screen.** D-12 records that snake "needs no explanation at
the table". The phase line carries *information* (who is left this pass), never a rule statement.
The order itself is visible in the ban board and in the turn banner, which is where a player checks
it.

**Pool pane:** the ban-mode `PoolGrid` over 235 entries plus the `TypeaheadField`. **One click bans
and the turn passes** — no lock button, no confirm, exactly like a pick. Undo is the safety net and
it does not confirm here, because the ban is on screen and reversing it is visible (unlike blind —
§7).

**Already-banned species render inert with a stated reason** — the constraint upstream of the
click, never a rejection after it (`04-CONTEXT` §Established Patterns; `03-UI-SPEC`'s
`selectRoundEligibleIds` precedent):

| Case | Cell state | Accessible name |
|------|-----------|----------------|
| Banned by the host at config time | `aria-disabled="true"`, `opacity: 0.45`, `line-through`, click returns early | `{name} — banned by the host` |
| Banned by another player earlier in this stage | same | `{name} — already banned by {playerName}` |
| Chosen by nobody | normal | `{name}` (unchanged) |

One visible rule line above the grid, `--text-body`, `--color-text`, rendered whenever at least one
cell is inert:

```
A struck-through Pokémon is already banned and cannot be banned again.
```

Same shape as `03-UI-SPEC`'s `A struck-through card would leave a later player with no legal card.`
The signal named is a shape, not a colour. **Per-cell visible reasons were rejected** — 235 reason
lines is noise, and the accessible name carries the per-cell answer for anyone who needs it.

**The typeahead matches the grid.** A publicly banned species renders as a `role="option"` with
`aria-disabled="true"` and the reason in its label. **Results are never silently filtered** — a
name the host typed that does not appear reads as a broken search, which is the same failure mode
`03-UI-SPEC` §9 spent a sentence preventing on the Mega-round pool.

**Board pane:** `BanBoard` `mode="public"`.

```
grid-template-columns: var(--board-label-w) repeat({passes}, minmax(0, 1fr));
gap: var(--space-2);
```

- Column header: `Pass {n}` at `--text-label`, `--color-text-muted`. Widest string at 6 passes is
  `Pass 6` ≈ 44px inside an 86px cell. Fits.
- Row label: `{playerName}` at `--text-heading`, ellipsised on one line — `BoardGrid`'s shipped
  mechanism, and the 176px column comes from `--board-label-w`, never a literal.
- Filled cell: `MonChip`, `showName={false}` in `split` and `true` at `board-full` — the shipped
  D-21 rule and its `alt` inversion come along unchanged.
- Empty cell: `--hairline-w dashed var(--color-border-strong)`, unchanged from the draft board.
- **The next cell to be filled carries `board__cell--next`** — accent border + `--color-accent-soft`
  tint, accent reserved use 1, shipped mechanism, new grid.
- Ban-board cells are **not interactive**. `03-UI-SPEC` Amendment 1 made a board cell interactive
  under four conditions, all four of which are about swaps; none holds here.

**Empty state**, before the first ban: `No bans yet. {firstPlayerName} bans first.` — the shape
Phase 2 set with `No picks yet. {firstPlayerName} picks first.`

**Snake has no reveal ceremony but it does end on the same screen.** When the last ban lands the
stage moves to `BanReveal` (§7) with no collision rows — collisions are impossible in snake by
construction (D-20). D-23's separate `Start draft` tap applies to both modes: the pool must never
appear the instant the last ban lands.

### 7. The reveal (BAN-04, BAN-07, RULE-08, D-13, D-19, D-22, D-23)

`.app-shell`, `TopBar` above it. **One component serves blind and snake** — it takes
`{ playerId, monIds }[]` regardless of whether the fold produced that from one `bans/revealed`
action or from a run of individual snake bans.

Top to bottom:

| Element | Size | Copy |
|---------|------|------|
| `<h1>` `tabindex="-1"` | `--text-display` | `{n} Pokémon banned` — `n` is `bannedEntries(entries, hostBans ∪ everyPlayerBan).length` |
| sub-head | `--text-body`, `--color-text-muted` | `Every player's bans are below. They apply to everyone.` |
| attribution rows | see below | one row per player, in starting order |
| collisions | `--text-body` | one line per collided species, or nothing |
| feasibility line | `--text-body` | see below |
| primary action | `--target-min`, accent fill | `Start draft` |

**The heading is mode-independent and count-first** on purpose. `Bans revealed` is wrong in snake
(they were revealed as they happened) and a per-mode heading would be two strings that can drift.
The count is the number the room actually wants, and it comes from the one correct source.

**Attribution rows (D-13).** Each row: `{playerName}` at `--text-heading`, then that player's bans
as named `MonChip`s, `flex-wrap: wrap`, `--space-1` gaps. Sprite at `--sprite-sm`, name at
`--text-body`. The row's accessible summary is the sentence the reveal exists to deliver:

```
{playerName} banned {name}, {name} and {name}.
```

A comma-and-`and` list needs the same singular/plural care `banCountPhrase` established: one ban
reads `{playerName} banned {name}.`, two reads `{a} and {b}`, three or more takes the Oxford-free
`{a}, {b} and {c}`.

**Collisions, named explicitly (D-19).** One line per species that more than one player banned:

| Players | Copy |
|---------|------|
| 2 | `{a} and {b} both banned {name}. It is banned once; the second ban is spent.` |
| 3+ | `{a}, {b} and {c} all banned {name}. It is banned once; the other {k} bans are spent.` |

Composed by one function with the same list helper the attribution rows use. **Not rendered at all
when there are no collisions** — a `No collisions` line answers a question nobody asked, and in
snake it would be permanent noise.

**The feasibility line (RULE-08).**

| Verdict | Copy | `Start draft` |
|---------|------|--------------|
| pass | `The pool can be drawn.` at `--color-text-muted` | live, accent fill |
| blocked | see below, `--color-text`, in a `role="status"` region | `aria-disabled="true"`, `aria-describedby` → the region |

**The blocked copy (D-22):**

```
Not enough Pokémon can Mega after the bans. {p} players × {m} Mega rounds needs {x};
{y} can still Mega. The bans are locked, so this tournament cannot start —
abandon it and set it up again.
```

The last clause is not optional. D-22 removes every other exit: `TournamentConfig` never changes
after creation (D-14), so there is no config edit to offer, and a host-voids-a-named-player's-ban
remedy was rejected because it makes the host publicly overrule a named player with no rule to
point at. An error that states a problem without a next action violates `CLAUDE.md` §Copy; here the
next action is abandonment and the sentence must say so.

**The blocked state is reachable only from an imported or hand-edited document, and the planner
should know why.** D-21's config-time gate is fully pessimistic — it assumes every player ban lands
on a Mega-capable species — and a collision *wastes* a ban rather than removing an extra species,
so the post-reveal pool is always at least as large as the config-time worst case. A tournament
created through the config screen therefore cannot fail here. The reachable path is a document
adopted by import (`import-guard` deliberately runs no referential-integrity check — Phase 2
decision 5) or edited by hand. **A test for this state must construct a document, not drive the
config flow.**

**`Start draft` draws the pool (D-23).** It is the first `pool/built` dispatch of the tournament.
The group reads the reveal before the screen changes under them, and a failed RULE-08 check never
has to un-draw anything.

**Abandoning from the reveal or the locked state** uses the top bar's existing abandon control with
new copy — §8.

### 8. Confirmation dialogs — three new sets

All three reuse `ConfirmDialog` over `Dialog`. No new mechanism: focus trap, Escape-to-safe,
return-focus and `tone` are already correct. Consequence sentence stating what changes **in
numbers**, then two buttons that each name a verb and its object, destructive/confirming first so
the safe one is the last thing focus reaches. Nothing is labelled `OK`, `Submit`, `Yes` or `Cancel`
alone.

| Action | Tone | Body copy | Confirm | Safe |
|--------|------|-----------|---------|------|
| Abandon from the ban stage | `danger` | `This discards the tournament and every ban the {m} players have entered. Nothing recovers it unless you have already downloaded the tournament JSON.` | `Abandon tournament` | `Keep the bans` |
| **Undo a blind submission** | `default` | `This removes {playerName}'s bans. They are not shown on screen, so ask {playerName} for the list again before you re-enter it.` | `Remove {playerName}'s bans` | `Keep {playerName}'s bans` |
| Undo the reveal | `default` | `This takes the reveal back to the locked screen. The {m} players' bans stay recorded, and everyone who has already read them still has. Undo again to remove a player's bans.` | `Undo the reveal` | `Keep the reveal` |

**Undoing a blind submission confirms, and this is the sharpest design point in the phase.** Every
other undo in this project acts on something visible — a pick on the board, a card in the played
row, a swap in a slot. D-05 forbids re-displaying a removed blind submission, so this undo removes
a thing the host cannot see. An unconfirmed undo of an invisible thing is precisely the misclick
D-03 exists to correct, and the dialog is the **only** place the host can be told what is about to
happen and what it will cost them (a second message to Discord). The confirm names no species, so
it leaks nothing.

**Undo in snake does not confirm.** The ban is on screen and reversing it is visible, so it is the
same category as a pick, and Phase 1 D-08's no-confirm posture holds.

**Undoing the reveal is honest about what it cannot undo.** Un-revealing cannot un-read. The body
copy says so rather than implying a secrecy restoration the tool cannot deliver. D-23 means no pool
has been drawn, so there is nothing to un-draw — which is why this undo is clean enough to offer at
all.

**Abandon is the same destructive reservation as `Abandon draft`,** with a second copy set because
the state differs: zero picks, locked bans. `Keep the bans` is the safe label because bans are what
is at stake here, exactly as `Keep drafting` is right when picks are.

## The Live-Region Contract — what `announce` may and may not say

`announce` is a **module-level signal that outlives any render** (`LiveRegion.tsx`, `CLAUDE.md`
§Tests). A polite announcement naming a species during blind entry would defeat D-05 through a
channel the visual shield does not cover — it is audible in the room, and it persists in the
accessibility tree after the render that wrote it is gone. Phase 3's screen-reader verification was
**descoped by the host** (`STATE.md` §Deferred Items), so this cannot be deferred to a manual pass
and must be structural.

### The rule

**No `announce()` call anywhere in the blind ban stage names a species, at any time before
`bans/revealed`.** Enforced structurally by S1: the entry surface does not import the module, so a
species name has no route to it. The locked surface owns every announcement in the stage and has no
access to the in-progress selection.

### Permitted during the blind stage

| Trigger | String |
|---------|--------|
| A submission locks | `{playerName}'s bans are locked in. {n} of {m} entered.` |
| The last submission locks | `All bans are in. {m} of {m} entered. Ready to reveal.` |
| An entry is discarded (button, tab-hide, or restore) | `{playerName}'s entry was discarded. Nothing was recorded.` |
| A submission is undone | `{playerName}'s bans were removed. {n} of {m} entered.` |
| The reveal fires | `Bans revealed. {n} Pokémon are banned.` |

### Forbidden before `bans/revealed`

- Any string containing a species name, without exception.
- **Specifically: the shipped `{name} banned. {n} bans.` announcement from `ConfigScreen`.** That
  string is deliberately composed in one place so the typeahead and the grid cannot disagree
  (`ConfigScreen.tsx`, doc comment). The blind entry surface must not reuse it, and S1 is what
  makes reuse impossible rather than merely discouraged.

### Selection feedback during entry, and why it is not a leak

A screen-reader user entering bans still needs to know a toggle registered. That feedback is
carried by **focus-scoped state, not by the broadcast region**:

- The pool cell is a `<button aria-pressed>`; the state change is announced as a property of the
  control the user is focused on.
- The typeahead's `aria-activedescendant` names the option the user is choosing.
- `BanChipList` is a navigable list of the current selection.

All three are scoped to the entering user's own focus and are the same channel the visual selection
already uses. They are unavoidable, they are correct, and they are **not** the live region. This is
stated explicitly so nobody reads the contract as forbidding accessible feedback to the person
actually entering the bans.

**The counted alternative is available where a broadcast is genuinely wanted:** `{k} of {m} chosen.`
names no species and may be announced freely.

### The region is cleared on entering the locked state

Every transition into the locked state writes `announce('')` before or with its own message. Since
every permitted string already names no species this is belt-and-braces — and that is the point: it
makes the leak structurally impossible instead of dependent on every future string being reviewed.
`LiveRegion`'s known byte-identical limitation is not hit, because consecutive stage announcements
always differ by player name or by count.

**A test touching the live region resets `announce` in `beforeEach`** (`CLAUDE.md` §Tests,
restated because this phase adds six announcements).

### Extending Phase 3's arc-minute analysis rather than restating it

`03-UI-SPEC` computed three rows and the host's physical check **passed all of them on the
pessimistic screen** — a ~24" 1080p monitor at 3 metres (`STATE.md`, 2026-08-19 and 2026-08-20).
Every new surface in this phase reuses one of those three sizes, so the analysis extends by
mapping rather than by re-deriving:

| New surface | Size | Same size as | Status |
|-------------|------|-------------|--------|
| Locked headline; entry `<h1>`; reveal `<h1>` | 36px | the priority-card digit (~11 arcmin @92ppi, ~20 @51ppi) | **verified pass** on the 24" monitor, 2026-08-19 |
| Progress-row and reveal-row player names | 24px | the hand-strip pip and the board row label (~7.6 arcmin @92ppi, ~14 @51ppi) | **verified pass**, recorded as marginal-but-readable on the 24" |
| Reveal species names; progress `Entered` / `Not yet`; collision and feasibility lines | 18px | the Mega marker (~5.7 arcmin @92ppi, ~10 @51ppi) | **verified pass**, recorded as marginal-but-readable on the 24" |
| Ban-board column header `Pass {n}` | 14px | the `R{n}` axis label | covered by assertion 5's 14px floor |

**This phase therefore introduces no new legibility risk.** It introduces new *surfaces* at sizes
already physically verified on the harder of the two screens the spec models. That is a claim the
next pass can falsify, not an assumption.

**Physical check, mandatory and not substitutable.** Extends the passes `02-UI-SPEC` and
`03-UI-SPEC` require, with a fourth, using the same setup — 8 players, `standard` density, 3 metres
from a 1080p screen — and it doubles as the secrecy check:

4. **The ban stage.** Configure 8 players, `blind`, 2 bans each.
   a. Stand 3 metres back from the **locked** state and read aloud whose turn it is, the progress
      count, and which players show `Entered`. **Confirm you can name no Pokémon from the screen.**
   b. Enter one player's bans, then trigger each of the three discard paths in turn — the
      `Hide these bans` button, an alt-tab away and back, and a browser Back followed by Forward.
      **Confirm each lands on the locked state with nothing retained and the same notice.**
   c. Reveal, then stand 3 metres back and read every attributed ban aloud, plus any collision line.
   d. Repeat (a) and (c) in `snake` with the ban board on screen.

   **Record the screen's physical size and the result per surface.** A failure at 18px is a finding
   about `--text-body` on a shared screen — not a licence to introduce a fifth font size. The

## Interaction & Accessibility

Phase 1's, Phase 2's and Phase 3's tables apply in full. These are the additions this phase forces.

| Rule | Requirement |
|------|-------------|
| **The announce-vs-focus rule still holds** | `03-UI-SPEC` records, unresolved, that a polite announcement queued alongside a focus move is routinely preempted (`SplitPanes.tsx:146-167`). Nothing in this phase depends on the answer: every announcement in §The Live-Region Contract is *also* carried by persistent on-screen text — the progress count, the discard notice and the reveal are all rendered, not merely spoken. |
| **Focus on entering the entry surface** | To the entry surface's `<h1 tabindex="-1">`, which names whose bans these are. **Not** to the typeahead: the one fact that must never be got wrong is *which player* is being entered, and an auto-focused input announces the field, not the heading. The typeahead is the first tab stop after it. |
| **Focus on every exit from entry** | To the locked state's primary action (`Enter {playerName}'s bans` / `Reveal bans`). One target for all four exits — lock, `Hide these bans`, tab-hide, bfcache restore — because the control that was focused no longer exists in any of them. Never left on a detached node, never dropped to `<body>`. |
| **Focus after the reveal** | To the reveal's `<h1 tabindex="-1">`, **not** to `Start draft`. D-23 exists so the group reads the reveal before the screen changes under them; landing focus on the button that changes it would put the draft one keystroke away from a screen nobody has read. |
| **Focus after a snake ban** | To the pool cell that now occupies the removed cell's grid position — the shipped post-pick rule, unchanged, because a snake ban *is* a pick as far as the grid is concerned. |
| **Focus after an undo confirm** | `Dialog` returns focus to the element that opened it. In blind that is the top bar's undo button, which still exists — no override needed. In snake the undo may return a species to the grid; focus stays on the undo button, unchanged from Phase 2. |
| **`aria-disabled`, never native `disabled`, on every inert cell and blocked action** | A natively disabled control is not focusable, so its reason is unreachable by keyboard. This is why `Start draft`, the inert ban cells, the inert typeahead options and the not-yet-complete `Lock in` button all use `aria-disabled` with `aria-describedby` or a reason in the accessible name. **The one exception is the duplicate-policy control's disabled `Re-ban` member**, which keeps `SegmentedControl`'s shipped both-attributes pattern — a natively disabled radio is still in the accessibility tree and still announces its name (`SegmentedControl.tsx:76-92`). |
| **Inert ARIA is always shed** | Every inert state here — a publicly-banned cell after an undo, the duplicate-policy control when the mode changes to blind, the `Lock in` button once `{m}` are chosen, a typeahead option after an unban — removes `aria-disabled` the moment its condition lifts. WR-04; this phase adds four consumers. |
| **No roving tabindex on any new surface** | The progress board is ≤ 8 static rows and the reveal is a list of non-interactive chips; neither is a *large uniform interactive* set, which is what `use-roving-tabindex` exists for. The pool grid inside the entry surface keeps the hook it already has. Stated explicitly so the hook is not wired out of habit. |
| **`BanBoard` semantics** | `<div>`s in a CSS grid, matching `BoardGrid` exactly. **No `role="grid"`, no `role="row"`, no `role="gridcell"`** — the shipped board does not invent them and a second, differently-shaped board would be a second accessibility model for one visual pattern. The blind progress board's rows carry the accessible sentence `{playerName} — Entered` / `{playerName} — not yet entered`. |
| **Reveal row summary** | One accessible sentence per row: `{playerName} banned {name}, {name} and {name}.` The chips are decorative to assistive technology given that sentence — `MonChip`'s `alt` inversion rule applies as shipped. |
| **Target size** | Every new control ≥ `--target-min` in both axes: `Enter {playerName}'s bans`, `Reveal bans`, `Lock in {playerName}'s bans`, `Hide these bans`, `Start draft`, `Bans per player`, every duplicate-policy label. Ban-board cells and progress rows are **not** interactive and are exempt, exactly as board chips are. |
| **Motion budget — one phase-specific rule** | Unchanged: colour and border transitions only, ≤ 120ms. **The transition from the entry surface into the locked state must not be animated at any duration** (S9). A fade, a slide or a cross-dissolve would leave the roster and the selection readable for the length of the animation, which is a leak measured in frames rather than a preference. This is the first hard motion prohibition in the project and it is a security property, not a taste. |
| **Zoom and responsive** | Unchanged. Snake's panes stack below 1280px via the shipped media query. The locked, entry and reveal screens are `.app-shell` and single-column, so they inherit the config screen's behaviour with no second code path. |
| **Read-only tabs** | The whole ban stage renders inside the existing `inert` shell gate. A read-only tab can never reach the entry surface, because the only route to it is a control inside that gate. No new ownership machinery. |

### Pure-core boundary — still a UI rule

No component owns a rule. The serpentine order, whose turn it is, which pass is current, who has
submitted, the public-ban set, the collision set, the post-reveal feasibility verdict and the ban
stage's own state machine are all **selectors and pure functions in `src/core/`**, beside
`selectCardTurn` and `selectStartingOrder`. `npm run check:pure` fails the build on any DOM, clock,
randomness, network, storage or `preact` import there.

Four things in this phase are UI-layer by necessity and are named so nobody has to guess:

1. The focus handoffs above — DOM operations.
2. The `pageshow` / `visibilitychange` listeners — `src/adapters/`, mirroring the two working
   handlers at `tab-lock.ts:624-636` and `persistence.ts:438-445`.
3. The in-progress selection during blind entry — deliberately **component state that dies with the
   component** (D-18). Nothing half-private survives a restore, which means there is no state for a
   leak bug to live in.
4. Which surface to render, which reads the stage selector and branches — it does not compute it.

If a surface here seems to need the UI to decide a rule, the selector is missing. Add the selector.
