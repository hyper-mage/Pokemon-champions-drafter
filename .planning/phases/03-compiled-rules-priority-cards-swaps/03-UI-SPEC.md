# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This document is a continuation of `02-UI-SPEC.md`, which is itself a continuation of
`01-UI-SPEC.md`.** The spacing scale, the four-size two-weight type scale, the colour roles and
their reservations, the density contract, the two-pane geometry, the confirm pattern, and the
interaction and accessibility baseline all remain binding in full. This document states only what
is **added**, what is **amended**, and one place where it **declines part of a locked decision's
reach**. Where this document is silent, Phase 2's contract governs; where that is silent, Phase 1's
does.

**Scope — the six surfaces this phase renders or reshapes:**

1. The config screen's compiled-schedule preview and its reorder control (RULE-06).
2. The config screen's Mega-forme ban surface and the new `Swaps` group (RULE-04, SWAP-01, SWAP-03).
3. The RULE-09 feasibility block and three other new gate reasons.
4. The board pane's typed round headers and per-player hand strips (CARD-02, CARD-07).
5. The card-play step (CARD-01, CARD-03…08).
6. The mid-draft swap flow and the dedicated swap rounds (SWAP-02, SWAP-04…07).

**Binding upstream:** `03-CONTEXT.md` (D-01…D-32, all locked), `03-RESEARCH.md` (measured layout
budget, measured roster figures, existing-code inventory), `02-UI-SPEC.md` (approved),
`01-UI-SPEC.md` (approved), `CLAUDE.md` §Conventions / §Architecture / §Styling / §Copy,
`.planning/REQUIREMENTS.md` (DRFT-04, RULE-01…06, RULE-09, CARD-01…08, SWAP-01…07),
`.planning/ROADMAP.md` §Phase 3.

## Amendments to Phase 2's Contract

Three Phase 2 contracts are deliberately broken by this phase. Each names the exact text it
replaces. **Every stylesheet or source comment that states the superseded rule must be corrected
in the same change that breaks it** — a stale contract comment is worse than no comment, because
the next reader trusts it (`02-UI-SPEC` §Amendments, `03-CONTEXT` §Specific Ideas).

### Amendment 1 — board cells become interactive, under one narrow condition (supersedes `02-UI-SPEC` §7)

**Removed text:**

> **Board cells are not interactive**, in this phase or any planned one. Undo is a top-bar
> button. Forty-eight tiny retract buttons on a shared screen is a misclick surface, and the one
> thing a no-confirm pick cannot afford is a second easy way to lose one.

**Replacement contract (D-27):** a board cell is a swap-target button **only** when all four hold:

1. The tournament's `swapBudget` is greater than 0.
2. The cell belongs to the player currently on the clock (mid-draft) or on the swap-round clock.
3. That player has at least one swap remaining.
4. The cell is filled.

Every other cell stays a non-interactive `MonChip`, exactly as today. The reasoning that produced
the original rule is preserved rather than overturned: at 8 players the interactive set is at most
`rounds − 1` cells out of 48, not 48 — and **a swap confirms** (§Confirmation Dialogs), unlike a
pick. The misclick surface the original rule protected against is a no-confirm surface, and this
one is not.

At the default `swapBudget` of 0 the board is byte-identically non-interactive, so a tournament
that never enables swaps sees no change at all.

### Amendment 2 — the undo label (supersedes `02-UI-SPEC` §Copywriting, Draft screen row `Undo`)

**Removed text:** `Undo last pick`

**Replacement copy (D-20):** `Undo last move`.

D-20 makes undo one stack spanning picks, cards, swaps and passes. A button labelled
`Undo last pick` that removes a priority card is wrong on the shared screen where it is read
aloud. `move` covers all four and stays plain English; `action` was rejected because it leaks the
log's internal vocabulary into copy the room reads. The disabled state, the styling, the
`Ctrl+Z` / `Cmd+Z` routing and the round-boundary confirm gate are all unchanged.

### Amendment 3 — pane-state availability extends to the card phase (extends `02-UI-SPEC` §A tension in the locked set)

The scoping table gains one row. The mechanism is unchanged — an unavailable expand is
**rendered inert with a visible reason**, never omitted, and the persisted value is silently
coerced.

| Screen state | States available | Coercion |
|--------------|-----------------|----------|
| Draft screen, **card play in progress** | `split` only | A stored `pool-full` **or** `board-full` coerces to `split`, silently |
| Draft screen, picking in progress | `split`, `board-full` (unchanged) | stored `pool-full` → `split` (unchanged) |
| Draft screen, **swap round in progress** | `split` only | as card play |
| Completed-tournament screen | `split`, `pool-full`, `board-full` (unchanged) | none |

`board-full` is unavailable during card play and during a swap round for one reason: the pool
pane holds the only control that can play a card or choose a swap target, and a state that hides
the only available action is not a preference. Its expand button renders inert with the reason
`Available once the round's cards are played` / `Available once the swap round ends`, through
`SplitPanes`' existing `PaneAvailability` union — which already makes "unavailable with no reason
given" unrepresentable (`SplitPanes.tsx:101`, `:262`).

## A locked decision whose reach this spec declines, recorded as such

**D-12's "two-forme affordance on a cell" is not built. The Mega-forme ban grid renders one cell
per forme — 76 cells — and every cell is an ordinary single-toggle cell.**

D-12 is honoured in full on its substance: the surface is a Mega-mode `PoolGrid` plus the
`TypeaheadField` + `BanChipList` pair D-10 built, and both formes of a dual-Mega species are
independently bannable. What is declined is its prediction that this requires a new two-toggle
cell affordance. Five reasons, strongest first:

1. **A pool cell is one `<button>`.** `02-UI-SPEC` §3 and §Accessibility fix that: the whole cell
   is the target, `aria-pressed` carries the ban state, and the roving tabindex model is one cell,
   one stop. Two toggles inside one cell breaks all three at once.
2. **Identity is already per forme.** D-09 keys bans on `megaFormes[].id`. One cell per forme is
   the shape the data has; merging two ids into one cell creates a second representation of a
   thing that already has one.
3. **A forme's own types and stats differ from its base species'.** Measured:
   `Charizard-Mega-X` is Fire/Dragon, `Charizard-Mega-Y` is Fire/Flying, and their base stats
   differ. A merged cell must render one of them and hide the other — exactly the information the
   host is deciding on.
4. **Every forme sprite exists.** `public/data/sprite-meta.json` carries 311 `byRosterId` entries
   = 235 draftable + 76 formes, all 76 resolved, zero missing (measured, `03-RESEARCH`).
5. **It costs nothing.** Banning both of Charizard's formes is two clicks either way.

Cost, stated: the grid holds 76 cells rather than 74, and Charizard and Raichu each appear twice.
That is what per-forme banning means, and the count line says so.

Recorded here rather than absorbed silently, following the precedent `02-UI-SPEC` set with its own
`pool-full` resolution. The planner should read it as a spec resolution, not as a free choice.

## Design System

Unchanged. Restated because the constraint is absolute and this phase adds five new components.

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-built Preact components under `src/ui/` |
| Icon library | none. **This phase needs zero glyphs.** The Mega marker is the word `Mega`; a priority card is a digit; the reorder controls are the words `Move up` / `Move down`. No arrow character, no icon file, no icon font, no SVG. |
| Font | system stack, no webfont (Phase 1 §Typography) |

**Hard constraint — do not violate.** Runtime `dependencies` is exactly `preact@10.29.8` and
`@preact/signals@2.10.1`, both exact-pinned. No CSS framework, no CSS-in-JS runtime, no component
registry, no icon package, no drag-and-drop library (which is why D-14's reorder is buttons), no
matching library (the CARD-04 check is ~25 hand-written lines of Hall's condition). A third
runtime dependency is a constraint violation, not a trade-off.

**Styling mechanism:** unchanged. `src/ui/tokens.css` declares values on `:root` and styles
nothing. One stylesheet per component, beside it, consuming tokens only. No raw hex. No raw px for
anything the token table covers. The two sanctioned raw lengths remain the board label column
(`--board-label-w: 176px`, declared in `BoardGrid.css`) and the pane split ratio (`60fr 40fr`);
this phase adds none.

`npm run check:nohtml` forbids `innerHTML` and `dangerouslySetInnerHTML` anywhere under `src/`.
Card pips, Mega markers, hand strips and swap chips are elements, not markup strings.

| `--space-1` | 4px | Gap between hand-strip pips; gap between a round header's `R{n}` and its Mega marker; Mega-marker padding-x |
| `--space-2` | 8px | Card-face padding-y; gap between card faces in a hand; schedule-row inner gap |
| `--space-3` | 16px | Card-face padding-x; gap between played-card entries; card-panel padding |
| `--space-4` | 24px | Gap between the card panel's blocks; gap between schedule preview and the field above it |
| `--space-5` | 32px | Gap between the new config sub-sections inside `Mega rules` |
| `--space-6` | 48px | unchanged |
| `--space-7` | 64px | unchanged |

### Size tokens — one added

| Token | Value | Notes |
|-------|-------|-------|
| `--sprite-lg` | 96px (density-scoped) | unchanged. Also the forme sprite in the Mega-ban grid. |
| `--sprite-sm` | 48px | unchanged |
| `--cell-min` | 128px (density-scoped) | unchanged |
| `--cell-h` | 188px (density-scoped) | unchanged |
| `--target-min` | 44px | unchanged. Every new control clears it — see §Interaction. |
| `--radius` | 8px | unchanged. Card faces and Mega markers use it. |
| `--border-w` | 2px | unchanged |
| `--hairline-w` | 1px | unchanged. Card-face border. |
| `--pill-h` | 24px | unchanged, and **not** reused by the Mega marker — an 18px line box does not fit a 24px pill. The marker sizes to its content. |
| **`--card-min`** | **64px** | **NEW.** The square minimum of a priority-card face, in both the playable hand and the played-this-round row. |

**Why `--card-min` is a token and not a one-off length.** Two independent consumers (the hand and
the played row) must stay in lockstep — a played `3` and a holdable `3` that are different sizes
read as different objects on a shared screen. More decisively, DRFT-14 makes the card face an
**acceptance criterion** (§DRFT-14, assertion 11), and a value an assertion cites must be a named
token so the assertion can be regressed, exactly as `--sprite-lg` is. It is a multiple of 4 and it
exceeds `--target-min` in both axes.

**Card-face arithmetic**, stated so the executor can verify a rendered card rather than trust the
number:

```
height  8 pad + 41 digit (--text-display 36 × 1.15) + 8 pad = 57  → --card-min (64) governs
width  16 pad + ~20 digit + 16 pad                          = 52  → --card-min (64) governs
```

## Typography

**Unchanged in every respect.** Four sizes, two weights (400, 600), no 500, no 700, no italics.
No fifth size is introduced by any surface in this phase.

| Token | Value | New usage in this phase |
|-------|-------|------------------------|
| `--text-body` | 400 18px / 1.5 | The Mega marker in a board round header; the turn banner's phase line; card-panel body copy and helper lines; schedule-preview row text; the pool's round-restriction statement; the swap-slot statement |
| `--text-label` | 600 14px / 1.4 | Round header `R{n}` (unchanged); pool count (unchanged); config helper text; ban-grid count |
| `--text-heading` | 600 24px / 1.25 | **Hand-strip pips**; **the player name under a played card**; card-panel heading; config sub-section headings; board row label (unchanged) |
| `--text-display` | 600 36px / 1.15 | **The digit on a card face**, played or playable; turn banner (unchanged) |

**Three board-legibility floors, and why each sits where it does.**

- The **card digit** takes `--text-display`. It is the entire information content of the surface
  the room is watching, and the largest token in the scale is the correct one.
- **Hand-strip pips** and **played-card player names** take `--text-heading` (24px), matching the
  board row label. Player identity and card value are the two things read at a distance, and
  giving them one size makes the label cell read as one block.
- The **Mega marker** takes `--text-body` (18px), which is the same floor `02-UI-SPEC` assertion 2
  set for board chip names. It states a round's kind — board text that carries state — so it sits
  at the floor, not at the 14px `R{n}` axis label beside it. That the marker is visually larger
  than the round number it annotates is deliberate: the marker is the information, the number is
  the axis.

## Color

**Unchanged. No token is added, no reservation is widened, and no new destructive surface exists.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0F1216` | unchanged |
| Secondary (30%) | `#1A1F26` | unchanged, plus the card panel and the schedule preview rows |
| Raised | `#232A33` | unchanged, plus the Mega marker's fill |
| Accent (10%) | `#FFCB05` | **unchanged reserved list — nothing in this phase is added to it** |
| Destructive | `#FF7A70` | **unchanged reserved list — this phase adds no destructive surface** |
| Type palette | 18 hues | unchanged — pool-card type pills and type filter controls only. The Mega-ban grid's forme cells render the **forme's** types, which is still a pool-card type pill and still inside the reservation. |

**Accent stays at exactly three uses.** The card-play step and the swap surfaces deliberately have
**no accent-filled button**, for the same reason the draft screen has none: playing a card is the
action and the card faces are the target; choosing a swap target is the action and the board cell
and pool cell are the targets. Card faces and the `Pass this swap` control are **secondary** —
transparent fill, `--hairline-w solid var(--color-border-strong)`, `--color-text` label.

The resolved pick order in the turn banner is **not** accent-marked, even though it names the
player about to pick. The on-the-clock signal is already the banner's own accent rule and the
board's `board__cell--next` border; adding a third element to that reservation would dilute the
one signal that must never be missed. The order strip is monochrome: positions in
`--color-text-muted`, names in `--color-text`.

**Destructive stays at exactly three uses** — the storage-unavailable screen, the import-overwrite
confirm, the abandon-draft confirm. A swap is not destructive: the swapped-out Pokémon returns to
the pool for everyone (D-26) and undo reverses it. A pass is not destructive. The RULE-09 block is
not destructive — nothing is lost; it is a not-yet state, and its sentence renders in
`--color-text`.

### Colour is never the only signal — new rows

| State | Colour signal | Non-colour signal |
|-------|--------------|-------------------|
| **A Mega round, in the board header** | none | the word `Mega` in a bordered marker beneath `R{n}`, plus a visually-hidden ` round` suffix so it reads `Mega round` |
| **A spent priority card (hand strip)** | none | `opacity: 0.45` **and** `text-decoration: line-through` on the digit — the pairing the config ban grid already uses; `opacity` alone is the disabled convention and would be ambiguous |
| **An unplayable card (D-21)** | none | `aria-disabled="true"` + `opacity: 0.45` + `line-through`, plus a reason in the accessible name and one visible line beneath the hand |
| **The inert Mega filter during a Mega round (D-16)** | `opacity: 0.45` | `aria-disabled="true"` + the visible reason beside the control, **shed when the round ends** (WR-04) |
| **An inert reorder button** | `opacity: 0.45` | `aria-disabled="true"` + the reason carried in the accessible name + one visible rule line under the list |
| **A swappable board cell** | none | it is a `<button>`; every other cell is not. Hover raises the fill, focus draws the ring, and the pool pane states which slot is armed. |
| **A round's slot type on the board** | none | the column header's marker — the slot inherits its type from the column it sits under, which is exactly why D-15 put the marker there |

## Layout Budget — the measured numbers this phase spends from

`03-CONTEXT` §Specific Ideas requires the board's width budget be **checked, not assumed**. Two
figures are in circulation and they do not disagree; they are measured at different points.

| Figure | Value | Source |
|--------|-------|--------|
| Board pane, 40% of a bare 1920px | 768px | `03-RESEARCH` §Layout Budget |
| Board pane, 40% **after** shell padding and the pane gap | 739px | `02-UI-SPEC` §Two-Pane Geometry |
| Label column | **176px** | `BoardGrid.css:54`, `--board-label-w` |
| Per round cell, **before** the six inter-column gaps | ~99px | `03-RESEARCH` |
| Per round cell, **after** the six `--space-2` gaps | **86px** | `02-UI-SPEC`, and what the shipped grid actually renders |

**86px is the binding figure.** `03-CONTEXT`'s "roughly 108px" is superseded, `03-RESEARCH`'s 99px
is the same measurement before gaps, and 86px is what a round cell is on screen. Design to 86px;
it is stricter than both.

### The two budgets this phase spends from — and both fit

**D-15, Mega markers, spend from the 86px round header:**

```
R{n}     --text-label 14 × 1.4                     = 20px tall
gap      --space-1                                 =  4px
marker   `Mega` at --text-body 18 × 1.5            = 27px tall
                                                     51px header cell (was 24px)
marker width  ~38px of text + --space-1 × 2 padding = 46px  ≤ 86px  ✓ (40px slack)
```

Board height becomes ≈ 683px against ~851px available at 1080p (`02-UI-SPEC` §Board height at 8
players: 656px + 27px). **The 8-player board still fits the split board pane with no internal
vertical scroll.**

**Open rounds reserve the marker line.** A round with no marker renders an empty span with the
same `min-height`, so reordering the schedule never shifts the grid and the two panes never fall
out of alignment. This is the reserved-chrome-height rule plan 02-09 established after a missing
`min-height` misaligned the panes by a full target height.

**D-24, hand strips, spend from the 176px label column:**

```
name    --text-heading 24 × 1.25                   = 30px
gap     --space-1                                  =  4px
pips    --text-heading 24 × 1.25                   = 30px
                                                     64px label cell
```

`.board__cell` already carries `min-height: calc(var(--sprite-sm) + var(--space-3))` = **64px**.
**The hand strip therefore costs zero additional row height** — an assertion the executor can
check rather than a hope.

```
pip width  6 digits at 24 × ~0.58em  ≈ 6 × 14 = 84px
gaps       5 × --space-1                      = 20px
                                               104px  ≤ 176px  ✓ (72px slack)
```

`03-RESEARCH` A6 expected ~95px of pips leaving ~75px for the name and predicted the strip must
stack below the name. **Stacking is confirmed as the design**, and the width is more comfortable
than predicted for one reason: a pip is a **bare digit with no box, no fill and no padding** —
separation is carried by the `--space-1` gap alone. The name therefore keeps the full 176px on its
own line, which is more name width than it has today (where it shares a centred single-line cell).

### 2. The compiled schedule preview and its reorder (RULE-02, RULE-06, D-13, D-14)

**Sub-section heading:** `Round schedule`. Helper line beneath it, `--text-label`,
`--color-text-muted`: `The draft runs these rounds in this order. Reorder them before you start;
the schedule is fixed once the draft begins.`

**Rows.** One row per round, `config.rounds` of them, never a literal 6. Each row is a `<li>` in
an `<ol>`, `--color-surface` fill, `--radius`, `--space-3` padding, `--space-2` between rows:

- Row text at `--text-body`: `Round {n} — Mega` or `Round {n} — Open` (D-14's own wording).
- Two buttons per row, visible labels `Move up` and `Move down`, each `min-height` and
  `min-width` of `--target-min`.

**Accessible names carry the destination, which is what makes the focus move safe:**

| Case | Accessible name |
|------|----------------|
| Movable up | `Move up to round {n−1}` |
| Movable down | `Move down to round {n+1}` |
| At the top | `Move up — round 1 is already first` |
| At the bottom | `Move down — round {rounds} is already last` |
| Neighbour is the same kind | `Move up — round {n−1} is already a Mega round` (and the open equivalent) |

Every name **contains** its visible label as a substring (`Move up` / `Move down`), which is what
SC 2.5.3 Label in Name requires.

**Inert, not removed.** A button whose move would change nothing takes `aria-disabled="true"`,
stays focusable, gets `opacity: 0.45`, and its click handler returns early. It **sheds the inert
ARIA the moment the condition lifts** (WR-04). Per-button visible reasons were rejected — twelve
reason lines on a config form is noise — so the rule is stated once, visibly, beneath the list at
`--text-label` `--color-text-muted`: `A move that would not change the schedule is unavailable.`
This does not repeat plan 02-09's mistake: that gap was **omission** (an empty chrome slot read as
a broken render), and nothing here is omitted.

**When there is nothing to reorder, the controls are not rendered at all.** When every round has
the same kind — `megasRequiredPerTeam` of 0 or of `rounds` — the preview is a read-only list plus
one line: `Every round is open, so there is nothing to reorder.` / `Every round is a Mega round,
so there is nothing to reorder.` This follows the shipped precedent for a wholly void affordance
(`Clear the banlist` and `Clear filters` are both "not rendered when nothing is active"), and it
avoids a list of twelve permanently inert buttons.

**Focus follows the moved round.** After a successful move, focus moves to the same-named button
in the row the kind moved to. Leaving focus on the pressed button would make a second press
reverse the first, which makes walking a Mega round from position 6 to position 1 impossible by
keyboard.

**This move is announced *and* the state is carried by the newly focused control's own name** —
see §Interaction, the announce-vs-focus rule. Nothing here exists only in the announcement.

**Reorder is config-time form state and dispatches nothing** (D-13). It resolves into the single
`schedule/compiled` action at Start, exactly as the banlist resolves into `pool/built`.

### 3. Mega-forme bans (RULE-04, D-09, D-10, D-12)

**Sub-section heading:** `Mega-forme bans`. Helper at `--text-label` `--color-text-muted`:
`A banned forme cannot be used this tournament. A species with no forme left simply stays out of
the Mega rounds — it is still draftable in an open round.`

That second sentence is not decoration. D-10 makes "Charizard pinned to X with X banned" a normal
outcome with no error state, and without the sentence a host reads a missing species as a bug.

- **`TypeaheadField`**, visually-hidden label `Ban a Mega forme by name`, placeholder `Name`. Same
  normalized substring predicate as every other search in the app — one predicate, one module.
- **`BanChipList`**, chip accessible name `Remove {formeName} from the Mega-forme banlist`,
  `Clear the Mega-forme banlist` after it with its own confirm, not rendered when the list is
  empty.
- **A Mega-mode `PoolGrid`** in a capped scroll region (`max-height: 60vh; overflow-y: auto`),
  rendering **76 forme cells** (see §A locked decision whose reach this spec declines). Each cell
  is a `<button aria-pressed={banned}>` showing the forme's sprite, its own name
  (`Charizard-Mega-X`), its own type pills and its own stats at the current density. Banned
  treatment is the shipped pairing: `opacity: 0.45` **and** `line-through` on the name.
- Count line: `{n} of {total} Mega formes banned`.
- **The `Mega capability` filter control is inert here**, reason `This list is Mega formes only`,
  shed if the surface is ever reused elsewhere. Search and the 18 type filters stay live and are
  genuinely useful — the forme's own types differ from its base species'.

Identity is `megaFormes[].id` throughout. **Never `includes('mega')`** — it returns Meganium — and
never string surgery on a name: `Meowstic-M-Mega` carries `battleOnly: "Meowstic"` with no `-M`.

### 4. The `Swaps` config group (SWAP-01, SWAP-03, D-29, D-30)

Two `NumericField`s, both free inputs with **no clamping** — the feasibility gate is the one
authority on what is satisfiable, and both inherit the `number | null` rule that keeps an empty
field from folding to `NaN`.

| Control | Default | Helper |
|---------|---------|--------|
| `Swap budget per player` | `0` | `Each player may swap this many times in total, mid-draft or in a swap round. 0 means no swaps.` |
| `Swap rounds after the draft` | `0` | `Each swap round gives every player one chance to swap or pass. 0 means the draft ends with the last pick.` |

Both default to 0, matching `megasRequiredPerTeam`'s precedent: a feature the host has not asked
for stays invisible, and at `swapBudget: 0` the board is non-interactive and nothing in Phase 2's

sentence so the host does not look for a second allowance.

### 5. Feasibility additions (RULE-09, D-11, D-32)

**This spec does not restate the precedence order.** `02-UI-SPEC`'s 7-item list went stale and
`03-CONTEXT` records it as such; a third copy is a third thing that can drift. The order lives in
`feasibility.ts`'s `PRECEDENCE` and is documented in `02-RESEARCH`. The four additions and their
**neighbours** are named instead:

| Code | Severity | Sits beside | Copy |
|------|----------|-------------|------|
| `notEnoughMegas` — **re-measured** | blocking | unchanged position | see below |
| `swapBudgetNotAnInteger` | blocking | `megasRequiredNotAnInteger` | `Swap budget needs a whole number. Enter 0 for no swaps.` |
| `swapRoundsNotAnInteger` | blocking | `megasRequiredNotAnInteger` | `Swap rounds needs a whole number. Enter 0 to end the draft with the last pick.` |
| `swapRoundsOnExactPool` | **warning** | `poolExactlyMinimum` | `Warning — the pool is exactly {n}, so it is empty when the last pick lands. The first player to swap can only take what someone else drops.` |

**The RULE-09 blocker, with the arithmetic and the right ban list named:**

```
Not enough Pokémon can Mega. {p} players × {m} Mega rounds needs {x};
{y} can still Mega after {b} species bans and {f} Mega-forme bans.
Lower the Mega requirement, or unban a Mega forme.
```

This replaces `Not enough Mega-capable Pokémon. {p} players × {n} Megas needs {x}; {y} are
draftable after {b} bans.` Three things change and each is load-bearing:

1. **"can Mega" rather than "Mega-capable."** After D-09/D-10 a species can be Mega-capable and
   still have no legal forme. The old wording describes a count the gate no longer measures.
2. **Both ban lists appear, with their own counts.** `03-RESEARCH` proves this gate can only fire
   because of Mega-forme bans at 4–8 players (`8 × 6 = 48 ≤ 74` pre-ban), so a host sent to the
   species banlist is sent to the wrong screen.
3. **The next action names unbanning a forme**, because that is the action that actually moves
   the number.

`{m}` is `Mega rounds`, not `Megas`, because the compiler has made them the same thing and the
schedule preview two sub-sections above uses that word.

**Severity is unchanged in kind:** blocking disables `Start draft` via `aria-disabled` on a
focusable button with `aria-describedby` pointing at the reason; warning does not. The
`Warning — ` text prefix remains the non-colour distinction.

### 6. Board pane — typed round headers (CARD-02, D-15)

Each `board__round` header cell renders two lines:

```
line 1   R{n}            --text-label, --color-text-muted        (unchanged)
line 2   Mega            --text-body, --color-text, in a marker  (Mega rounds)
line 2   (reserved)      empty span, same min-height             (open rounds)
```

The marker: `--color-surface-raised` fill, `--radius`, `padding: 0 var(--space-1)`,
`--color-text` ink. It carries a visually-hidden ` round` suffix so it reads `Mega round` rather
than `Mega`. No ARIA is invented — the header cells are `<div>`s with no programmatic association
to the grid today, and adding a fake one would be worse than the text.

`Mega` is the widest string the header must hold (~46px inside 86px). A longer word does not fit,
which is why the marker is a word and not a sentence — the sentence lives in the pool header,
where there is room for it.

**CARD-02 is satisfied twice over:** the config preview shows the whole schedule before Start, and
the board headers show it on screen throughout the card phase, above the columns of slots they
type.

### 7. Board pane — hand strips (CARD-07, D-24)

Each `board__label` cell stacks:

```
{player name}     --text-heading, ellipsised on one line (unchanged mechanism)
{hand strip}      six pips at --text-heading, --space-1 gaps
```

- A pip is a **bare digit**. No box, no fill, no border, no padding.
- Remaining: `--color-text`. Spent: `opacity: 0.45` **and** `text-decoration: line-through`.
- The strip is `aria-hidden="true"` and the containing element carries one accessible summary:
  `{name} holds 2, 5 and 6.` — six separate pip announcements would make every board traversal
  unbearable, and CARD-07 asks for the remaining cards, which is exactly what the sentence names.
- The strip renders whenever the tournament deals cards. **A migrated schema-2 document — picks
  present, no card ever played — renders no strips**, because it never dealt any and six unspent
  pips would be a lie about a draft that ran flat rounds.

Row height is unchanged at 64px (§Layout Budget). This is a checkable assertion, not an
expectation.

### 8. The card-play step (CARD-01, CARD-03…08, D-17…D-24)

**Where it lives.** The card panel replaces the pool pane's content while
`selectPhase(state) === 'cards'`. The board pane is untouched and stays beside it — the schedule
headers, every player's hand strip and the pick history are all on screen while cards are played,
which is what a room reading one screen needs. This reuses the precedent that the pool pane also
hosts `CompletedDraft`: it is the current-activity pane.

`board-full` is coerced to `split` for the duration (Amendment 3).

**Sticky head during the card phase:**

| Line | Copy |
|------|------|
| Turn banner (`--text-display`) | `Round {r} of {rounds} — {playerName} plays a card` |
| Phase line (`--text-body`) | `The lowest card picks first.` + when `players > rounds`, ` Ties go to whoever played the value first.` |

The tie clause is conditional because with `players ≤ rounds` the no-repeat rule makes a tie
impossible, and CARD-05 scopes its requirement to `players > rounds`. Conditional suffixes are
the shipped pattern (`. Filters cleared.`).

**Panel contents, top to bottom:**

1. **Heading** `Priority cards` at `--text-heading`.
2. **The hand on the clock.** A `<div role="group" aria-label="{playerName}'s cards">` holding one
   `CardFace` button per remaining value, ascending, `--space-2` gaps.
   - Playable: secondary styling, `--card-min` square, digit at `--text-display`.
   - **Unplayable (D-21):** `aria-disabled="true"`, focusable, `opacity: 0.45`, `line-through`,
     click returns early, accessible name `Play {v} — this would leave a later player with no
     legal card`. The inert ARIA is shed the moment the value becomes playable again (WR-04).
   - One visible line beneath the hand, rendered only when at least one card is inert:
     `A struck-through card would leave a later player with no legal card.` The signal named is a
     shape, not a colour.
   - **The deadlock escape.** When no card is playable at all — reachable only from an imported or
     hand-edited log — every card is offered and the panel states why:
     `The no-repeat rule is lifted for this play: every card left would otherwise strand a later
     player.`
   - **Playing a card does not confirm.** Phase 1 D-08's no-confirm posture holds, and D-20's undo
     is what makes it safe.
3. **Played this round.** One entry per card already down, **in play order**, `flex-wrap: wrap`,
   `--space-3` gaps. Each entry is a `CardFace` in its played state (same `--card-min`, same
   digit, no button) with the player's name beneath at `--text-heading`.
   Play order is also the tiebreak order (D-22), so the row *is* the tiebreak rule made visible —
   which is what CARD-05 asks for.
   Before the first card: `No cards are down yet. {playerName} plays first this round.`
4. **Still to play.** One line at `--text-body`: `Still to play: {name} · {name}` — the remaining
   rotation (D-18). Not rendered when the list is empty.

**Resolution and CARD-08.** When the last card lands, `order/resolved` fires, the panel unmounts
and picking begins. The resolved order is **not** shown in a transient panel that disappears — it
becomes the sticky head's phase line for the whole round:

| Line | Copy |
|------|------|
| Turn banner | `Round {r} of {rounds} — {playerName} picks` (unchanged from Phase 2) |
| Phase line | `Pick order: 1 {name} · 2 {name} · 3 {name}` |

It is therefore on screen **when picking begins and for as long as picking lasts**, at
`--text-body` in the always-visible sticky head. An explicit "start picking" click was rejected:
it costs a click per round, and it would put the screen's mode partly in the UI when `selectPhase`
is meant to be the one place it is decided.

The sticky head grows by one 27px line. Board height ≈ 683px against ~824px available — still no
internal board scroll at 1080p.

### 9. Pool pane during a Mega round (RULE-03, DRFT-09, D-16)

**The count line always uses the "of" form during a Mega round**, even with no user filter
active — because the pool *is* filtered:

```
{n} of {total} available
```

Beside it, at `--text-body` in `--color-text` (not muted — this is current state, not meta):

```
Round {r} is a Mega round — only Pokémon that can still Mega are shown.
```

That sentence is the answer to "why is the pool suddenly short", and it is why a short pool cannot
read as a broken render.

**The `Mega capability` segmented control renders inert** with the visible reason
`Round {r} is a Mega round` beside it, using the `— ` separator mechanism 02-12 settled (an
`aria-hidden` span, not generated content, with the reason constant excluding it so the string
table, the source constant and the test assertion stay one value). **It sheds its inert ARIA when
the round ends** — the WR-04 correction, restated because this is the second consumer of it.

Search and the 18 type filters stay live and compose with the round restriction (DRFT-09).
`MegaFilterMode` does **not** gain a fourth member; the restriction is a separate composed clause.

**New empty-state variants:**

| State | Copy |
|-------|------|
| Search matches nothing in a Mega round | heading `No Pokémon match` / body `Nothing in round {r}'s Mega-only pool matches "{query}".` / action `Clear the search` |
| Filters match nothing in a Mega round | heading `No Pokémon match` / body `No Pokémon that can still Mega is left in the pool with those types.` / action `Clear filters` |
| A Mega round with an empty offer | heading `No Pokémon can Mega here` / body `Round {r} is a Mega round, and nothing left in the pool can still Mega. Undo a pick to return one, or start a new tournament.` |

The last one is reachable only from an imported or hand-edited document — the RULE-09 gate is the
guarantee for documents this build creates. **The offer is never widened to fill it.** A fallback
that quietly allowed a non-Mega pick in a Mega round is the runtime validator the compiler exists
to remove, wearing a friendlier name.

### 10. Mid-draft swap (SWAP-02, SWAP-05, SWAP-06, D-25, D-26, D-27)

**Slot first, then pool.** Selecting the slot is what names the predicate, so the leftover pool is
correct on the first frame rather than by rejection afterwards.

**Step 1 — arm.** The on-the-clock player clicks one of their own filled board cells (Amendment 1).
The cell is a `<button>` with accessible name `Swap {species} out of round {r}`.

**Step 2 — the pool restates itself.** The pool pane header replaces its heading with
`Swapping {species} out of round {r}` at `--text-heading`, and the count line reads:

| Slot kind | Copy |
|-----------|------|
| Mega | `{n} of {total} available for this slot — round {r} is a Mega round, so only Pokémon that can still Mega are shown.` |
| Open | `{n} of {total} available for this slot — round {r} is an open round, so the whole leftover pool is shown.` |

**Both cases are stated, including the unfiltered one.** SWAP-06's real failure mode is a player
reading a short pool as a bug; the symmetric failure — assuming a long pool is unfiltered when it
is not — is closed by saying which case is in force every time.

A `Keep {species}` secondary button disarms without swapping.

**Step 3 — choose and confirm.** Clicking a pool cell opens the swap confirm (§Confirmation
Dialogs). A swap confirms; a pick does not. The asymmetry is deliberate: a pick fills an empty
slot and undo restores it exactly, while a swap changes a slot the room has been looking at for
several rounds and returns a Pokémon to the shared pool.

**Step 4 — the turn still ends with a pick** (D-25). The swap spends budget, never the turn. The
turn banner does not change and the board's next-slot marker does not move.

**Budget line.** While the player is on the clock and holds budget, the pool pane header carries
`{name} has {n} swaps left` at `--text-label` `--color-text-muted`. At zero the board cells are
simply not buttons and no line is rendered — a tournament with `swapBudget: 0` shows nothing about
swaps anywhere.

### 11. Swap rounds (SWAP-03, SWAP-04, SWAP-07, D-28…D-31)

Reached when every player holds `config.rounds` picks **and** `config.swapRounds > 0`.

**Sticky head:**

| Line | Copy |
|------|------|
| Turn banner | `Swap round {s} of {swapRounds} — {playerName} swaps or passes` |
| Phase line | `Swap order reverses round {rounds}.` — or, when that resolved order is missing (a migrated or imported document), `Swap order reverses the starting order.` |

Naming which source is in use is SWAP-04's actual requirement: the order must be **explicit**, and
a fallback that silently used a different source would not be.

**`SwapPanel`** occupies the pool pane until a slot is armed:

- Heading `Swap round {s} of {swapRounds}` at `--text-heading`.
- `{playerName} has {n} swaps left.` at `--text-body`.
- `Choose one of {playerName}'s slots to swap, or pass.` at `--text-body`.
- `Pass this swap` — secondary, `--target-min`, **no confirm** (nothing is lost; undo covers it).
- At zero remaining budget the slot cells are not interactive and the panel reads
  `{playerName} has no swaps left — pass to continue.`

Arming a slot switches the pool pane to exactly the surface §10 specifies. There is one swap flow,
not two.

**Two completion states (D-31), and the export gate.**

| State | What is on screen |
|-------|------------------|
| Picks complete, swap rounds pending | The swap-round surface. **No export panels, no completion checkpoint.** The panel carries `Teams are not final until the swap rounds finish. Exports open then.` |
| Tournament complete | `CompletedDraft`, the per-player export panels, and the PERS-06 checkpoint — unchanged from Phase 2 |

Nobody may copy a paste that is about to change. With `swapRounds: 0` the two states coincide and
every Phase 2 string and surface is byte-identical.

Turn banner at tournament complete: `Draft complete — {picks} picks, {teams} teams` — the existing
string, unchanged, so a swap-free tournament reads exactly as it does today.

### 12. Confirmation dialogs — three new sets

All three reuse `ConfirmDialog` over `Dialog`. No new mechanism: focus trap, Escape-to-safe,
return-focus and `tone` are already correct. Consequence sentence stating what changes **in
numbers**, then two buttons that each name a verb and its object, destructive/confirming first so
the safe one is the last thing focus reaches. Nothing is labelled `OK`, `Submit`, `Yes` or
`Cancel` alone.

| Action | Tone | Body copy | Confirm | Safe |
|--------|------|-----------|---------|------|
| Make a swap | `default` | `This spends one of {name}'s {n} swaps. {out} leaves round {r} and returns to the pool for everyone; {in} takes the slot.` | `Swap in {in}` | `Keep {out}` |
| Clear the Mega-forme banlist | `default` | `This clears all {n} Mega-forme bans at once. Every banned forme becomes legal again.` | `Clear the Mega-forme banlist` | `Keep the bans` |
| Undo across a resolved pick order | `default` | `This un-resolves round {r}'s pick order and takes {name}'s {v} back into their hand — {c} steps in total. The order everyone just read changes.` | `Undo the pick order` | `Keep the pick order` |

**All three are `default`-toned**, so the confirming button takes accent fill (reserved use 2 — a
modal is the current screen) and the safe button stays secondary. None of them loses data: a swap
is undoable and returns its Pokémon to the shared pool, a forme banlist can be retyped before any
tournament exists, and an undo is the mechanism that makes the whole draft safe.

The undo dialog's `{c}` is `RoundBoundaryCrossing.removedCount`, which is 2 here — `order/resolved`
plus the `cards/played` that triggered it are removed together as one step, because removing the
resolution alone would let the app immediately re-resolve. The dormant `removedCount > 1` clause
in `confirm-copy.ts` goes live for the first time.

## DRFT-14 as a Checkable Assertion — extended

`02-UI-SPEC` §DRFT-14 stands in full: eight assertions plus a mandatory two-pass physical check.
Four assertions are added. **Any one failing fails the phase.**

| # | Assertion | Measured where |
|---|-----------|---------------|
| 9 | A hand-strip pip renders at ≥ 24px | `--text-heading` on `.hand-strip__pip` |
| 10 | Any board text stating a round's kind renders at ≥ 18px | `--text-body` on the Mega marker. The `R{n}` axis label stays at 14px and is covered by assertion 5's 14px floor. |
| 11 | A card face measures ≥ 64px in both axes and its digit renders at ≥ 36px | `--card-min`, `--text-display` |
| 12 | Adding the hand strip does not increase board row height | label cell 30 + 4 + 30 = 64px against `.board__cell`'s existing 64px `min-height` |

### The three-metre question, stated honestly rather than asserted

`03-RESEARCH` records that whether six pips are legible at three metres could not be settled, and
this spec does not claim it is. The arithmetic, so the physical check has something to falsify:

| Surface | Size | On a 24" 1080p monitor (~92ppi) | On a 43" 1080p TV (~51ppi) |
|---------|------|--------------------------------|---------------------------|
| Card digit | 36px | ≈ 10mm → ~11 arcmin at 3m | ≈ 18mm → ~20 arcmin at 3m |
| Hand pip, board row label | 24px | ≈ 6.6mm → ~7.6 arcmin | ≈ 12mm → ~14 arcmin |
| Mega marker, phase line | 18px | ≈ 5mm → ~5.7 arcmin | ≈ 9mm → ~10 arcmin |

Comfortable reading wants roughly 16–20 arcmin; the acuity limit is about 5. **What this predicts:
every one of these passes on a TV-sized shared screen, and on a 24" monitor at three metres only
the card digit is comfortable while the pips and the marker are marginal.** That is a prediction,
not a result.

**Physical check, mandatory and not substitutable.** Extends the two-pass check `02-UI-SPEC`
already requires, using the same setup — 8 players, at least two rounds filled, `standard`
density, 3 metres from a 1080p screen — with a third pass:

3. **Card play.** Stand back during a card-play step and read aloud: the value on each card in the
   hand, the value and player of each card already down, and the six pips in two different board
   rows. Then read the Mega marker on each round header. **Record the screen's physical size and
   the result per surface.** If the pips fail on the tested screen, that is a finding about
   `--text-heading` on the board — not a licence to introduce a fifth font size. The remedies
   available inside this contract are the existing scale and the existing pane states.

## Interaction & Accessibility

Phase 1's and Phase 2's tables apply in full. These are the additions this phase forces.

| Rule | Requirement |
|------|-------------|
| **The announce-vs-focus rule** | **No information in this phase exists only in a live-region announcement that is committed in the same tick as a focus move.** `SplitPanes.tsx:146-167` records, as an open question needing a real screen reader, that a polite announcement queued alongside a focus move is routinely preempted. That finding is **not** resolved here and this spec does not contradict it. Instead every new surface is built so it does not depend on the answer: a reorder announces *and* the newly focused button's name states the destination; a resolved pick order announces *and* renders persistently in the phase line; a swap announces *and* the board cell and pool header both show the result. Announcements remain, because on transitions that move no focus they are the only signal a screen-reader user gets. |
| **Add these surfaces to the WR-02 screen-reader check** | The two expand transitions still owe a check with NVDA or VoiceOver. The reorder move and the card-resolution transition are the two new focus-moving announcements and must be checked in the same pass. Record the outcome in the component doc blocks either way. |
| **No roving tabindex on either new surface** | The hand is ≤ 6 buttons and the reorder list is ≤ 12; `use-roving-tabindex` exists to collapse a *large uniform* set into one stop (235 pool cells, 18 type pills), and `PlayerList` already sets the precedent that a form list of rows uses plain tab stops. Stated explicitly so the hook is not wired out of habit. |
| **Focus after a card is played** | The played card's button leaves the hand and the panel re-renders for the next player. Focus moves to the first playable card of the new hand. Never left on a detached node, never dropped to `<body>`. |
| **Focus after the round resolves** | The card panel unmounts entirely. Focus moves to the pool grid's first cell — the control the host activated no longer exists, and this is the same handoff `SplitPanes` performs when the button that was pressed is the one that disappears. |
| **Focus after a swap confirms** | `Dialog`'s default return-focus target is the element that opened it — here a pool cell that has just been removed from the pool. **The caller overrides the return target to the board cell that now holds the swapped-in species.** Without the override, focus falls to `<body>`. |
| **Focus after a reorder** | Moves to the same-named button in the row the kind moved to (§2). |
| **Swappable board cell** | A real `<button type="button">`. In `split` it measures 86 × 64px, and in `board-full` 275 × 64px — both clear `--target-min` in both axes with no extra padding. Accessible name `Swap {species} out of round {r}`; the sprite keeps `alt=""` because the name is on the button. |
| **Hand strip** | `aria-hidden` pips plus one accessible summary on the container: `{name} holds 2, 5 and 6.` |
| **Card faces** | Real buttons when playable or inert; plain elements in the played row. An inert card takes `aria-disabled="true"` and stays focusable — the reason is the whole point of rendering it. |
| **Reorder buttons** | `aria-disabled`, never native `disabled`, for the same reason `Start draft` uses it: a natively disabled button is not focusable, so its reason is unreachable by keyboard. |
| **Inert ARIA is always shed** | Every inert state in this phase — the Mega filter, an unplayable card, a reorder button, a pane expand — removes `aria-disabled` the moment its condition lifts. This is WR-04, and this phase adds four consumers of it. |
| **Target size** | Card face 64 × 64. Reorder buttons `--target-min` in both axes. `Pass this swap`, `Keep {species}`, and both new numeric fields at `--target-min`. Hand-strip pips are **not** interactive and are exempt, exactly as board chips were. |
| **Live regions** | Unchanged: one global `role="status" aria-live="polite"` at app root, plus a surface-owned `role="status"` where a message lives on screen (the feasibility reason). Nothing uses `assertive`. `announce` is a module-level signal; a test touching it resets it in `beforeEach`. |
| **`LiveRegion`'s byte-identical limitation** | Still not hit. Two consecutive `{name} plays {value}.` announcements cannot be identical: a value is spent once per player, so either the name or the value differs. Two consecutive swap announcements differ by species. The duplicate-name feasibility blocker keeps protecting every player-named string. |
| **Motion budget** | Unchanged. Colour and border transitions only, ≤ 120ms. **A phase change is not animated**, a reorder is not animated, and a card is not dealt or flipped. |
| **Zoom** | Unchanged. Below 1280px the panes stack; the card panel and the swap panel inherit that with no second code path. |

### Pure-core boundary — still a UI rule

No component owns a rule. The compiled schedule, a round's kind, a slot's kind, a hand, which
cards are playable, the resolved order, the swap predicate, the swap budget remaining, the
swap-round order, both completion states and the RULE-09 gate are all **selectors and pure
functions in `src/core/`**. `npm run check:pure` fails the build on any DOM, clock, randomness,
network, storage or `preact` import there.

Two things in this phase are UI-layer by necessity and are named so nobody has to guess: the
focus handoffs above (DOM operations), and the decision of *which* panel to render, which reads
`selectPhase` and branches — it does not compute the phase.

If a surface here seems to need the UI to decide a rule, the selector is missing. Add the selector.
