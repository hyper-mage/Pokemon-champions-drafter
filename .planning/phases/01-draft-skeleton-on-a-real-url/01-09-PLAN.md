  <action>
    src/adapters/tab-lock.ts is impure and lives in adapters. It must never be imported from
    src/core.

    Give every tab a session id from `crypto.randomUUID()` at module load. Open a
    `BroadcastChannel('champions-drafter')`. Define a small message protocol, all messages
    carrying `{ type, tabId, at }`:

      `claim`     — I am asserting ownership
      `heartbeat` — I still hold ownership, sent on an interval
      `takeover`  — I am taking ownership from whoever holds it
      `released`  — I am giving up ownership (sent on pagehide)
      `ping`      — is anyone holding ownership? (sent by a booting tab)
      `pong`      — yes, I am, and here is my tabId

    Claim protocol on boot: broadcast `ping`, then wait a short window (250ms is ample for
    a same-origin BroadcastChannel round trip). If no `pong` arrives, claim ownership,
    broadcast `claim`, and start the heartbeat. If a `pong` arrives, this tab is a
    secondary: it does not write, and it renders read-only.

    Heartbeat: the owner broadcasts `heartbeat` every 2000ms. Every secondary records
    `lastHeartbeatAt`. A secondary that has seen no heartbeat for 6000ms — three missed
    beats — marks the lock STALE. Do not auto-promote on a stale lock: the surviving tab
    still requires an explicit human click, because an auto-promote race between three tabs
    is a worse failure than an extra click. Stale changes only what the banner says.

    Takeover: `requestTakeover()` broadcasts `takeover` with this tab's id, claims ownership
    locally, and starts its own heartbeat. Any tab receiving a `takeover` naming a different
    tabId immediately demotes itself to secondary, stops its heartbeat, and stops writing.
    That is the handoff, and it must work in both directions: the tab that was demoted can
    take ownership back.

    A tab claiming or reclaiming ownership must reload the persisted document via
    `load()` before writing anything, and adopt it if its `generation` is higher than the
    generation this tab last wrote. Otherwise a tab that sat read-only for ten picks would
    take over and immediately write its stale in-memory copy back — which is precisely the
    clobber this whole mechanism exists to prevent.

    Release on `pagehide`: broadcast `released` so a surviving tab can claim promptly
    instead of waiting out the stale window.

    Handle the environment where `BroadcastChannel` is undefined: fall back to assuming sole
    ownership and log once. A missing BroadcastChannel must degrade to today's behaviour,
    never to a locked-out app.

    Then gate `save()` in src/adapters/persistence.ts on `isOwner()`. A secondary tab must
    never call `setItem` for the tournament key. This is the enforcement point — the banner
    is the explanation, the gate is the guarantee.

    Test what is testable without a browser: instantiate two lock modules against a fake
    BroadcastChannel that delivers messages synchronously between them, and assert that
    exactly one is the owner after both boot, that a takeover flips ownership in both
    modules, that ownership can flip back, that a secondary's `save` is a no-op, and that
    absence of heartbeats for the stale window marks the lock stale without changing
    ownership.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| tab ↔ tab over BroadcastChannel | Same-origin message passing between browsing contexts; any same-origin script can join the channel |
| tab → shared localStorage key | Multiple contexts writing one key is the documented silent-data-loss path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-06 | Tampering | two tabs both autosaving, last writer silently winning | mitigate | `save()` returns early unless `isOwner()`; a secondary never calls setItem for the tournament key. The banner explains it; the gate guarantees it |
| T-01-40 | Tampering | a demoted tab taking over and writing back a stale in-memory document | mitigate | Any tab claiming or reclaiming ownership reloads via `load()` and adopts the persisted document when its `generation` is higher, before writing. Verified by hand in checkpoint step 6 |
| T-01-41 | Denial of Service | owner tab crashes, leaving every other tab permanently read-only | mitigate | 2000ms heartbeat with a 6000ms stale threshold; the surviving tab surfaces the stale sentence and an enabled takeover button. Deliberately no auto-promote, because a three-tab auto-promote race is worse than one click |
| T-01-42 | Spoofing | a same-origin script forging a `takeover` message | accept | Only same-origin code can open the channel, and any same-origin code could already write localStorage directly. There is no privilege to escalate on an accountless static page |
| T-01-43 | Denial of Service | BroadcastChannel unavailable in an embedded webview | mitigate | The module falls back to assuming sole ownership and logs once. A missing API degrades to the pre-lock behaviour, never to a locked-out app |
</threat_model>
