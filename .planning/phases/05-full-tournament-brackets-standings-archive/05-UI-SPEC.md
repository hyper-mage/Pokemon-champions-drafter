## The reframe this contract is built on

`05-CONTEXT` D-03 is load-bearing, and every results-grid decision below inherits it:

> **Nothing in the tool tells the group what to play next**, so the grid itself has to make "what
> is left" obvious at a glance.

There is therefore no on-the-clock player anywhere in this phase. The round robin is filled in
whatever order the games happen, and in a bracket all four quarter-finals are playable at once.
**This phase adds no accent-marked "next" indicator, and the executor must not reach for one.**
"What is left" is carried by two things instead, both readable across a room:

| Signal | Where |
|--------|-------|
| A stated count | `{k} of {n} matches still to play.` above the grid, at `--text-heading` |
| A hole in the grid | An unplayed cell renders **empty** — no fill, no text, only the shipped dashed empty-slot boundary. The eye counts holes; it cannot count filled cells. |

The count is not decoration. It is what makes the cut control inert until the round robin is
complete (§8), so the same sentence carries the scanning affordance and the gate.

## Amendments to Earlier Contracts

Three shipped contracts are deliberately changed by this phase. Each names the exact text it
replaces. **Every stylesheet or source comment stating the superseded rule must be corrected in the
same change that breaks it** — a stale contract comment is worse than no comment, because the next
reader trusts it (`02-UI-SPEC` §Amendments, `03-UI-SPEC` §Amendments, `04-UI-SPEC` §Amendments).

### Amendment 1 — `New tournament` informs, it no longer warns (supersedes `02-UI-SPEC` §11 row 1, and `confirm-copy.ts` `ABANDON_CONFIRM` at its `New tournament` call site only)

`02-UI-SPEC` §11 gives one `danger`-toned dialog for *"Abandon draft / start a new tournament"*.
D-15 splits that row in two, because with a library in place the two actions no longer lose the
same thing:

| Path | Tone | What is true now |
|------|------|-----------------|
| **`New tournament` over a live one** | `default` | The live tournament is **filed into the library**. Nothing is lost. The dialog's job is to say where it went and to offer the download anyway (D-14's eviction reason). |
| **`Abandon draft`** (the explicit top-bar action) | `danger`, **unchanged mechanism** | Still discards. But it is now the *only* path that does, so its body must say so — see §Copywriting, `ABANDON_CONFIRM` body change. |

`ABANDON_CONFIRM` keeps its heading, both button labels and its tone. **Only its body string
changes**, gaining the clause that abandoning does not file. The destructive reservation stays at
three (§Color).

### Amendment 2 — `DEPTH_NOTE` becomes false and is replaced by a per-option note (supersedes `src/ui/screens/ConfigScreen.tsx:138-139`)

The shipped string is:

```ts
const DEPTH_NOTE =
  'Depth is recorded now. Round robin and brackets arrive with the tournament screens.';
```

This phase is those screens. One note under the group is also the wrong shape now, because D-01
makes the difference between the two deeper tiers a *specific* one — the numeric field and the
editable history — and a single sentence cannot state three different outcomes. **Replaced by one
note that changes with the selected option**, given verbatim in §Copywriting.

### Amendment 3 — the persistence wrapper holds a library, not a slot (supersedes `01-UI-SPEC` §Persistence's one-tournament assumption; `persistence.ts:39`, `:75`)

`STORAGE_KEY = 'champions-drafter:tournament'` is one key holding one `PersistedRecord`. D-14
expands it. This is a UI contract only in what it makes visible — a list on the landing screen, a
filing confirm, and an at-cap eviction confirm — and the storage shape itself belongs to planning.
What this contract fixes is the **cap number and its defence** (§The Library Cap), because the
number is what the eviction copy interpolates and what the landing screen's height budget is sized
against.

## Design System

Unchanged. Restated because the constraint is absolute and this phase adds thirteen components.

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-built Preact components under `src/ui/` |
| Icon library | none. **This phase needs zero glyphs.** A bye is the word `Bye`; a champion is the word `Champion`; a bracket connector is a CSS border (§The Bracket). No trophy icon, no chevron, no SVG, no icon font. |
| Font | system stack, no webfont (Phase 1 §Typography) |

**Hard constraint — do not violate.** Runtime `dependencies` is exactly `preact@10.29.8` and
`@preact/signals@2.10.1`, both exact-pinned (verified in `package.json` this session). No CSS
framework, no CSS-in-JS runtime, no component registry, no icon package, **no bracket-rendering
library, no charting library, no virtualization library, no drag-and-drop library**. `CLAUDE.md`
§What NOT to Use rejects `brackets-manager`, `brackets-viewer`, `@dnd-kit/core`, `sortablejs` and
`@tanstack/virtual-core` by name. A third runtime dependency is a constraint violation, not a
trade-off.

**Styling mechanism:** unchanged. `src/ui/tokens.css` declares values on `:root` and styles
nothing. One stylesheet per component, beside it, consuming tokens only. No raw hex. No raw px for
anything the token table covers. The three sanctioned raw lengths remain `--board-label-w: 176px`
in `BoardGrid.css`, the `60fr 40fr` pane split, and — added here — the results grid's
`--results-col-min` (§Size tokens). `npm run check:nohtml` forbids `innerHTML` and
`dangerouslySetInnerHTML` anywhere under `src/`.

**Bracket connectors are CSS borders, never inline SVG.** An SVG connector layer has to know where
each match card landed, which CSS Grid decides at layout time — so it would have to measure the
DOM and re-measure on every resize, zoom and font-size change. That is a second authority on card
position, free to disagree with the first. `::before` / `::after` pseudo-elements carrying
`border-top` and `border-right` at `--hairline-w` in `--color-hairline` are positioned by the same
layout that positions the card, so they cannot drift. This is the same argument the project used
to reject `brackets-viewer`, applied one level down.

existing scale; a standings row is text at existing sizes; a library row is a heading and a
description. Adding a token no assertion cites would make the token table longer without making
anything regressable (`04-UI-SPEC` §Size tokens).

## Typography

**Unchanged in every respect.** Four sizes, two weights (400, 600), no 500, no 700, no italics.
**No fifth size is introduced by any surface in this phase**, and none may be introduced as the
remedy to a legibility finding (`STATE.md`, Phase 4 blocker note).

| Token | Value | New usage in this phase |
|-------|-------|------------------------|
| `--text-body` | 400 18px / 1.5 | Recap entry lines; library row descriptions; config helper text below the new controls; the staleness banner sentence; the roster-refresh result sentence; the cut preview line; the bracket's `Winner of {label}` placeholder slot |
| `--text-label` | 600 14px / 1.4 | Bracket round headers (`Quarter-final` / `Semi-final` / `Final`); the `Champion` label; a standings row's tiebreak note; recap section timestamps; the results-grid metric caption |
| `--text-heading` | 600 24px / 1.25 | **Every player name on every new surface** — results-grid row and column headers, standings rows, bracket match slots, tiebreak-override rows, recap actor names; **every results-grid cell result**; the remaining-match count; library row headings; standings column headers |
| `--text-display` | 600 36px / 1.15 | The tournament screen's `<h1>`; the champion's name in the final's winner slot when the tournament is finished (D-18) |

**Four legibility floors, and why each sits where it does.**

- **Every player name takes `--text-heading` (24px)**, matching the board row label, the hand-strip
  pip and the ban-stage progress row. Player identity is read at a distance on every surface this
  project has shipped; one size across all of them is what makes the tournament screens read as the
  same tool as the draft.
- **A results-grid cell's result takes `--text-heading` (24px), not `--text-body`.** This is the
  one place this phase goes *above* the floor an equivalent Phase 4 surface used, and the reason is
  D-03: with no on-the-clock indicator, the cell content is the only thing distinguishing a played
  pairing from an unplayed one at three metres. It is the most-scanned text on the phase's most
  crowded screen. The cost is 14px of column width (§Layout Budget) and the budget carries it.
- **Bracket round headers take `--text-label` (14px)**, the same floor as the board's `R{n}` axis
  label, and are covered by assertion 5's existing 14px floor. A round header is an axis label; it
  is read once and then ignored.
- **The champion's name takes `--text-display` (36px)** and only when the final is recorded. It is
  the single fact the room turned to look at, and the largest token in the scale is the correct one
  — the same argument `03-UI-SPEC` made for the card digit and `04-UI-SPEC` made for the locked
  headline.

## Color

**Unchanged. No token is added, no reservation is widened.**

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0F1216` | Background; **an unplayed results-grid cell**; the results grid's diagonal and lower triangle |
| Secondary (30%) | `#1A1F26` | Standings rows, library rows, recap entries, bracket match cards, the staleness banner field |
| Raised | `#232A33` | **A recorded results-grid cell's fill**; a bracket slot that has advanced; the finished-tournament notice |
| Accent (10%) | `#FFCB05` | **unchanged reserved list — see below** |
| Destructive | `#FF7A70` | **unchanged reserved list — this phase adds no fourth use** |
| Type palette | 18 hues | unchanged — pool-card type pills and type filter controls only. **No tournament surface carries a type hue**, including the recap's `MonChip` lines, exactly as no board chip does. |

### Accent reserved for — still exactly three, and this phase uses only one of them

1. **The on-the-clock indicator** — **not used by this phase, and deliberately so.** There is no
   on-the-clock player in a fill-in-any-order round robin (D-03) and no single next match in a
   bracket where a whole round is playable at once. **Accent must not mark a playable match, an
   advancing seed, a leading player, or the champion.** Every one of those is a state, and this
   project marks state with lightness, boundary and words. Stated as a prohibition because a
   yellow "next match" is the first thing a bracket implementation reaches for.
2. **The primary action of the current screen** — one per screen:
   - Round-robin stage: `Take the cut` (once every match is recorded).
   - Bracket stage: none until the final is recorded, then `View the draft recap`.
   - Standings, still tied: `Confirm this order`.
   - Match record dialog: `Record the result` / `Record and void {n} matches`.
   - Landing: `New tournament`, unchanged.
   - The confirming button of each `default`-toned confirm dialog.
3. **The keyboard focus ring** — unchanged, global, `:focus-visible`.

### Destructive reserved for — still exactly three

1. The storage-unavailable blocking screen (unchanged).
2. The import-overwrite confirm (unchanged).
3. The abandon confirm — one mechanism, now three copy sets (live draft, ban stage, and the
   clause added by Amendment 1).

**The D-10 and D-11 cascade confirms are `default`-toned, not `danger`.** This is a deliberate
call and it is the reservation's load test. What a cascade voids is recoverable in one step — D-10
exists precisely so that "undo puts the whole correction back in one step" is true, and the voided
matches are named in the recap either way (D-22). `danger` in this project means *there is no way
back without a file you may not have downloaded*, which is the storage screen, the import
overwrite and abandon. Colouring a fully-undoable correction the same red would make the three
irreversible surfaces less legible as a category, which is the only job the reservation has.

**A locked (finished) tournament is not danger-coloured either.** Nothing is wrong; the night
finished. It takes `--color-surface-raised` and a sentence, following `ReadOnlyBanner`'s
"read-only is emphatically not a danger state" precedent.

### Colour is never the only signal — new rows

| State | Colour signal | Non-colour signal |
|-------|--------------|-------------------|
| **A match not played yet** | none | The cell is **empty** with a `--hairline-w dashed var(--color-border-strong)` boundary — the shipped empty-board-slot treatment — plus the accessible name `{rowPlayer} versus {columnPlayer} — not played yet`, plus the `{k} of {n} matches still to play.` count above the grid |
| **A match recorded** | none | `--color-surface-raised` fill, `--border-w solid var(--color-hairline)` boundary, and the words `Won` / `Lost` |
| **A match whose result is inert (finished tournament)** | none | `aria-disabled="true"` + `opacity: 0.45` + the reason in the accessible name + one visible sentence above the grid |
| **A bracket slot whose participant is not known yet** | none | The words `Winner of {roundLabel} {n}` at `--text-body`, and the card is `aria-disabled` with a reason |
| **A bye** | none | The word `Bye` in the second slot at `--text-heading`, and the card is not interactive — it is already resolved |
| **The champion (D-18)** | none | The word `Champion` at `--text-label` above the name, the name at `--text-display`, and `--border-w solid var(--color-text)` on the card — the shipped selected/pending treatment, a lightness and shape change, no hue |
| **A player still tied after the whole chain** | none | The sentence `Tied — order these yourself` at `--text-label` on every row of the block, plus the override control immediately below |
| **A stale roster (REFR-03)** | none | A full sentence naming the regulation and its expiry date, plus a named next action |
| **A corrected result, in the recap** | none | The original entry stays in place and carries `Corrected later` at `--text-label`; the correction carries `Corrects an earlier result`. **Never a strike-through** — see §The Recap. |

## Layout Budget — measured, not assumed

Every figure below is derived from `02-UI-SPEC` §Two-Pane Geometry and `BoardGrid.css:54`.

### The tournament screens are full-bleed, and the arithmetic forces it

The tournament surfaces use **`.draft-shell`** (full-bleed, `--space-4` padding, `height: 100dvh`,
independent scrolling regions), **not `.app-shell`**. This is not a preference:

```
.app-shell   1200 cap − 48 padding − 176 label − 64 gaps = 912 ÷ 8 players = 114 px per column
.draft-shell 1920      − 48 padding − 176 label − 64 gaps = 1632 ÷ 8 players = 204 px per column
```

The longest reachable results-grid cell string is `Won 2–1 · 18` — a Bo3 verdict plus the maximum
metric value (§Match Record Entry). At `--text-heading` (24px / 600, ~0.55em average advance
≈ 13.2px per character) that is 12 characters ≈ 158px, plus `--space-2` padding on both sides
= **188px**. That is `--results-col-min`.

**114px cannot hold 188px. 204px can, with 16px of slack.** Full-bleed is forced by measurement,
exactly as `02-UI-SPEC`'s 86px round cell forced sprite-only board chips.

### Where the results grid starts scrolling horizontally

```
176 label + n × (188 + 8 gap) ≤ 1872   →   196n ≤ 1696   →   n ≤ 8.65
```

**The results grid fits with no internal horizontal scroll up to and including 8 players.** At 9 or
more it scrolls, carried by `BoardGrid.css`'s shipped `overflow-x: auto` wrapper and
`position: sticky; left: 0` label column, reused verbatim. 8 is the project's stated design ceiling
(`CLAUDE.md` §Constraints — "4–8 players by default"), so the boundary lands exactly where the
constraint puts it, and `MAX_PLAYERS = 64` degrades to a scroll rather than to a break.

### The 8-player results grid fits vertically

```
cell height    24 × 1.25 = 30 text + --space-2 × 2 padding = 46 px   (clears --target-min 44 ✓)
column header  two wrapped lines at 30 + --space-2 × 2            = 76 px
8 body rows    8 × 46                                             = 368
gaps           8 × --space-2                                      =  64
                                                                    508 px
```

Available height at 1080p, following `02-UI-SPEC` §Board height: `1080 − 48 shell padding −
~181 sticky head − ~46 caption and count lines − 40 bottom ≈ 765px`. **508 < 765 — the 8-player
results grid fits with no internal vertical scroll**, with 257px of slack for the standings block
below it to begin on the same screen.

Column headers **wrap rather than ellipsise.** Player names are host-typed with no length bound in
`import-guard.ts`, and `02-UI-SPEC` assertion 7 already established that a truncated name is a
failure, not a fallback. `overflow-wrap: anywhere` on the header so a single long token cannot
force horizontal overflow; the header row is sized for two lines and grows past it if it must.

### The 8-seed bracket fits

```
match card     2 slots × (30 text + --space-1 × 2) = 76 + --space-2 × 2 padding = 96 px  (clears 44 ✓)
round 1        4 cards × 96 + 3 × --space-4        = 384 + 72                   = 456
round header   14 × 1.4 = 20 + --space-2 gap                                    =  28
                                                                                  484 px
```

484 < 765 ✓. Horizontally, three rounds:
`1872 − 2 × --space-6 = 1776 ÷ 3 = 592px per column`, and a card needs 16px padding plus a name —
592px holds ~43 characters at 24px. Comfortable.

**At 16 seeds the bracket scrolls vertically** — round 1 is `8 × 96 + 7 × 24 = 936px` against
765px. That is accepted and stated rather than gated: `CLAUDE.md` §Constraints says the tool must
not break above 8 players, not that it must fit on one screen there. Four rounds still fit
horizontally: `1872 − 3 × 48 = 1728 ÷ 4 = 432px`.

### The library at the cap is under two screens

```
library row    --space-3 pad + 30 heading + --space-1 + 27 description + --space-3 pad = 93 px
stride         93 + --space-2                                                          = 101 px
12 rows                                                                                = 1212 px
```

Landing screen available height ≈ `1080 − 48 padding − 41 title − 24 − 27 subtitle − 24 −
~200 actions − 30 library heading − 16 ≈ 670px`. **Twelve rows is 1.8 screens — one deliberate
scroll, not a feed.** This is the third of the three defences for the cap number (§The Library Cap).

## The Library Cap — D-16's number, chosen and defended

**The cap is 12 tournaments.** D-16 leaves the number to Claude and asks that it be defended
against measured document size rather than chosen because it sounds round. Three independent
defences, any one of which would justify a smaller number; together they justify this one.

**1. Storage, measured.** A synthetic worst-case document was serialized this session: 8 players,
6 rounds, `blind` bans, `draftBracketsAndLog` depth, a 96-id pool, a 12-species host banlist, a
full 28-match round robin and a 7-match bracket — 153 log entries.

```
JSON.stringify(doc).length                        = 21,572 characters  (21.1 KB)
fixed part (config + pool/built with 96 ids)      ≈  2,500 characters
variable part ÷ 153 entries                       ≈    125 characters per log entry
```

`PROJECT.md` puts a full night at roughly 350–500 actions. At the upper bound:
`2,500 + 500 × 125 = 65,000 characters ≈ 65 KB`. Budget **80 KB** per entry — a 23% margin over the
computed worst case.

```
12 × 80 KB library + 80 KB live document = 1.04 MB
against a conservative 5 MB localStorage budget    → 21% used, 4.8× headroom
```

Even if the per-entry figure is 2× low, the library lands at 42% of quota. `probeStorage`
(`persistence.ts`) remains the canary and becomes more load-bearing, not less — the cap is a design
for the common case, not a substitute for the failure path.

**2. Regulation rotation.** `roster.index.json` records M-A at 70 days (2026-04-08 → 2026-06-17)
and M-B at 77 days (2026-06-17 → 2026-09-02). A group drafting fortnightly fills 12 slots in
24 weeks — roughly two and a half regulations. **The first eviction therefore fires on a night that
is at least two regulations old**, which is the point at which D-24's "a filed M-B night stays an
M-B night" is doing archaeology rather than holding recent history.

**3. The landing screen.** 12 rows is 1,212px against ~670px available — under two screens
(§Layout Budget). A cap of 24 would be three and a half.

**The cap is a constant with a doc block citing all three defences**, not a literal at a call
site, because the eviction copy interpolates it and the landing-screen height budget is sized
against it.

`StalenessBanner` and `FinishedNotice` are **new components rather than variants of

### 1. Config screen — the tournament controls (TOUR-01, TOUR-07, D-01, D-02, D-04, D-08)

The `Depth` group grows from one `SegmentedControl` plus a static note into a group of four
controls.

| Control | Type | Options | Inert when |
|---------|------|---------|-----------|
| `Tournament depth` | `SegmentedControl` | `Draft only` · `Draft and brackets` · `Draft, brackets and match log` — all three enabled, unchanged | never |
| `Match result` | `SegmentedControl` | `Pokémon left` · `KO difference` | **`draftOnly` and `draftAndBrackets`** — D-01/D-04. The whole control is `aria-disabled` with a visible reason, following `Start draft`'s pattern rather than `SegmentedControl`'s disabled-*member* pattern: here every member is unavailable, not one of them. |
| `Round robin format` | `SegmentedControl` | `Best of one` · `Best of three` | **`draftOnly`** |
| `Bracket format` | `SegmentedControl` | `Best of one` · `Best of three` | **`draftOnly`** |

The per-option depth note replaces `DEPTH_NOTE` (Amendment 2). At the two deeper tiers a second
line states the round-robin size as a plain fact, not a warning:
`A round robin at {p} players is {n} matches.`

**One feasibility addition, warning severity, and it lives in `feasibility.ts`.** `05-CONTEXT`
leaves to discretion whether depth gets a gate; it does, and it is a `warning`, never `blocking`,
consistent with the project's warn-rather-than-hard-cap posture:

> `A bracket needs at least 4 players to mean much. At {p} players the round robin already decides
> it. Choose Draft only, or add players.`

**No high-player-count gate is added**, deliberately. A 16-player round robin is 120 matches and a
long night, but it is a legitimate choice and the match count is already stated above. Recorded so
nobody adds one reflexively (`04-UI-SPEC` §Deferred precedent).

### 2. Config screen — roster refresh and offline import (REFR-01, REFR-02, D-23, D-26)

One group, placed **beside the roster the tournament is being created against** (D-23), holding
both controls (D-26) so the tension between D-23 and D-25 is resolved by routing rather than by
growing a second control anywhere else.

| Element | Detail |
|---------|--------|
| Group heading | `Roster` at `--text-heading` |
| Current line | `{regulationLabel} — {n} Pokémon, valid until {date}.` at `--text-body` |
| Primary control | `Check for a new roster` — a plain button, not accent-filled (the screen's primary action is `Start draft`) |
| Secondary control | `Import roster JSON…` — the shipped hidden-`<input type="file">` + button pattern from `LandingScreen` and `TopBar`, reused verbatim including the `input.value = ''` reset |
| Result region | A surface-owned `role="status"` holding one sentence, replaced on each attempt (§Copywriting) |

**Refresh states — five, each with a sentence:** idle (no sentence), checking, already current,
updated, failed. The failure sentence names the offline path, because REFR-02 exists for exactly
that host: `No network. Import a roster JSON file instead, or try again when you are online.`

**Where the fetch goes — recorded, with reasoning, as `05-CONTEXT` §Discretion requires.**
Recommendation: **same-origin re-fetch of the project's own deployed snapshot with the HTTP cache
and the service-worker cache bypassed**, not `raw.githubusercontent.com`. Reasoning: it keeps the
invariant `roster-source.ts:1-13` states in as many words and a test asserts (T-01-25), and for
this project a commit and a Pages deploy are effectively the same moment, so the practical
freshness gap between the two options is small. If planning chooses off-origin instead, that doc
block and that test change **deliberately, with the reasoning written down**, and this contract
changes in exactly one place: the failure sentence must distinguish "GitHub is unreachable" from
"you are offline", because with a third-party origin those are different problems with different
next actions. Everything else in §2 is unaffected.

### 3. The staleness banner (REFR-03, D-25, D-26)

Warns, never blocks (D-25). Not danger-coloured — nothing is wrong yet, and a group mid-rotation
may run a night on last regulation's roster deliberately.

**It appears on exactly two screens: the landing screen and the config screen.** Not during a live
tournament, not on a filed one. D-24 makes a live or filed tournament's roster a settled fact — it
loads its own snapshot by `rosterVersion` and keeps working unchanged — so a banner there would
warn about something that is not a problem and offer an action that would not change that
tournament. D-25's own words give the banner its job: to stop a host starting a night on an expired
roster *by accident*. There are exactly two screens where a night gets started.

| Screen | Behaviour |
|--------|-----------|
| **Config** | States the problem and **names the control beside it**. No second refresh button — the control is on the same screen (D-26). |
| **Landing** | States the problem and offers `Update the roster`, which **routes to the config screen with focus on `Check for a new roster`** (D-26). It does not refresh in place. |

The comparison reads a clock and therefore lives in `src/adapters/`, stamped at the edge and handed
to the UI as a boolean plus a date string. `npm run check:pure` would fail a core implementation,
and correctly.

### 4. The round-robin results grid (TOUR-02, D-03) — the sharpest legibility case

A crosstable of every pairing, all present from the moment the round robin starts.

**Shape.** `N` columns × `N` rows so the headers align, in a CSS Grid of `<div>`s matching
`BoardGrid` exactly. **Only the upper triangle carries live cells** — at 8 players that is
`8 × 7 / 2 = 28` cells. The diagonal and the lower triangle render as plain non-interactive
`<div>`s with no text and `aria-hidden="true"`, because they carry zero information: a mirrored
lower triangle would render every pairing twice, doubling the reading load on a screen people are
reading from across a room, and it would be a second visual authority on one match.

| Region | Element | Treatment |
|--------|---------|-----------|
| Row label (`--board-label-w`, 176px) | `<div>` | Player name at `--text-heading`, `position: sticky; left: 0` |
| Column header | `<div>` | Player name at `--text-heading`, wrapping to two lines, `overflow-wrap: anywhere` |
| Diagonal, lower triangle | `<div aria-hidden="true">` | `--color-bg`, no border, no content |
| Unplayed cell | `<button>` | Empty. `--hairline-w dashed var(--color-border-strong)`. |
| Recorded cell | `<button>` | `--color-surface-raised`, `--border-w solid var(--color-hairline)`, one line of text |
| Recorded cell, finished tournament | `<button aria-disabled="true">` | Same, plus `opacity: 0.45` and a reason in the accessible name |

**Cell content, from the row player's perspective** — the row and column headers already name both
players, so the cell only says who won:

| Depth | Format | Bo1 | Bo3 |
|-------|--------|-----|-----|
| `draftAndBrackets` | winner only | `Won` / `Lost` | `Won 2–1` / `Lost 1–2` |
| `draftBracketsAndLog` | winner + metric | `Won · 4` | `Won 2–1 · 18` |

The `·` is an `aria-hidden` span, the separator convention `03-UI-SPEC` established. The metric's
unit is stated **once** in a caption above the grid, never repeated in 28 cells.

**Above the grid, in this order:** the `{k} of {n} matches still to play.` count at
`--text-heading`, then the metric caption at `--text-label` (tier 3 only). The count is the phase's
answer to D-03 and it is also the cut's gate (§8).

**Accessible name of a live cell** — carries both axes, so the grid needs no grid roles (the
`BanBoard` / `BoardGrid` precedent):

- unplayed: `{rowPlayer} versus {columnPlayer} — not played yet`
- recorded: `{rowPlayer} beat {columnPlayer} 2–1, 18 {metricLabel}` (or `lost to`)
- finished: the recorded sentence plus `— this tournament is finished`

### 5. Match record entry (TOUR-04…07, D-05, D-08, D-09, D-10, D-11)

Activating any live cell — in the grid or in the bracket — opens `MatchRecordDialog`, built on
`Dialog`. A modal rather than an inline panel for three reasons: `Dialog` already solves focus
trapping, Escape and return-focus, so 28 openings need no new accessibility model; return-focus
lands back on the cell, which answers "focus after" for free; and on a shared screen a modal puts
the room's attention on the one result being transcribed.

**One gesture, one action (D-05).** The dialog collects everything and dispatches once. A match is
never half-recorded, so standings never read a match with a winner and no metric.

| Field | Control | Present when |
|-------|---------|--------------|
| Winner | `SegmentedControl`, two members, one per player | always |
| Games | `SegmentedControl`: `2–0` · `2–1` | the stage's format is `Best of three` (D-08) |
| Metric | `NumericField`, bounded `0 … MAX_MATCH_METRIC` | depth is `draftBracketsAndLog` (D-01) |

`MAX_MATCH_METRIC = 18` — six Pokémon × three games. **Bounded at the same constant
`import-guard.ts` uses**, so the build cannot create a document `isValidTournament` refuses to
re-open (Phase 3's rule). `18` is also the value `--results-col-min` was sized against.

**The cascade is stated inside this dialog, not in a second one (D-10, D-11).** The moment the
entered values differ from what is already recorded, a `role="status"` region inside the dialog
names exactly what will be voided, and **the primary button relabels to name it**:

| Situation | Primary button |
|-----------|---------------|
| Nothing recorded yet | `Record the result` |
| Correction, nothing downstream affected | `Record the result` |
| Correction changing who is in a downstream match (D-10) | `Record and void {n} matches` |
| Correction to a round-robin result after the cut (D-11) | `Record and void the bracket` |

The relabel **is** the confirm DRFT-13 requires: nobody presses a button labelled
`Record and void the bracket` without reading it, and buttons in this project already name a verb
and its object — here the object is the void. Stacking a `ConfirmDialog` on top of a form dialog
would be a second modal pattern for one gesture. The safe button reads `Keep the recorded result`.

**Re-recording an identical result is unreachable.** When every entered value matches what the
cell already holds, the primary button is `aria-disabled` with the reason
`This is already the recorded result.` This is the constraint-upstream-of-the-click pattern
(`selectCardOffer`), and it is also what makes the live-region announcement safe from
`LiveRegion`'s byte-identical limitation (§Interaction).

### 6. The standings table (TOUR-08, D-02, D-13)

| Column | Width | Content |
|--------|-------|---------|
| Position | `--space-6` | `1`…`n` at `--text-heading` |
| Player | `--board-label-w` | Name at `--text-heading` |
| Record | auto | `{w}–{l}` at `--text-heading` |
| `{metricLabel}` | auto | **Rendered only at `draftBracketsAndLog`** (D-02) |
| Tiebreak note | auto | `--text-label`, empty for rows that were never tied |

**The chain is stated above the table, and the statement differs by depth (D-02).** A greyed-out
differential column was rejected by D-02; an empty column is not the same statement as a table that
has two links. So the column is absent and the caption says why:

- tier 3: `Ties break on record, then {metricLabel} summed across every match, then head-to-head
  between two players. Anything still tied is yours to order.`
- tier 2: `Ties break on record, then head-to-head between two players. Draft and brackets records
  no numbers, so there is no {metricLabel} link and a tie reaches you sooner.`

**Where the automatic chain stops — decided, per `05-CONTEXT` §Discretion.** **Head-to-head applies
to two-way ties only. A tie of three or more goes straight to the host override.** Reasoning:
head-to-head is undefined for three (A beats B, B beats C, C beats A), the ties a mini-table cannot
resolve are exactly the cyclic ones, and `PROJECT.md` §Out of Scope explicitly rejects automatic
multi-link tiebreak chains. A mini-table would resolve the easy cases and then have to explain to
the room why it gave up on the hard one — two explanations where one will do.

**Which link is deciding is on the row, not only in the caption** (`05-CONTEXT` §Discretion
requires the table SAY it):

| Row state | Note at `--text-label` |
|-----------|----------------------|
| Never tied | *(empty)* |
| Broken on the metric | `Tied on record · {metricLabel} decided it` |
| Broken on head-to-head | `Tied on record and {metricLabel} · head-to-head decided it` |
| Broken on head-to-head, tier 2 | `Tied on record · head-to-head decided it` |
| Still tied | `Tied — order these yourself` |

### 7. The tiebreak override (TOUR-08, D-13)

The host puts the still-tied block in an order by hand. **Up/down buttons, one pair per row —
the `SchedulePreview` reorder pattern, reused down to the focus rule.** Not drag-and-drop
(`CLAUDE.md` §What NOT to Use rejects DnD libraries and notes up/down buttons are more reliable on
touch), not typed seed numbers (D-13 rejects them: collisions and gaps), not pair-by-pair winners
(D-13 rejects them: the host can produce a cycle).

- Only the tied block is reorderable. Rows outside it are not rendered in this control.
- The end buttons are `aria-disabled`, never native `disabled` — a natively disabled button is not
  focusable, so its reason is unreachable by keyboard.
- **Focus after a move goes to the same-named button in the row the player moved to**
  (`03-UI-SPEC` §2, verbatim).
- Confirming dispatches one action naming exactly which players it resolved (D-13), so the recap
  and the bracket seeding both point at a deliberate host act.
- Primary action `Confirm this order` — accent-filled; it is the primary action of this screen.

### 8. The cut (TOUR-09, D-06)

Chosen from the standings screen after the round robin, never at config time (D-06).

| Element | Detail |
|---------|--------|
| Control | `NumericField`, label `Players who advance`, bounded `2 … {playerCount}` |
| Preview | `Top {n} advance. Seeds 1 to {b} get a bye.` — recomputed live, `--text-body` |
| Preview, no byes | `Top {n} advance. No byes at {n}.` |
| Primary action | `Take the cut` — accent-filled |

**The control is inert until every round-robin match is recorded.** Reason, in the
`aria-describedby` region and visible:
`{k} matches are still to play. Record them all before you cut.`
Seeding from incomplete standings is a whole class of bad state removed upstream of the click
rather than caught after it — and it is why the `{k} of {n}` count above the grid is load-bearing
rather than decorative.

No confirm dialog. Taking the cut destroys nothing and is undoable like everything else (D-12).

### 9. The bracket (TOUR-03, D-07) and its finished state (D-18)

**CSS Grid, one column per round, connectors as pseudo-element borders.** No SVG, no library
(§Design System).

```
.bracket        display: grid; grid-auto-flow: column; gap: var(--space-6)
.bracket__round display: grid; align-content: space-around; gap: var(--space-4)
```

`align-content: space-around` is what centres each round's cards against the pair feeding them,
without any code knowing a card's pixel position.

**Byes go to the top seeds, standard seeding (D-07)** — seed 1 first, then seed 2. 7 players take
1 bye, 6 take 2, 5 take 3. **A bye renders as a resolved match card**, not as an empty slot: the
seeded player in the first slot and the word `Bye` at `--text-heading` in the second, the card
non-interactive. An empty second slot would use the not-yet-played treatment and read as a match
someone forgot to record.

| Card state | Treatment |
|------------|-----------|
| Participants unknown | `aria-disabled`, slots read `Winner of {roundLabel} {n}` at `--text-body`, reason in the accessible name |
| Playable | A real `<button>`, both slots named at `--text-heading`, dashed empty result area |
| Recorded | `--color-surface-raised`, winner's slot at `--border-w solid var(--color-hairline)`, result text `2–1 · 4` |
| Bye | Resolved, non-interactive, second slot reads `Bye` |
| The final, once recorded (D-18) | `Champion` at `--text-label` above the winner's name at `--text-display`, card at `--border-w solid var(--color-text)` |

Round headers at `--text-label`: `Quarter-final` · `Semi-final` · `Final`, and for larger brackets
`Round of {n}`.

**D-18: no new summary screen.** When the final is recorded the bracket stays exactly where it is
and the champion is named on it. `CompletedDraft`'s posture is inherited — the top bar stays, so
`Undo last move` and `Download JSON` stay reachable from the screen a host is looking at when they
realise the last result was wrong. The recap is reachable from here (§11).

### 10. Finished and reopen (D-17)

Locked is a fold — a final recorded with no later `tournament/reopened` — in exactly the way
`selectPhase` and `selectBanStageState` already work. It survives reload, travels with an exported
JSON, cannot be disagreed about by two tabs, and cannot be claimed falsely by an imported document.

`FinishedNotice` renders above the bracket, `--color-surface-raised`, never danger:

> `This tournament is finished. Results are read-only.` + `Reopen this tournament`

**Every result control on a locked tournament is inert with a stated reason, never hidden.** This
is the codebase's established move (`selectCardOffer`, `selectRoundEligibleIds`,
`SegmentedControl`'s disabled-member pattern) and a hidden control would make a host think the app
had lost a feature. Reason in each cell's accessible name:
`This tournament is finished. Reopen it to change a result.`

Reopening uses `ConfirmDialog`, `default` tone — nothing is destroyed and the reopen is itself
undoable. The body states the D-10/D-11 interaction plainly, because the friction is intended.

### 11. The recap (PERS-09, D-19…D-22)

**Chronological, top to bottom** (D-19). It **replaces the tournament screen's main region and
nothing else** — the top bar stays, following `CompletedDraft`'s stated reasoning verbatim, so
undo and the JSON download remain reachable from the recap. Reached by `View the draft recap`;
left by `Back to the bracket` (or `Back to the draft` at `draftOnly` depth).

Sections in log order, each headed at `--text-heading`: `Bans` · `Priority cards` ·
`Round {n}` (one per round) · `Swaps` · `Round robin` · `Bracket`. Every action family the log
holds is covered (D-20); omitting one would be a deliberate choice rather than a saving.

| Entry kind | Line |
|-----------|------|
| Ban | `{playerName} banned {name}.` — with a `MonChip` at `--sprite-sm` |
| Collision | `{a} and {b} both banned {name}. It was banned once.` |
| Card | `{playerName} played {value}.` |
| Pick | `{playerName} picked {name}.` — `MonChip` at `--sprite-sm` |
| Swap | `{playerName} swapped {out} for {in}.` |
| Pass | `{playerName} passed.` |
| Match | `{winner} beat {loser} {games}.` (+ ` · {metric} {metricLabel}` at tier 3) |
| Cut | `The cut was taken at {n}.` |
| Override | `The host ordered {a}, {b} and {c} by hand.` |
| Void | `{n} matches were voided by a correction.` |

**Blind bans render from `bans/revealed` and its collisions only (D-21)** — never from the raw
`bans/submitted` entries, which Phase 4's D-06 puts in the log as plaintext defended by the screen
shield rather than by the file. The recap reads `selectPublicBanIds` / `selectAttributedBans`, the
same selectors `04-UI-SPEC` Amendment 1 routes the top-bar disclosure through. **The case this
protects: a blind tournament abandoned before the reveal and filed into the library. Its recap has
no `Bans` section at all, which is correct — those bans were never public.**

**Corrections are shown, never struck through (D-22).** The original entry stays in chronological
position carrying `Corrected later` at `--text-label`; the correction carries
`Corrects an earlier result`. Strike-through in this project means *gone or unavailable* (the
snake ban-list treatment); a corrected result is neither — it happened, and then it was changed.
Using the same treatment for both would make one signal mean two things.

### 12. The tournament library (PERS-08, D-14, D-15, D-16)

A capped list of **whole documents** on the landing screen (D-14). Each entry is the full log,
re-foldable, re-exportable, and able to render a recap — which is why a compacted summary was
rejected outright.

| Element | Detail |
|---------|--------|
| Section heading | `Your tournaments` at `--text-heading` |
| Row heading | `{formatLabel}` at `--text-heading` |
| Row description | `{date} — {m} players, {status}` at `--text-body` |
| Row actions | `Open` · `Download JSON` |
| Order | Newest first, by `createdAt` |

`{date}` is `createdAt` formatted absolutely. This does **not** contradict
`savedDraftDescription`'s "no timestamp" rule, which rejected a *relative* time because it needs a
clock; formatting a stamp already on the document is a formatting call. With up to 12 entries a
format label alone cannot distinguish them.

`{status}` is one of: `{championName} won` · `draft complete, no bracket` ·
`in progress, {picks} of {total} picks`.

**At zero entries the section is not rendered at all.** `LandingScreen` deliberately has no "no
saved drafts" empty state, with the stated reason that "saying 'nothing here' would be noise on the
screen with the least to say". Same rule, same reason.

**Opening a library entry files the current tournament first**, through the same D-15 confirm —
one filing path, not two.

**D-16's eviction tells the host before anything goes.** At the cap, filing raises a
`ConfirmDialog` naming the tournament about to be dropped and offering its download in the same
dialog (§Copywriting). An unbounded library that fails on quota was rejected because that failure
lands while the host is trying to save a night.

## DRFT-14 as a Checkable Assertion — extended

`02-UI-SPEC` (1–8), `03-UI-SPEC` (9–12) and `04-UI-SPEC` (13–16) all stand in full. Seven
assertions are added. **Any one failing fails the phase.**

| # | Assertion | Measured where |
|---|-----------|---------------|
| 17 | Every player name on a results-grid row label, a results-grid column header, a standings row, a bracket match slot and a tiebreak-override row renders at ≥ 24px | `--text-heading` |
| 18 | Every results-grid cell result renders at ≥ 24px | `--text-heading` on `.results-grid__cell` — deliberately above the 18px floor, see §Typography |
| 19 | The 8-player results grid fits the full-bleed tournament shell with no internal horizontal scroll at 1920 × 1080 | §Layout Budget: `196n ≤ 1696 → n ≤ 8`; `--results-col-min` 188px against 204px available |
| 20 | The 8-player results grid fits with no internal vertical scroll at 1920 × 1080 | §Layout Budget: 508px against ~765px |
| 21 | An 8-seed bracket fits with no internal vertical scroll at 1920 × 1080 | §Layout Budget: 484px against ~765px |
| 22 | Every results-grid live cell and every playable bracket match card measures ≥ 44px in both axes | 46px and 96px against `--target-min` |
| 23 | The champion's name renders at ≥ 36px once the final is recorded | `--text-display` on `.match-card__champion-name` |

### Extending Phase 3's and Phase 4's arc-minute analysis rather than restating it

`03-UI-SPEC` computed three rows and the host's physical check **passed all of them on the
pessimistic screen** — a ~24" 1080p monitor at 3 metres (`STATE.md`, 2026-08-19, 2026-08-20 and
the Phase 4 pass). Every new surface here reuses one of those three sizes, so the analysis extends
by mapping rather than by re-deriving:

| New surface | Size | Same size as | Status |
|-------------|------|-------------|--------|
| Champion's name; tournament `<h1>` | 36px | the priority-card digit (~11 arcmin @92ppi, ~20 @51ppi) | **verified pass** on the 24" monitor |
| Every player name; every results-grid cell result; the remaining-match count | 24px | the hand-strip pip and the board row label (~7.6 arcmin @92ppi, ~14 @51ppi) | **verified pass**, recorded as marginal-but-readable on the 24" |
| Recap lines; library descriptions; cut preview; staleness sentence; `Winner of …` slots | 18px | the Mega marker (~5.7 arcmin @92ppi, ~10 @51ppi) | **verified pass**, recorded as marginal-but-readable on the 24" |
| Bracket round headers; `Champion` label; tiebreak notes | 14px | the `R{n}` axis label | covered by assertion 5's 14px floor |

**This phase introduces one new legibility risk, and it is density of information rather than
size.** Every *size* here is already physically verified. What is new is 28 cells in one view where
the ban board had at most 8 columns of 8. That is precisely why §The reframe puts the remaining
count in words at 24px and leaves unplayed cells visually empty: neither depends on resolving 28
small differences across a room.

**Physical check, mandatory and not substitutable.** Extends the passes `02-`, `03-` and
`04-UI-SPEC` require, with a fifth, using the same setup — 8 players, 3 metres from a 1080p screen:

5. **The tournament stage.** Configure 8 players, `Draft, brackets and match log`, `Best of one`
   round robin, `Best of three` bracket. Complete a draft, then:
   a. With about half the round robin recorded, stand 3 metres back and **read the remaining-match
      count aloud, then say without moving closer roughly how many cells are still empty.** The
      count is the pass condition; the visual estimate is the evidence for or against the
      empty-cell treatment.
   b. Read aloud three recorded cells — the two players from the headers and the result from the
      cell.
   c. Read the standings: every player name, every record, and the tiebreak note on any tied row.
   d. Take a cut at 5 so three byes are drawn. Read every bracket slot aloud, including the byes
      and the `Winner of …` placeholders.
   e. Record the final. Read the champion's name aloud.

   **Record the screen's physical size and the result per surface.** A failure at 24px in a
   results-grid cell is a finding about `--text-heading` on a crowded shared surface — **not a
   licence to introduce a fifth font size.** The remedies available inside this contract are the
   existing scale, removing the metric from the cell (leaving it in the standings only), and
   raising `--results-col-min` at the cost of the no-scroll threshold dropping from 8 players to 7.

## Interaction & Accessibility

Phases 1–4's tables apply in full. These are the additions this phase forces.

| Rule | Requirement |
|------|-------------|
| **The announce-vs-focus rule still holds** | `03-UI-SPEC` records, unresolved, that a polite announcement queued alongside a focus move is routinely preempted (`SplitPanes.tsx:146-167`). Nothing here depends on the answer: every announcement below is also carried by persistent on-screen text — the cell fills in, the count decrements, the standings reorder, the champion is named. |
| **Results-grid keyboard navigation** | One tab stop, via the shipped `use-roving-tabindex` **with `columns` omitted** so the hook runs in its 1-D mode over the live cells in reading order. The live set is triangular, so a fixed column stride is wrong on every row and a per-row stride would be a second navigation model for one hook. Left/Right move between live cells, Home/End jump to first/last, Enter and Space open the record dialog. **No `role="grid"`, no `role="row"`, no `role="gridcell"`** — the board does not invent them and each cell's accessible name already carries both axes. |
| **No roving tabindex on the standings table, the bracket, the library or the recap** | None is a large uniform interactive set — the standings and library are ≤ 12 rows, the bracket is ≤ 15 cards, the recap is not interactive at all. `PlayerList` already sets the precedent that a list of rows uses plain tab stops. Stated explicitly so the hook is not wired out of habit. |
| **Focus after recording a match** | `Dialog` returns focus to the element that opened it — the cell or card, which still exists and now shows the result. **No override needed, and none may be added**: an override would be a second focus authority for the one case `Dialog`'s default already handles correctly. |
| **Focus after a cascade void** | Same target. The downstream cards that were voided are still on screen, now empty — the host must see that, and moving focus away from the cell they just corrected would hide the cause of the change. |
| **Focus after a tiebreak reorder** | To the same-named button in the row the player moved to (`03-UI-SPEC` §2, verbatim). |
| **Focus after taking the cut** | To the bracket's `<h2 tabindex="-1">`. `Take the cut` no longer exists once the cut is taken, so focus cannot stay where it was and must not drop to `<body>`. |
| **Focus after reopening** | To the `FinishedNotice`'s replacement — nothing — so focus moves to the results grid's first live cell, the surface the reopen exists to make usable. |
| **Focus entering and leaving the recap** | To the recap's `<h2 tabindex="-1">` on entry; to `View the draft recap` on exit — the control that was activated, which exists again. |
| **`aria-disabled`, never native `disabled`, on every inert control** | The metric segmented control below tier 3, both format controls at `draftOnly`, the cut control before the round robin is complete, an unknown-participant match card, every cell of a finished tournament, the reorder end buttons, and the record dialog's identical-result state. A natively disabled control is not focusable, so its reason is unreachable by keyboard. |
| **Inert ARIA is always shed** | Every inert state here removes `aria-disabled` the moment its condition lifts — the cut when the last match lands, a match card when its participants resolve, every cell on reopen, the metric control when depth changes. WR-04; this phase adds seven consumers. |
| **Target size** | Every new control ≥ `--target-min` in both axes: results-grid cell (188 × 46), bracket match card (592 × 96 at 8 seeds), `Take the cut`, `Confirm this order`, both reorder buttons, `Reopen this tournament`, `Check for a new roster`, `Import roster JSON…`, `Open`, `Download JSON`, `Update the roster`, `View the draft recap`, and every field in the record dialog. Column headers, row labels, the diagonal and the lower triangle are **not** interactive and are exempt, exactly as board chips are. |
| **Live region — match results** | Permitted, and safe. `announce` fires `{winner} beat {loser} {games}. {k} matches left.` on a round-robin record and `{winner} beat {loser} {games}. {winner} advances.` in the bracket. `LiveRegion`'s byte-identical limitation is not reachable: the only way to produce two consecutive identical announcements is to record the same result twice running, and §5 makes that state's primary button inert. |
| **Live region — the cascade** | A void announces separately and after the record: `{n} matches were voided.` Two announcements rather than one long sentence, because the second is the surprising one. |
| **Motion budget** | Unchanged: colour and border transitions only, ≤ 120ms. **A bracket does not animate an advance, a standings table does not animate a reorder, and taking the cut is not a transition.** A row that slides into place is a row nobody can read while it moves, on a screen a room is reading. |
| **Zoom and responsive** | Unchanged. Below 1280px the tournament screen's regions stack via the shipped media query. 200% zoom on 1920px is a 960px CSS viewport, which stacks — no second code path. The results grid keeps its `overflow-x: auto` wrapper and sticky label column at every width. |
| **Read-only tabs** | Every tournament surface renders inside the existing `inert` shell gate. A read-only tab can reach none of the record, cut, override or reopen controls, because the only routes to them are inside that gate. No new ownership machinery. |

### Pure-core boundary — still a UI rule

No component owns a rule. Standings, the tiebreak chain and where it stops, seeding, bracket
structure, bye placement, the cut, which matches a correction voids, the locked/reopened fold, the
recap fold and the remaining-match count are all **selectors and pure functions in `src/core/`**,
beside `selectIsTournamentComplete` (`selectors.ts:709`) and `selectPhase` (`:754`).
`npm run check:pure` fails the build on any DOM, clock, randomness, network, storage or `preact`
import there.

Five things in this phase are adapter- or UI-layer by necessity and are named so nobody has to
guess:

1. The focus handoffs above — DOM operations.
2. **The staleness comparison** — it reads a clock, so it lives in `src/adapters/` and is stamped
   at the edge. A core implementation would fail `check:pure`, and correctly.
3. **The refresh fetch and the roster-JSON file read** — `src/adapters/roster-source.ts`.
4. **The library's storage** — `src/adapters/persistence.ts`.
5. Which surface to render, which reads the stage selector and branches — it does not compute it.

If a surface here seems to need the UI to decide a rule, the selector is missing. Add the selector.

## Deferred, and recorded so the next planner does not discover it

- **Removing a library entry by hand.** Absent from D-14, D-15 and D-16, and deliberately not
  invented here. The only removal path is D-16's at-cap eviction. The cost is real — a host who
  fills the library with test tournaments evicts them one new tournament at a time — and it is
  recorded rather than solved, because adding a per-row destructive control with its own confirm is
  a decision the owner has not made.
- **TOUR-11, game-by-game logging inside a best-of-three.** v2. TOUR-04 is a label plus a 2-of-3
  counter and this contract renders exactly that. `MAX_MATCH_METRIC = 18` (6 × 3) is the seam: a
  future per-game log would replace the single number, not extend it.
- **TOUR-10, the free-text house-rules field.** v2, and `05-CONTEXT` names it explicitly as not the
  answer to "what else does tier 3 hold". Tier 3 holds the numeric field and the editable history,
  and nothing else (D-01).
- **REFR-04, a regulation selector.** v2. D-24 already gives a tournament its own snapshot by
  `rosterVersion`; pinning a *new* tournament to an older regulation is the missing half and is not
  this phase.
- **Double elimination, Swiss, consolation brackets, Buchholz.** `PROJECT.md` §Out of Scope. The
  bracket's CSS Grid is single-elimination-shaped on purpose; a losers bracket is not a variant of
  it. This is the phase where "the real discipline is refusing scope" (ROADMAP Notes) applies.
- **The WR-02 screen-reader check.** Descoped by the host at Phase 3 (`STATE.md`), which is why the
  live-region rules above are structural rather than verified. This phase adds two focus-moving
  announcements (the record and the cascade void) to the list already owed.
- **A results grid above 8 players fitting without horizontal scroll.** It does not, by
  measurement, and no gate or cap is added — the sticky label column carries it. Recorded so nobody
  adds one reflexively.
